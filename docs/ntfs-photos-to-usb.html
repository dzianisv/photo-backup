Back up photos to an NTFS USB drive from Android

The drive's format decides whether your phone can write to it at all. NTFS is a Windows format — most Android phones won't mount it, and the ones that do often mount it read-only. Check the format first, then pick the route that fits.

The honest centre: the format is the gate

A USB drive is not just storage — it is storage with a format, and the format decides who can write to it. NTFS is the format Windows uses for its own disks. It is robust and handles huge files, but outside Windows the support is patchy: a Mac opens an NTFS drive read-only, and most Android phones, cameras and car stereos don't open it at all. That is not a guess — it is what the format guides say, and it is the whole problem this article exists to solve. The drive that came out of a Windows PC, the external hard drive you have been using with your laptop for years, the flash drive a Windows machine formatted by default — all of them are very likely NTFS, and all of them hit the same wall when you plug them into a phone.

Android reads and writes FAT32 and exFAT natively on most current phones. NTFS is the odd one out: Android on most phones won't mount it, and a few manufacturers add support of their own, so the behaviour varies by phone. Where the phone does mount it, the mount is often read-only — you can look at the files, but you cannot add one. And "the phone can see the drive" is not one thing: an NTFS-writer app can show you the drive inside its own file manager while the phone itself still cannot mount it for other apps. That distinction matters, because SnapDisk writes to the mounted volume — the drive as the phone sees it — not to whatever one app's private drivers can reach. So the first question is never "which backup app", it is "what format is this drive, and can this phone write to it".

The second half of the honest centre is what SnapDisk does when the answer is no, and it was verified by reading the code at the current base, not by trying it on a phone. SnapDisk has no NTFS code at all — the word "ntfs" does not appear anywhere in the app, and there is no check for a read-only mount. The only format check in the app is the FAT32 one: a file of 4 GB or more on a FAT32 drive is skipped up front with the reason "use exFAT". On a drive the phone cannot mount at all, there is nothing to check: SnapDisk offers the backup when the phone reports a drive attached, and a drive the phone never sees produces no offer, no notification, nothing to tap. On a drive the phone mounts read-only, the offer does appear — the phone did report a drive — and the failure comes later, file by file, in a way the article spells out in its own section below. What the code cannot tell you is which of those two cases your phone falls into: whether a given phone mounts an NTFS drive read-only or not at all is unverified — no real-disk test of SnapDisk against an NTFS drive has been run, and the follow-up for exactly that test is still open in the Work Log. So this article tells you how the code behaves in both cases, and tells you to check the format before you trust either one.

First, check the drive's format

Do this before anything else, because the format decides which route you take, and because "the drive doesn't work with my phone" is very often a format problem wearing a different name. There are two checks, and you need only one of them to come back with an answer.

1. On a Windows PC: right-click the drive, then Properties. Plug the drive into a Windows computer, open File Explorer, right-click the drive, and choose Properties. The "File system" line says NTFS, exFAT, or FAT32 — that is the answer, in one word. This is the most reliable check there is, because Windows reports the format exactly as it is, with no app in between. If it says NTFS, the rest of this article is your route. If it says exFAT or FAT32, the drive is already writable and you can skip to Method 3.

2. On the phone: check the drive's Properties in a USB file-manager app. If there is no computer handy, plug the drive into the phone through an OTG adapter and open a file-manager app that reads USB drives. USB File Manager shows the file system among the drive's Properties — exact size, number of files and folders, file system, capacity, and free space — so the format is listed next to the capacity. The same goes for the NTFS-writer apps in Method 2: they show the drive they have mounted, and the format with it. One caution: if the phone shows nothing at all when you plug the drive in — no drive in the file manager, no notification, no offer from SnapDisk — that is itself an answer. The phone cannot mount the drive, and the most likely reason is the format: NTFS, on a phone that does not support it. Do not conclude the drive is broken, or the adapter is broken, until you have checked the format on a computer.

If the check says NTFS, do not try to force it. There is no setting on the phone that turns NTFS write on, no toggle in SnapDisk, and no file-manager trick that makes the phone's own mount writable. The routes that work are the ones in this article: change the format, or bring an app that carries its own NTFS driver, and copy by hand.

What you need

For the check: the drive, an OTG adapter if it is USB-A, and either a Windows computer or a USB file-manager app on the phone. For the reformat route: the same, plus somewhere to put the drive's current contents while you reformat — a folder on the computer, or another drive — because reformatting erases everything on the drive. For the NTFS-writer route: the NTFS-writer app of your choice, installed from Google Play, and the drive. For the SnapDisk route: the drive, reformatted to exFAT or FAT32, and the SnapDisk v0.1.2 APK (it is not on Google Play yet). One format note for every route: drives formatted FAT32 can't hold a single file over 4 GB. That only matters for very long videos — SnapDisk skips those files and lists them instead of failing the whole backup. A drive formatted exFAT has no such limit, and it is the format to use if you are formatting fresh.

Method 1: reformat to exFAT — the clean route

This is the route to pick when the drive does not have to stay NTFS — and for a photo-backup drive, it almost never does. NTFS is the right format for a drive that lives on Windows PCs. A backup drive that travels between a phone and a PC wants exFAT: Windows and Mac both write to it without extra software, Android reads and writes it on most current phones, and it has no 4 GB file limit, so a long 4K video copies in one piece. Reformatting is the only route in this article that ends with SnapDisk's one-tap backup working — because after the reformat, the drive is a drive the phone itself can write to, not one an app has to translate.

The price is stated up front because it is the whole risk: reformatting erases the drive. Everything on it — photos, documents, whatever the drive holds — is gone after the format. So the first step is not the format, it is the copy-off: plug the drive into a computer, copy everything on it to a folder on the computer, and check the copy before you format. Only then reformat. On Windows, right-click the drive in File Explorer and choose Format, then pick exFAT. On a Mac, open Disk Utility, select the drive, and click Erase, then pick exFAT. On the phone itself, a formatting app such as DriveForge formats the drive from the phone with an OTG adapter — it writes exFAT, FAT32 up to 32 GB, FAT16 and ext4 for free, and NTFS and large FAT32 with its one-time Pro unlock — so no computer is needed for the format step, only for holding the drive's contents while you do it. Whichever tool you use, pick exFAT, not FAT32: FAT32 caps a single file at 4 GB, and a long video will fail on it later, while exFAT takes files of any size.

After the format, the drive is empty and writable, and the rest is Method 3: plug it into the phone, tap Backup in SnapDisk, and the library copies oldest-first in the background. One more check before you trust the new format: after the first backup, open three or four photos from the drive on another device and confirm they render — the format change is only proven by a copy that reads back, not by the format dialog saying exFAT.

Method 2: an NTFS-writer app + manual copy

If the drive must stay NTFS — it is shared with a Windows setup that expects NTFS, or it holds files you cannot move off, or you simply do not want to reformat — the route is an app that carries its own NTFS driver. Android itself cannot write to the drive, so the app does the writing, through its own filesystem engines, and you do the copying, by hand, in the app's file manager. This is the honest trade of this method: it keeps the format, and it gives up the automation.

Four apps do this, and they differ in how you pay and how you copy. Paragon exFAT/NTFS for USB is a document provider built on Android's Storage Access Framework: install it, plug the drive in through OTG, mount the filesystem you need, and copy, move, delete and rename files using the file manager, with the drive reached through Paragon's provider. NTFS support is an in-app purchase — the listing says the supported filesystems are available via in-app purchase, and you can try the app in trial mode first. NTFS Reader: USB+Bitlocker is a file manager with its own USB storage stack: it reads NTFS free, and NTFS write unlocks with a single one-time in-app purchase; reading and writing exFAT and FAT32 is free, with no root and no computer. USB File Manager opens NTFS, exFAT, FAT32 and ext4 drives and reads and writes their files without a PC or root: copy and move files between the phone and the drive, import files or whole folders from the phone, and open files from the drive in other apps. AnExplorer reads and writes NTFS without root, again as a manual copy in its file manager. All four need a phone with USB host (OTG) support and an OTG adapter, and a large hard drive may need a powered USB hub — the drive has to appear for the app's drivers to reach it, and power is the usual reason it does not.

The manual copy itself is the same in all four: open the app, open the drive, select the photos — or a folder of them — and copy them to the drive, then wait. There is no oldest-first ordering, no whole-library run, no background progress notification with Pause and Stop, no resume where it stopped, and no per-file size verification beyond what the app shows you. A new batch of photos means the same manual selection again, and a copy interrupted halfway means working out for yourself what arrived and what did not. That is the price of keeping NTFS: the format stays, and the backup stays a chore. If the chore is the problem, Method 1 is the fix — reformat once, and the one-tap backup in Method 3 does the rest, every time, without the manual step.

One limit that applies to every app in this method, stated plainly: the NTFS write happens inside the app, through its own drivers. SnapDisk cannot use it. SnapDisk writes to the mounted volume — the drive as the phone sees it — and an NTFS-writer app's private mount is not that volume. So Method 2 and SnapDisk do not combine: you copy by hand in the NTFS app, or you reformat and let SnapDisk do it. There is no route where SnapDisk writes to an NTFS drive through another app's driver.

What SnapDisk actually does on a read-only drive

This section exists because the failure is silent in the worst way: the app does not warn you, and the run does not stop. It just skips everything, one file at a time, and ends. Here is exactly what happens, verified by reading the code at the current base — and where the code gives no answer, that is stated too.

First, the setup: SnapDisk has no NTFS detection at all. The word "ntfs" does not appear anywhere in the app's code, and there is no check for a read-only mount. The only format check in the app is the FAT32 one — a file of 4 GB or more on a FAT32 drive is skipped up front with its reason. So the app never tells you "this drive is NTFS" or "this drive is read-only". It only ever tells you, file by file, that a write failed.

Then the two cases. Case one: the phone does not mount the drive at all. This is the common case on most phones. SnapDisk offers the backup when the phone reports a drive attached — it listens for the system telling it a drive appeared — and a drive the phone never sees produces no offer. There is no notification, nothing to tap, and no error, because from the app's point of view nothing happened. If you plug the drive in and nothing appears, check the format on a computer before you blame the app or the adapter: the drive is almost certainly NTFS on a phone that does not support it.

Case two: the phone mounts the drive read-only. The offer appears — the phone did report a drive — and tapping Backup starts the run. The first file fails when the app tries to open its working file for writing: a read-only filesystem refuses the write, and the copy returns a failure carrying the full error. The service does not retry it — the retry-once rule fires only on a size-verification failure, when a copy finished but the size does not match, and a refused write is not that. It does not stop the run either: one bad file never stalls the job, so the file is recorded in the skipped list with its reason and the job moves to the next file. The next file fails the same way, and the one after that, and the run ends with every file skipped and nothing copied — 0 files, 0 bytes, the whole library listed as skipped. There is no "drive is read-only" message anywhere in that outcome; the skipped list is the only signal, and the full error behind each skipped file is what says the filesystem refused the write.

And the boundary of what is known: whether a given phone mounts an NTFS drive read-only or not at all is unverified — no real-disk test of SnapDisk against an NTFS drive has been run, and the follow-up for exactly that test is still open in the Work Log, with the Firebase Test Lab route never attempted. So this section tells you the code's behaviour in both cases, and the format check tells you which case you are in. Do not run a backup onto an NTFS drive and trust it without opening the copy on another device first — and if the run ends with everything skipped, the drive's format is the first thing to check, not the app.

Method 3: SnapDisk's one-tap copy — once the drive is writable

This is the backup step itself, and it belongs in this article for one reason: it is what the reformat in Method 1 buys you. Once the drive is exFAT or FAT32 — a format the phone itself can write to — the one-tap route opens, and this is how it runs. Install SnapDisk from the v0.1.2 APK (it's not on Google Play yet), then:

  1. Plug in the drive. SnapDisk offers a backup in a notification: "External storage is connected. Backup photos?"
  2. Tap Backup. Photos and videos copy oldest-first — your earliest photos first — in the background, while you use the phone normally. The default run reads the whole media library via MediaStore, not DCIM only, so every photo the gallery sees is covered, whatever folder it sits in. This was verified in the code, not assumed: with no From folder picked, the app queries the MediaStore images and videos tables with no folder filter.
  3. Watch the progress notification — real percent, copied / total size, speed, and time left — with Pause and Stop. You can pause and resume any time.
  4. Wait for "Backup complete." Every file is size-verified after copying, so the counts are proof, not a promise. Files that already copied are never copied twice — so if the free 5 GB per-run limit stops a big library partway, just run it again and it picks up where it left off.

Copying only some photos? If you would rather copy just one folder than the whole library, use the From folder picker: tap it, navigate to the folder, and the run copies only that folder, recursively. The picker route keeps only recognised photo and video extensions. If the drive is unplugged by accident, the backup pauses with the full error shown and resumes where it stopped when the drive is back. If a file is corrupt or too big for FAT32, it's retried once, then skipped with its reason listed — it never stalls the whole backup. The free version backs up manually, up to 5 GB per backup run, with no ads, no account, and no cloud. SnapDisk Pro is a one-time $9.99 purchase (no subscription) that starts the backup automatically when you plug in a disk and removes the size limit. The app has no internet permission, so your photos physically cannot leave your device.

And the combination, stated once more because it is the question this article exists to answer: the one-tap copy needs a writable drive. On exFAT or FAT32 it runs; on NTFS it does not — either nothing appears at all, or every file is skipped. That is not a SnapDisk limitation to work around with a setting; it is the drive's format, and the fix is Method 1 or Method 2. If you ran the format check and it said exFAT, run the backup and check the copy before you trust it: open three or four photos from the drive on another device, confirm they render, and only then treat the drive as the backup.

What to avoid

  • Reformatting without copying the drive's contents off first. Formatting erases the drive — everything on it, gone. Copy it all to a computer first, check the copy, and only then format. The reformat step is quick; the regret is not.
  • Assuming the phone will mount NTFS because the drive shows up somewhere. A drive can appear inside an NTFS-writer app's file manager while the phone itself still cannot mount it for other apps. Appearing in one app is not the same as being writable for SnapDisk — the app writes to the mounted volume, not to another app's private drivers.
  • Buying an NTFS-writer app before checking what the purchase unlocks. Paragon sells its filesystem support as an in-app purchase; NTFS Reader reads NTFS free and charges a one-time purchase for NTFS write, while exFAT and FAT32 read and write free. Read the listing before you pay, and remember the purchase buys a manual copy, not an automated backup.
  • Expecting SnapDisk to write to an NTFS drive. The app has no NTFS code and no read-only check. On a drive the phone mounts read-only, the run ends with every file skipped and nothing copied — and the skipped list is the only signal. Reformat first, or copy by hand in an NTFS-writer app.
  • Reformatting to FAT32 for a library with long videos. FAT32 can't hold a single file of 4 GB or more, and SnapDisk skips those files with "use exFAT". Pick exFAT when you format fresh: no 4 GB limit, and Windows, Mac and Android all write to it.
  • Assuming the copy keeps running with the screen off. Unverified — no wake lock, no battery-saver handling in the repo — so keep the phone awake for the run, or check it. Screen-off continuation under battery saver is unverified, and a run that stopped when the screen went dark is the expected failure, not a surprise.
  • Deleting before verifying. A backup is only a backup once you've confirmed the copy. Copy, open a few photos on the drive, then delete from the phone — never the other way round. SnapDisk only copies — it never deletes — so the delete step is always yours, and always after the check.
  • Unplugging mid-copy. Pulling a USB drive out while files are still writing can corrupt the file in flight. Wait for the copy to finish, or pause it first — SnapDisk's Stop button exists for exactly this.

Rule of thumb: check the format before you blame the app — most "won't back up to this drive" cases are NTFS, and the fix is a format change, not a different backup app. exFAT is the format a phone and a PC both write to, with no 4 GB limit — reformat once, and the one-tap backup works every time after.
