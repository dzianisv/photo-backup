Save WebP photos to a USB drive from Android

A WebP is an ordinary .webp file — smaller than a JPEG, with transparency like a PNG. The job is finding the file, because the apps that show you WebPs keep them in folders the backup never sees.

November 25, 2026 · 13 min read

TL;DR: A WebP is an ordinary .webp file, and everything that makes it worth keeping lives inside the file itself — the smaller size, the transparency, and, for an animated WebP, the frames stored one after another, no playback note, no sidecar file, nothing like the slow-motion case where the speed lives in a note attached to the video. That is the good news, and it makes the backup simple once you have the file: copy the .webp and all of it comes with it, byte-for-byte, because there is nothing to lose in the copy. The trap is getting the file in the first place, and it is a trap with two jaws. The first jaw is the web: most of the images you save from a browser are WebPs already, because the sites serve them that way — but they land in Downloads as .webp files with no fanfare, and nothing on the phone tells you they are not JPEGs. The second jaw is stickers: WhatsApp keeps every sticker you have ever sent or received as a .webp file in its Stickers folder, and that folder carries a .nomedia marker, so Android's media scanner never indexes it — which means SnapDisk's default run, which reads the media index, copies zero stickers while copying every photo in the library. The certain route copies the saved .webp file, never a re-shared copy: find it in Downloads, in Pictures, or in the WhatsApp Stickers folder, and copy that file to the drive. SnapDisk's default run covers saved .webp files with no folder to pick — .webp is a recognised image extension, and Android indexes image/webp files in the MediaStore Images table exactly the way it indexes JPEGs — so plug in the drive, tap Backup, and the WebPs copy along with everything else, except the stickers, which need the From picker pointed at their folder. The check is opening one WebP back from the drive and watching it move, if it is animated, with no white box behind it, if it is transparent: a WebP that lost its animation or its transparency still looks like a photo in every other check. And screen-off continuation under battery saver is unverified — the repo holds no wake lock and no battery-saver handling — so keep the phone awake for the run or check it. As of November 25, 2026, no top search result offers a dedicated WebP-to-USB how-to: the results are generic OTG copy guides that never name WebP at all.

The wall: the WebPs you see are rarely files you chose — and the files that are WebPs hide in three folders

Start with the fact that decides the whole job, because the WebP wall is easy to misread in both directions at once. It is not a locked door like Threema's wall: the photos exist and the app will not let them out until you save them. And it is not a hall of mirrors like the GIF wall: the GIFs are everywhere on your screen and almost none of them is a file. The WebP wall is a filing error. The files exist, the phone can open them, the backup can copy them — and they sit in folders nobody thinks to look in, under a name nobody recognises, because WebP arrived quietly. It is Google's format, and it has been the web's default image format for years: smaller than a JPEG at the same quality, with transparency like a PNG, and able to animate like a GIF. Android has supported it since 4.0 for lossy images and since 4.2.1 for lossless images and transparency, and Android's own gallery and image viewers generally open WebP. So a phone can hold hundreds of WebP files — downloaded images, converted photos, every WhatsApp sticker — and the owner has never once seen the extension, because the gallery shows the picture and never the filename.

That is the wall, and it is a total one in the same way the messaging-app walls are, but with the blame in a different place. A phone full of WebPs that were never hunted down is a phone full of files the backup copies only by accident: the default run copies the ones the media index knows about — the Downloads saves, the Pictures exports — and misses the ones it does not, because the WhatsApp Stickers folder carries a .nomedia marker that keeps the whole sticker collection out of the index. The difference from Threema is what counts as the save. Threema gives you a switch and a save button, and the saved file lands in a named folder. WebP gives you no switch at all, and the save is scattered across the phone: a browser download lands in Downloads, a converted photo lands in Downloads or Pictures, a sticker lands in a folder whose name you have never typed. There is no single save step to turn on, and no single folder to point at. The job is a hunt first and a copy second, and the hunt is the part this article does that the generic guides do not.

Two scope facts, because they decide what this article can and cannot promise. First, the file itself is simple in a way that should reassure you once you have it: a WebP is an ordinary file with everything stored inside it — the smaller size is the compression, the transparency is an alpha channel in the file, and the animation, for an animated WebP, is a sequence of frames, exactly like a GIF. Copy the .webp and you copy all of it — every frame, the transparency, at the original quality — because the copy is byte-for-byte and the bytes are the picture. There is no conversion step to get wrong and no quality setting to choose, and SnapDisk never converts anything in any case. Second, the format confusion is real and worth naming plainly: a WebP is not a JPEG with a different name, and renaming a file does not convert it. A file called photo.webp holds WebP data; renaming it to photo.png leaves WebP data inside a file called .png, and the next app that opens it by extension will fail or misread it. The guides that measured this say it outright: keep the extension the site supplied unless you intentionally convert the file with an image editor. This article is about the .webp files; a file that was renamed is a different problem, and the fix is converting it properly, not renaming it back.

And a word on whose WebPs these are, because WebPs are usually someone else's picture — a photo from a site, a sticker someone made, a meme clipped from a show — and because the line between saving and re-posting is worth stating plainly. The WebPs this article covers are the ones you downloaded or were sent for yourself: an image you saved from a web page, a sticker a friend sent you in a chat that you want to keep. Saving them to your own drive for your own records is the job. They are also someone else's work in a plain sense: a photograph with a photographer, a sticker with an author you will never meet. Saving a file does not grant permission to reuse it — so re-posting a WebP as if it were yours, or using someone's picture in your own content without asking, is a different act, and the same courtesy applies here as anywhere: the person who made it is the person to ask before the WebP leaves your phone for anywhere else. This article's methods copy the file to your drive; what you do with it afterwards is yours to decide, and asking is the honest step before anything leaves your phone. Only save WebPs you have permission to keep — and this article makes no claim about recovering WebPs from a chat you have already deleted, because the chat apps keep no .webp file to recover once the chat is gone, and a WebP that was served from a library was never yours to recover in the first place.

Where .webp files live on an Android phone — Downloads, Pictures, and the WhatsApp Stickers folder

This section exists because the folder is the one fact the guides do not answer at all — and because WebPs, unlike the messaging-app photos in this series, have no single home folder. A Threema photo lands in Pictures/Threema; a WhatsApp photo lands in WhatsApp Images. A WebP lands wherever the thing that made it put it, and the phone has three different makers. So this article does not state one path as the path for every WebP. It gives the check order instead, and the check order is the same on every phone — and the check itself is the file extension, not the app that showed it to you. A file that ends in .webp is a WebP; a file that ends in .jpg is a JPEG, even if it looks identical on screen.

Check Downloads first. Open your file manager, go to Internal Storage, then Download — or open Files by Google and tap Downloads. This is where a WebP downloaded from a browser lands: Chrome on Android saves every download to the shared Downloads folder by default, at Internal Storage/Download, and the guides agree on the path across manufacturers. A WebP you long-pressed on a web page and saved, a WebP you downloaded from a converter site, a WebP someone sent you as a file attachment that your app saved to Downloads — all of them land here, as .webp files with their transparency and animation intact. Most of the images on the modern web are served as WebP, so an image you save from a site is a .webp far more often than a .jpg now — and the save keeps the site's format, so the file you get is the format the site sent. If you have ever saved an image from the web on purpose, it is almost certainly here, and this is the folder to check first because it is the only folder a deliberate WebP save reliably produces.

Check Pictures second, and the WhatsApp Stickers folder third — and understand that the third check is the one this article exists for. Pictures is where a WebP saved from an app that writes to the shared Pictures directory lands, and where a converted photo exported by an editing app usually goes, and it is worth a look when Downloads comes up empty. Then check the WhatsApp Stickers folder — Internal storage, Android, media, com.whatsapp, WhatsApp, Media, WhatsApp Stickers — for the sticker collection: WhatsApp stores every sticker you have sent or received as a .webp file in that folder, and the guides that walked it report finding a large number of WebP files there, your personal collection and every single one you have ever received. WhatsApp Business keeps the same folder under com.whatsapp.w4b instead of com.whatsapp. The folder is reachable with any standard file manager, no root needed — but it carries a .nomedia marker, so the stickers never show in your gallery, and the gallery is the check that would have told you they were there. If the file is in none of those places, check that the save actually happened: a WebP you only viewed on a web page was never saved, a sticker you picked from the keyboard's search was served from a library and never touched your storage, and a Telegram sticker lives in Telegram's own cache, not in any folder you can open. The hunt ends where the file begins — and for a WebP that was never a file, the hunt ends with making one: save the image from the web page, or export it from the app that made it, and then it is a file like any other.

One more scope fact for this section, because it decides what the drive copy holds: the saved .webp is the WebP as it was when you saved it, and the phone gives you no way to improve it afterwards. A WebP is already the small version — that is the point of the format, smaller than a JPEG at the same quality — so a WebP saved from the web is already a compressed copy of whatever the site had, and copying it byte-for-byte keeps it exactly that good and exactly that bad. SnapDisk copies the saved file with no conversion and no quality change — but it cannot recover detail the WebP compression already removed, and it cannot upgrade a WebP someone sent compressed. If the picture you want is a photo you still have as a JPEG in your camera roll, the JPEG is the one worth keeping alongside it: the WebP is a smaller copy the web made for loading fast, and the original is the one with the full detail. The WebP route for a photo you still have as a JPEG is only needed when you want the file as a WebP — for a website, for a sticker, for the one place that only renders WebP. And the WebPs you converted yourself in the browser are a separate case again: they were made from a JPEG or a PNG, and the original is usually still in your camera roll in DCIM/Camera — back that up too, because the WebP is a small copy of a moment the original holds in full.

What you need

An Android phone — Android 7.0 or later, which is SnapDisk's minimum version — with the apps that hold your WebPs already on it, plus one USB drive your phone can read: a USB-C flash drive, or a regular USB drive with a USB-C OTG adapter. SnapDisk itself is installed from the v0.1.2 APK — it is not on Google Play yet — so install it by allowing "install unknown apps" for the browser or Files app you download it with, which is standard Android. You need nothing else for the main route: no file manager, no extra app, no account. The hunt step is inside the apps you already have — the browser's Downloads, the Gallery, the file manager — and the backup is SnapDisk's default run. Check the drive's space first: WebPs are small — a WebP is usually well under a megabyte, a sticker far less — so space is almost never the problem here, but look anyway, because a whole-library default run copies everything, not just WebPs. One format note: drives formatted FAT32 cannot hold a single file over 4 GB. That only matters for very long videos — SnapDisk skips those files and lists them instead of failing the whole backup. A drive formatted exFAT has no such limit, and exFAT is the format to use for a photo drive.

Before any method, settle the one question that decides whether the phone route works at all: does your phone see the USB drive? Plug the drive in and open Settings > Connected devices or Settings > Storage — the drive should appear there. That check is the test, and it takes ten seconds. If the drive does not appear, try a different adapter first — cheap OTG adapters are the usual failure — then a different drive, and a powered hub if the drive is a spinning hard drive rather than a flash drive. And one warning up front, because it applies to every route below: do not delete anything from the phone until the USB copy is done and verified. The WebPs in Downloads are yours — but until the drive copy is checked, Downloads is the only copy outside the browser, and deleting from Downloads before the check is how a WebP ends up nowhere at all. And do not delete the chat app, or clear its data, until the save and the copy are both done: a sticker that was never copied as a file is gone when the chat is gone, and WhatsApp keeps no second copy of a sticker outside its Stickers folder.

Method 1: Find the saved .webp, then back up with SnapDisk

This is the route to use, because it is the only one that joins the whole job — the .webp file, found on the phone, onto a USB drive plugged into the phone, no computer — using only the apps already on the phone plus SnapDisk. It has two halves, and they have to happen in order: the hunt, which finds the .webp files, and the SnapDisk copy, which puts them on the drive. The first half is the work, and with WebPs it is a hunt across folders rather than a single save step, because there is no switch to turn on and no single folder to open. Skipping the first half is the mistake this article exists to prevent: running SnapDisk's default backup without knowing where the WebPs are copies every photo in the gallery — and zero stickers, because the stickers sit in a folder the media index never sees.

  1. Hunt the .webp files first, in check order. Open your file manager and go to Internal Storage, Download — the browser-downloaded WebPs live here, as .webp files. Then check Pictures for WebPs saved from apps that write there. Then open the WhatsApp Stickers folder — Internal storage, Android, media, com.whatsapp, WhatsApp, Media, WhatsApp Stickers — and look at what is inside: every sticker you have ever sent or received, as a .webp file. The check at each stop is the file extension: a file that ends in .webp is a WebP, and a file that ends in .jpg is a JPEG, even if it looks identical on screen. If a folder holds no .webp files, move on — do not assume the WebPs are there because the folder's name sounds right. If you find WebPs in more than one folder, note all of them: the default run covers the indexed ones all at once, and the picker route in Method 2 needs one pick per folder — and the stickers need their own pick, because the default run never sees them.
  2. If the hunt comes up empty, make the file before you back it up. A WebP you only viewed on a web page was never a file, and a sticker you picked from the keyboard's search was served from a library — neither is on the phone, and no step in this article conjures a file out of a viewed picture. The fix is at the source: long-press the image in the browser and save it, and it lands in Downloads as a .webp — or export it from the app that made it, and it lands in Downloads or Pictures as a .webp. A WebP sent to you as a file attachment, rather than as a chat image, is already a file: save the attachment, and it lands in Downloads or the app's folder as a .webp. Do not try to rescue a chat picture by sharing it to yourself: the share step can flatten an animated WebP to a still, or hand on a JPEG instead of the WebP, and a shared copy is the least reliable WebP on the phone.
  3. Do not re-share a WebP to get it onto the drive. This is the trap the whole article is built around, and it deserves its own step because it looks like the obvious shortcut. Sharing a WebP out of the Gallery or a chat into another app — into a file manager, into a different chat, into yourself — can change it on the way: some share targets take only the first frame of an animated WebP and hand on a still, and some re-encode the file as a JPEG, dropping the transparency with it. A flattened or converted copy is a still image or a JPEG wearing a WebP's name, and no backup step after it restores the animation or the transparency, because both were lost in the share, not in the copy. The certain route copies the saved .webp file, never a re-shared copy — and if the only copy you have is a re-shared one, go back to step 2 and save the WebP from its source instead.
  4. Check the files are in Downloads, or the stickers are in their folder. Open your file manager, go to Downloads, and look for .webp files — if they are there, the save works. Then open the WhatsApp Stickers folder and look for .webp files — if they are there, the stickers exist as files, and this is also the check that proves the picker route in Method 2 can reach them, because the file manager and the folder picker read the same folders. If the files are in the folder but not in the gallery, that is expected for the stickers — the .nomedia marker keeps them out of the gallery by design — and it is not a problem for the picker route, which does not use the gallery. If no folder holds a .webp at all, the save is the suspect: a WebP you viewed was never saved, and step 2 is the fix — save it from the web page or export it from the app.
  5. Plug in the drive and run SnapDisk. Plug the USB drive into the phone. SnapDisk offers the backup in a notification — tap Backup — or open the app and tap Start. The run copies oldest-first, verifies every file by size after copying, and shows progress with Pause and Stop in the notification. The free run covers up to 5 GB, and WebPs are small, so one run is almost always enough for the WebP half — though a whole-library run copies everything else too, and that is the point: the saved WebPs come along with the rest, with no folder to pick and no step to remember — except the stickers, which need Method 2, because the default run never sees them. Screen-off continuation under battery saver is unverified — the repo holds no wake lock and no battery-saver handling — so keep the phone awake for the run or check it.
  6. Do not plan around the WebPs you never saved. A WebP you only viewed on a web page is still on the web page, and no step in this article changes that: there is no save-all for a page's images, and there is no export that writes a page's WebPs out as files. If a WebP matters, save it from its source now, while the page is still up — a WebP that was served from a site is gone when the site stops serving it. A screenshot is the only copy left for a WebP the built-in save will not give you — and a screenshot is a picture of the screen, not the WebP: it is a still image, usually a PNG or a JPEG, it carries the app chrome around it, it lands in the Screenshots folder, not with the WebPs, and it does not animate and has no transparency to keep. Do not plan a backup around saving what the apps will not let you save as a file.

Two honest limits. First, the hunt is not retroactive in the other direction either: finding WebPs today does not put the WebPs from a chat you already deleted onto the phone — a deleted chat is gone, and WhatsApp keeps no second copy of a sticker outside its Stickers folder. That is step 2's job, and it is a manual job: one save per WebP. Second, the 5 GB free cap is per run — a WebP collection will never reach it, but a whole-library default run might, and running it again picks up where it stopped, because files already copied are never copied twice. Third, SnapDisk copies, it never deletes: deleting the WebPs from the phone after the check is always your step, never the app's — and deleting them from the chat is the chat app's, not SnapDisk's, and it does not free the drive copy. The drive copy is the backup; the phone copy is the original until you decide otherwise.

Copying only some WebPs? If you would rather copy just a few WebPs than the whole collection, the From folder picker still takes a folder, not single files — so copy the ones you want into their own folder first (in the file manager, or by saving them to the gallery and selecting them there), then point the picker at that folder. The picker route keeps only recognised photo and video extensions. If the drive is unplugged mid-copy, the backup pauses with the full error shown and resumes where it stopped when the drive is back. If a file is corrupt or too big for FAT32, it's retried once, then skipped with its reason listed — it never stalls the whole backup. The free version backs up manually, up to 5 GB per backup run, with no ads, no account, and no cloud. SnapDisk Pro is a one-time $9.99 purchase (no subscription) that starts the backup automatically when you plug in a disk and removes the size limit. The app has no internet permission, so your photos physically cannot leave your device.

And the check that matters for this article: after the run, open a WebP back from the drive and look at it — watch it move, if it is animated, and check there is no white box behind it, if it is transparent. A green backup that copied the whole library has still copied zero stickers if nothing was ever picked from the Stickers folder — which is exactly what happens when the stickers were only ever seen inside WhatsApp. Open the drive and look for the WebPs by extension: the default run mirrors the source tree, so the files should be there as .webp files, in Downloads or the Pictures folder. If they are missing, the hunt is the suspect, not the run — find the .webp files first, then run again. SnapDisk copies, it never deletes — the only files it ever deletes are its own half-finished .part files — so deleting the originals after the check is always your step, never the app's.

Method 2: Point the From picker at the folder that holds the WebPs

If you would rather copy just the WebPs and nothing else — and the WebPs are already saved as files — point SnapDisk's From folder picker at the folder that holds them. Open SnapDisk, tap the From folder picker, and navigate to the folder you found them in, using the check order in the folder section above: Downloads first, then Pictures, then the WhatsApp Stickers folder — and tap Backup. To get everything in Downloads at once, pick the Downloads folder itself: SnapDisk walks the folder recursively, so one run copies the WebPs and any other photo or video that lives under Downloads together. The same 5 GB free cap applies, and the same oldest-first order, size verification, Pause and Stop.

The honest limit on this route is that it is the code-supported route, not the test-proven one — and this article says so rather than claiming a test that never ran — and the folder itself is the second honest limit. The picker is the system's folder picker, and the code has no WebP path handling anywhere — zero matches for "webp" as a folder in the whole source tree, only the .webp extension in the recognised-extensions list — so the navigation is yours, step by step, through folders whose names are ordinary. But the exact folder depends on where the WebP was saved — Downloads for a browser download, Pictures for an app save, the WhatsApp Stickers folder for a sticker — so this article does not state one folder path as the path, and no SnapDisk test has picked any of these exact folders yet. None of the candidate names starts with a dot, so none of them is hidden from the picker the way a dot-folder would be, and the folders sit in shared storage, not under Android/data, so the scoped-storage wall that blocks the Telegram folder does not apply here at all. And the folder walk recurses into every subfolder it can list, so picking the parent Downloads folder reaches every WebP under it. But the end-to-end pick is untested, and this article marks it as such. If the picker will not show the folder on your phone, fall back to Method 1: find the .webp files first, then run the default backup, which is the route that is proven to work. And one more scope fact for this route: the folder walk keeps only recognised photo and video extensions — a document in the folder is simply skipped, and a chat is never copied, because a chat is not a photo or a video. For a whole chat, use Method 3 — this article is only about the .webp files.

One WebP-specific reason Method 2 matters more here than in the other format articles: the split between the indexed WebPs and the stickers. The default run reads the media index, and it reads both the images table and the videos table, so it covers Downloads' .webp files and Pictures' .webp files together with no step beyond the hunt. The picker route does not need the index at all: it walks one folder tree directly, so pointing it at the WhatsApp Stickers folder reaches the stickers the default run cannot see — the .nomedia marker that hides them from the index means nothing to a walk that lists files directly. That makes the picker the route for the stickers, and the default run the route for everything else. This is a code-grounded difference, not a guess: the default path queries both MediaStore tables, while the picker path walks one folder tree — and the split is WhatsApp's own .nomedia marker, which hides the stickers from the index before the files ever reach a folder. The pick itself is still untested end to end on a real phone, and this article marks it as such — but the reason the picker covers the stickers where the default run covers the rest is the code's own two paths, stated as such.

Method 3: The WebPs that are not files — WhatsApp stickers, Telegram stickers, and the keyboard

WhatsApp stickers, Telegram stickers, and the keyboard are the three places WebPs are seen most and saved least, and they are worth untangling carefully, because each one fails in a different way — and each failure looks like a backup problem when it is really a file problem. WhatsApp is the first, and it is the one with a route: every sticker you have sent or received is a .webp file in the WhatsApp Stickers folder, and the guides agree on the shape — the folder holds your personal collection of stickers and every single one you have ever received, and the files are small WebPs, a still sticker no more than 1024 pixels on its long side and under 400 KB, an animated sticker a 512×512 WebP. The folder is public, in shared storage, and any standard file manager can open it. So a WhatsApp sticker is a file, and Method 2 copies it — the only catch is the .nomedia marker, which keeps it out of the media index and therefore out of the default run. If you want the .webp itself, ask nothing of anyone: open the folder, and it is there.

Telegram is the second, and it is stricter: a Telegram sticker is a WebP too — the static ones are .webp files, 512×512 — but Telegram keeps them in its app-private cache under Android/data, and the guides state the access plainly, that root may be needed on Android 11 and later to reach them. So there is no Telegram sticker folder to back up, and no Telegram sticker file to hunt for with the tools on the phone: the stickers you saved inside Telegram live in your Telegram account and reappear on any device you sign into, and the files in the cache are copies Telegram made for itself, not files it offers you. The animated Telegram stickers are a different format again — .webm video, not WebP — so even a cache copy would not be the file this article is about. Both still back up in the only sense that matters: the stickers need nothing, because they live in your account. But a drive holding nothing holds no Telegram stickers at all — because the stickers were never files in shared storage. If you want a Telegram sticker as a .webp, the route is the same as the GIF route: get the original file from its source — the sticker pack's download, the sender as a document — and save that file to Downloads.

The keyboard is the third, and it is the quietest of the three: a sticker you pick from the keyboard's search — the sticker button in Gboard or in the chat app's own sticker search — is served from a content library and never touches your storage. The guides state it in the same breath as the WhatsApp folder: a sticker from the keyboard's search loads from a library, has no file size issue, and leaves no file behind. So a sticker you sent from the keyboard was never yours to back up in the first place: it is a library entry you borrowed for one message, and the copy of it that matters — if any — is the one in the chat history, which the chat app holds and which no backup in this article touches. The fix is the same as the other two: if a keyboard sticker matters enough to keep, find it at its source — search the sticker site for it, download it from the web page, save it to Downloads as a .webp — and then it is a file like any other, and Method 1 covers it. And the same permission rule applies to all three routes: only save WebPs you have permission to keep, and do not use a backup tool to pull someone else's picture out of a chat you were never meant to keep.

Can SnapDisk read the WebP folders directly?

This is the question the whole article turns on, and it deserves a straight answer in three parts — what the code proves it can do, what is untested, and what would prove the rest. The first part is proven, from the code at the current base and from how Android's media index works — and it is the same shape as the GIF case, with one WebP-specific condition. SnapDisk's default run reads the phone's media index — it queries the MediaStore images and videos tables, oldest-first by date taken, with no folder filter. A saved .webp file is an ordinary indexed file: Android's own developer documentation states that each MediaStore collection is organised by the primary MIME type of the content, and that image/* content is indexed under Images — and a WebP's MIME type is image/webp, so a WebP is indexed under Images exactly the way a JPEG is. The app's recognised image extensions include .webp, in the same list as .jpg, .png, and .heic. The query is in PhotoQuery.kt, the no-folder-filter shape is the code's own design — the query call passes no selection at all — and the gallery evidence is the platform fact that closes the loop. So the default run sees saved WebPs that show in the gallery, and it sees them with no step beyond the hunt. That is not an assumption: it is the code's query shape plus the platform's indexing rule, stated as such. And the default run copies the whole library, not DCIM only — the query reads every indexed image and video on the phone, whatever folder it sits in, so the WebPs in Downloads are covered the same way DCIM is.

The condition is the .nomedia marker, and it is the part that makes WebP different from every other format in this series: the default run's coverage is conditional on the WebPs having been indexed, and the WhatsApp Stickers folder is not indexed at all — the folder carries a .nomedia marker, which tells Android's media scanner to skip it, so the stickers never enter the index the default run reads. If the stickers are the WebPs you care about, the default run copies zero of them while the chats sit full of stickers. The fix is its own: point the From picker at the Stickers folder, so the folder walk lists the files directly instead of asking the index. Until that is done, the default run copies zero stickers while the folder sits full of .webp files. This article states the condition in the TL;DR, in the wall section, in Method 1 steps 1 and 5, and here — because a guide that promised the default run covers every WebP, without the condition, would be wrong on exactly the phones where the WebPs are stickers. The second condition is the share trap: a WebP that was re-shared into a still or a JPEG is a still or a JPEG in the index too, and the default run copies it faithfully — the copy is correct, and the file was already wrong.

The second part is untested, and this article marks it as such rather than guessing in either direction: whether SnapDisk's From folder picker reaches the WebP folders end to end on a real phone. The picker is the system's folder picker — ActivityResultContracts.OpenDocumentTree, in MainActivity.kt — and it opens with no folder pre-selected: there is no initial-folder hint anywhere in the code, and no WebP path handling anywhere in the app — the only "webp" in the source is the .webp extension in the recognised-extensions list. The navigation chain is ordinary folders — Downloads, Pictures, the WhatsApp Stickers folder — none of them dot-prefixed, so none of them is hidden from the picker the way a dot-folder would be, and the folders sit in shared storage, outside Android/data, so the scoped-storage wall that blocks the Telegram folder does not apply here. The sticker guides report that the system's folder picker does show the WebP files in the Stickers folder. And the folder walk recurses into every subfolder it can list, so picking Downloads should reach every WebP under it. But the exact folder depends on where the WebP was saved, and no SnapDisk test has picked any of these exact folders yet, so the end-to-end pick is untested — do not plan a backup around it as the only route, and do not assume it fails either. The joined workflow in Method 1 is the route that is proven to work, and it is the route this article gives first. The picker has one WebP-specific limit the default run does not, stated in Method 2: it walks one folder tree, so Downloads gives the indexed WebPs and the Stickers folder needs a second pick for the stickers — but that limit is itself untested end to end, and this article marks it as such too.

The third part is what the code does prove about the rest of the job, so the limits above are not mistaken for a wider doubt. The manifest requests the media-read permissions (READ_MEDIA_IMAGES and READ_MEDIA_VIDEO, plus the older READ_EXTERNAL_STORAGE capped at Android 12), the notification permission, and foreground-service permissions — and no INTERNET permission at all, zero occurrences, so the photos physically cannot leave the device. It does not request all-files access — no MANAGE_EXTERNAL_STORAGE anywhere — which is the permission a file manager uses to browse another app's folders freely, and the absence is the reason SnapDisk cannot simply walk into Telegram's app-private cache the way a file manager can; the folder picker is the route instead, and it needs your tap. The backup itself is the verified core: oldest-first by date taken with a date-modified fallback (PhotoQuery.kt), every file size-verified after copying (BackupEngine.kt), Pause and Stop in the notification (NotificationHelper.kt, BackupService.kt), files of 4 GB or more on a FAT32 drive skipped with their reason instead of stalling the job (BackupService.kt), and the free run capped at 5 GB with Pro a one-time $9.99 purchase (ProPrefs.kt). None of that changes the picker verdict — it bounds it. The backup engine is proven; the end-to-end pick of these exact folders is not yet tested.

WebPs you downloaded vs WebPs the apps made

The route is the same for both, but the starting point is not, and it is worth saying which one you are saving before you start. WebPs you downloaded — the case this article is really about — are the ones the hunt governs: with the save they land in Downloads or Pictures, and without it they are not on the phone at all, and the methods above are written for them. WebPs the apps made are different, because the apps made them for their own use: a WhatsApp sticker is a .webp file in a folder you can open, and a Telegram sticker is a .webp file in a cache you cannot. Back the WhatsApp ones up with the picker, and leave the Telegram ones in the account — they reappear on any device you sign into, and no file on the phone holds them in a form the picker can reach. That matters more than it sounds, because the stickers are often the WebPs you care about most: a sticker pack you built over years, a reaction shot you use every day, the one sticker nobody else has. The WhatsApp ones are files, and files can be backed up. The Telegram ones are account entries, and account entries back themselves up by syncing.

One related corner is worth a line, because WebP owners hit it and it looks like a shortcut that is not one: a WebP sent as a file, rather than as a chat image, is a different thing again — WhatsApp lets you send files as documents, and a WebP sent that way is sent as-is, without conversion, and it lands in Downloads or the app's folder as a .webp. That is the one WhatsApp route that preserves the WebP, and it is the route to ask for when someone sends you a WebP you want to keep: ask them to send it as a document, not as a picture in the chat. The same shape holds on Telegram: a WebP sent as a file lands as a file, while a WebP sent as a photo can be re-encoded as a JPEG. If a WebP you are missing was sent as a chat picture, check Downloads for the file version first — and if the .webp itself is what you want, ask the sender to re-send it as a document. And one more WebP-specific corner: a WebP with transparency — a floating sticker with no background — is the one WebP that must stay a WebP, because converting it to JPEG fills the transparent areas white, and converting it to MP4 does the same. If your WebP relies on transparency, keep it as a .webp and do not convert it; the JPEG versions the chat apps make already lost the transparency when they converted it, and no backup step brings it back.

Checking the drive after the copy

The check has two halves, and they have to happen in order: first that the hunt actually produced .webp files on the phone, then that the drive holds them whole. After the SnapDisk run finishes, open the drive on a computer or on the phone itself and count: the drive should hold the WebPs you saved, in a Downloads folder of their own — the default run mirrors the source tree, so the files should be there by name and extension — and one opened at random should look right. Open a WebP itself — not just any photo on the drive — because a run that covered the rest of the library would still look complete on a random check while the one format you cared about was missing. Open it in a viewer that plays WebP — a browser, the gallery app, or a file manager with a preview — and watch it: an animated WebP should move for a full loop, and a transparent sticker should show no white box behind it. If it moves and the background is clear, the copy is good: the animation is frames stored inside the .webp file and the transparency is an alpha channel inside the same file, and a byte-for-byte copy carries all of both. If the count is short, the run is not the first suspect — the hunt is. Check Downloads: are the .webp files actually there, and do they end in .webp? If the folder holds no .webp files, the WebPs were never saved — save them from the source and run again. If the files are in Downloads but not on the drive, the run is the suspect, and the run needs repeating, not a different folder. If the files are in the folder but not in the gallery, the media scanner is the suspect for the indexed ones — restart the phone to force a rescan, and run again — or pick the folder directly with the From picker, which does not depend on the gallery. And if the stickers are the ones missing, the .nomedia marker is the suspect, not the run: the default run never sees them, and the picker route in Method 2 is the fix.

If the drive's free space ran out mid-run, the run stops with the full error shown; free space by moving the drive's contents to a bigger drive first, or back up to a second drive. If the run stopped at the 5 GB free cap — unlikely for a WebP collection alone, possible on a whole-library default run — run it again and it picks up where it stopped, because files already copied are never copied twice. If a WebP on the drive does not move, the copy is not the suspect — the source is. Check the source file's extension: if it ends in .mp4, the animation was converted by a chat app before you copied it; if it is a still image, it was flattened by a share step. Find the original .webp in Downloads or the WhatsApp Stickers folder and copy that file instead. And the check that matters most for a WebP that only existed inside a chat: confirm the drive copy before you delete anything from the phone. The copy in Downloads is an ordinary file and will survive; the copy in the chat depends on the chat app keeping it, and a WebP that was served from a library is gone when the library stops serving it. The drive is a plain folder of plain files. Anyone who picks up the drive can open them. That is the price of a copy you can open anywhere, and it is worth stating before the WebPs leave the phone — especially for WebPs, where the picture is often someone else's work.

What to avoid

  • Assuming a WebP you viewed is a .webp file on your phone. It usually is not saved until you save it — a WebP you only viewed on a web page was never a file, and a sticker you picked from the keyboard's search was served from a library and never touched your storage. A one-tap backup copies zero WebPs until the WebPs exist as .webp files in Downloads, Pictures, or the WhatsApp Stickers folder.
  • Assuming the default run covers your WhatsApp stickers. It cannot — proven from the code and the platform: the default run reads the media index, and the WhatsApp Stickers folder carries a .nomedia marker that keeps the stickers out of the index. A green backup copies zero stickers while the folder sits full of .webp files.
  • Assuming the chat apps keep .webp files. WhatsApp does — its stickers are .webp files in a folder you can open — but Telegram keeps its stickers in app-private cache under Android/data, which no file manager or folder picker on the phone can reach, and a keyboard sticker was served from a library and never touched your storage. The Telegram stickers live in your account and reappear when you sign in; the keyboard ones were never yours to keep.
  • Re-sharing a WebP to get it onto the drive. Sharing a WebP out of the Gallery or a chat can flatten an animated WebP to a still, or re-encode it as a JPEG and drop the transparency. Copy the saved .webp file, never a re-shared copy; a flattened or converted copy never animates again and never gets its transparency back.
  • Renaming a file to change its format. Renaming photo.webp to photo.png does not convert it — the WebP data stays inside a file called .png, and the next app that opens it by extension will fail or misread it. Convert with an image editor or a converter; never rename.
  • Assuming one folder holds every WebP. UNVERIFIED as a single path — the folder depends on where the WebP was saved: Downloads for a browser download, Pictures for an app save, the WhatsApp Stickers folder for a sticker. Check Downloads first, then Pictures, then the Stickers folder — do not plan a backup around a single path.
  • Assuming the From picker route is test-proven. Untested — no SnapDisk test has picked the Downloads, Pictures, or WhatsApp Stickers folders yet, and the exact folder depends on where the WebP was saved. The code supports it and the folder names are ordinary, but do not plan a backup around it as the only route; Method 1's hunt-first workflow is the proven one.
  • Assuming the default run covers the stickers if you only picked the Downloads folder. It does not — that is the picker route, not the default run. Pointing the From picker at Downloads copies the indexed .webp files and not the stickers, which live in the WhatsApp Stickers folder and need a second pick. The default run covers the indexed ones, because it reads the media index; it never covers the stickers, because the index never sees them.
  • Assuming a still on the drive means the copy failed. It does not — the copy is byte-for-byte, so a still on the drive means the source was already a still: a WebP flattened by a share step, or a screenshot. Check the source file, not the run; find the original .webp and copy that file instead.
  • Assuming a WebP you converted is the original. A WebP you made from a JPEG or a PNG is a smaller, compressed copy of it. The original is usually still in DCIM/Camera at full quality. Back the original up, and use the WebP only when the original is gone — except a transparent sticker WebP, which must stay a WebP, because converting it fills the transparency white.
  • Assuming a screenshot is the WebP. It is not — a screenshot is a picture of the screen, a still image, usually a PNG or a JPEG, carrying the app chrome around it, and it lands in the Screenshots folder, not with the WebPs. It does not animate and it has no transparency. Save the WebP itself when the save works, and screenshot only when it does not.
  • Assuming screen-off continuation under battery saver. UNVERIFIED — the repo holds no wake lock and no battery-saver handling. Keep the phone awake for the run, or check it.
  • Using a FAT32 drive for a library with long videos. FAT32 cannot hold a single file over 4 GB, and a library with long 4K clips will hold one. SnapDisk skips those files and lists them — use exFAT.
  • Assuming the free 5 GB cap covers the whole library. It is per run. A library over 5 GB needs several free runs — run it again and it picks up where it stopped — or one $9.99 Pro purchase.
  • Unplugging mid-copy. Pulling a USB drive out while files are still writing can corrupt the file in flight. Wait for the copy to finish, or pause it first — SnapDisk's Stop button exists for exactly this. An unplug mid-copy leaves a half-copied library that looks finished until you count it.
  • Checking the drive by opening any photo. Open a WebP back from the drive and look at it — watch it move, if it is animated, and check there is no white box behind it, if it is transparent — not just any photo. A random check passes even when the one format you cared about was never copied, because the photos that did copy render fine.

Rule of thumb: Find the .webp file first, then back it up — the WebPs you viewed on the web are in Downloads, the stickers are .webp files in a folder the gallery never shows, and the transparency and the animation live inside the file, so the saved .webp is the only copy that still moves and still has no background.
