Back up two phones' photos to one USB drive

Two phones, one USB drive, and a trap nobody warns you about: both phones name their photos the same way, so the second phone's copy can silently overwrite — or be skipped as if it were already there. One folder per phone fixes it.

November 23, 2026 · 7 min read

TL;DR: Yes, two Android phones can share one USB drive — plug it into the first phone, back it up, then plug the same drive into the second phone and back that one up. No computer, no cloud, no account. But do not point both phones at the same folder on the drive. Both phones name their photos the same way — IMG_20261123_142442.jpg, Screenshot_2026-11-23-14-24-42.png, DSC_0001.jpg — and SnapDisk builds the destination path from the photo's folder and filename, so DCIM/Camera/IMG_0001.jpg from both phones lands on the same drive path. Then its skip check decides by path and size only: if the second phone's file has the same name and the same byte size as the file already on the drive, SnapDisk skips it as already copied, and the second phone's different photo is silently missing from the backup — a green "Backup complete" that did not copy it. If the sizes differ, the second copy overwrites the first. The fix is one folder per phone: on the first phone set SnapDisk's To folder to something like /disk/Phone-1, on the second phone to /disk/Phone-2, and the collision never happens. The honest trade is that SnapDisk has no deduplication — a photo that genuinely exists on both phones is copied twice, taking twice the space — and the rival apps that do merge and dedupe (ThePhotoStick, VaultDrive) are separate paid products, not SnapDisk's route. As of November 23, 2026, no top search result offers a phone-direct, no-computer guide for backing up two Android phones onto one USB drive with the collision spelled out — the pages that exist are product pages for a backup stick or a rival app, a wireless-consolidation guide, or a computer-based sync tool.

The trap: two phones, one folder, same names

Start with the filenames, because they are the whole trap and they are easy to miss. Android cameras name photos by timestamp or by sequence, and every phone uses the same patterns: a Pixel or Samsung camera writes IMG_20261123_142442.jpg, a screenshot is Screenshot_2026-11-23-14-24-42.png, and some cameras still write sequential names like DSC_0001.jpg. Two phones in one household do the same things at the same times — the same holiday, the same birthday, both phones screenshotting the same boarding pass within the same second — so identical filenames across two phones are not a freak accident. They are the normal case. A sequential name is worse: two phones that both started counting at DSC_0001 will collide on dozens of names, not one.

Now what SnapDisk does with those names. The default run reads the whole library from MediaStore, oldest-first, and for each photo it builds the destination from the photo's relative path and filename — the code is File(File(base, item.relativePath), item.displayName) in BackupService.kt:616-621 — so DCIM/Camera/IMG_0001.jpg from either phone lands at /disk/DCIM/Camera/IMG_0001.jpg when the To folder is the default /disk/DCIM. And the skip check is by destination path and size only: destination.exists() && destination.isFile && destination.length() == expectedSizeBytes (BackupEngine.kt:102-108) — "Skip only when the destination already holds a file of the same size." There is no content comparison, no hash, anywhere in the code. So when the second phone's run reaches a file whose name and size match a file the first phone already put there, it returns Skipped — correctly, from the engine's point of view, because for one phone re-running its own backup that is exactly the resume behaviour you want. For two phones sharing a folder, it is a silent loss: a different photo, never copied, with no error and no listing. If the sizes differ, the second copy overwrites the first phone's file instead — also silent, and the first phone's photo is gone from the drive. If the names differ, both copies land safely. The trap is narrow — same name, same folder — but it is exactly the case a family backup hits, and nothing in the run warns you about it.

Two scope facts before the methods. First, each phone runs its own SnapDisk: the app, its settings, and its From and To folders live on that phone alone, so the To folder you pick on phone 1 has nothing to do with the To folder on phone 2 — you set them separately, and that is what makes the per-phone-folder method work. Second, the free 5 GB per-run cap is per run, per phone: each phone's backup is its own run with its own 5 GB free allowance, and running it again past the cap picks up where it stopped, because files already copied are never copied twice. Pro is a one-time $9.99 purchase per phone, not per drive — each phone that wants auto-backup on connect and unlimited size needs its own Pro. This article is for two Android phones and one plain USB drive, no computer. If one of the two devices is an iPhone, the routes are different — an iPhone needs its own app and its own export — and if a computer is in the loop at all, the transfer-via-computer guides already cover it.

One more scope fact, because it decides which of the methods below SnapDisk can help with at all. SnapDisk copies image and video files only. On the default run it reads the phone's MediaStore images and videos tables, with no folder filter — the whole library, oldest-first, whatever folder the photos sit in. On the From-picker route it walks the folder you picked and keeps only recognised photo and video extensions. A backup run that finishes green has copied that phone's photos — it has not touched the other phone, and the count it reports is that phone's count. If the number looks too small for two phones' worth of photos, that is probably why: the second phone was never in the run. Keep that in mind through Methods 1 to 4: the question is never "can SnapDisk copy these photos" in the abstract. It is "which phone is plugged in right now, and which folder on the drive is it writing to."

What you need

Two Android phones (Android 7.0 or later for SnapDisk — minSdk 24 in the repo), each with SnapDisk installed from the v0.1.2 APK (it is not on Google Play yet), and one USB drive your phones can read — a USB-C flash drive, or a regular USB drive with a USB-C OTG adapter (most modern Android phones support OTG; if a phone doesn't see the drive, try a different adapter) — with enough space for both libraries added together. Check the size first: look at each phone's photo storage (Settings > Storage, or the Gallery's storage view) and add the two numbers, then add headroom — and remember the per-phone-folder method copies a photo that exists on both phones twice, so a shared library counts twice. One format note: drives formatted FAT32 can't hold a single file over 4 GB. That only matters for very long videos — SnapDisk skips those files and lists them instead of failing the whole backup. A drive formatted exFAT has no such limit, and exFAT is the format to use for a two-phone drive.

Before any method, decide the folder names. The method only works if the two folders are different, so name them for the phones, not for the dates: Phone-1 and Phone-2 work, but Den-Pixel and Anya-Galaxy — or whoever's phones they are — are better, because in a year you will not remember which number was which phone. Do the labelling on the drive itself, in the folder names, not on a sticker on the drive: the sticker says whose drive it is, the folders say whose photos are inside. And one warning up front, because it applies to every route below: back up one phone completely before starting the second. The drive is the only copy either phone has made, and a half-finished first phone plus a started second phone is the state where a collision is most likely to be missed.

Method 1: SnapDisk, one folder per phone

This is the route to use, because it is the only one that makes the collision impossible by construction. Each phone runs its own SnapDisk with its own To folder, so set a different To folder on each phone before either backup starts. On the first phone, open SnapDisk, tap the To folder picker, and choose — or create — a folder for that phone on the drive, for example /disk/Den-Pixel. On the second phone, do the same with a different folder, for example /disk/Anya-Galaxy. The picker is the Android system folder picker, and the app keeps access to the folder you picked. Then, on the first phone:

  1. Plug in the drive. SnapDisk offers a backup in a notification: "External storage is connected. Backup photos?"
  2. Tap Backup. Photos and videos copy oldest-first — your earliest photos first — in the background, while you use the phone normally. The default run reads the whole library via MediaStore, not DCIM only, so every photo the gallery sees is covered, whatever folder it sits in. This was verified in the code, not assumed: with no From folder picked, the app queries the MediaStore images and videos tables with no folder filter.
  3. Watch the progress notification — real percent, copied / total size, speed, and time left — with Pause and Stop. You can pause and resume any time.
  4. Wait for "Backup complete." Every file is size-verified after copying, so the counts are proof, not a promise. Files that already copied are never copied twice — so if the free 5 GB per-run limit stops a big library partway, just run it again and it picks up where it left off.

Then unplug the drive, plug it into the second phone, and repeat the same four steps there — with that phone's own To folder already set. The second phone's run cannot collide with the first phone's files, because it is writing into a different folder: the same filename on both phones lands on two different drive paths, and the skip check on each phone only ever sees its own folder. Two honest limits. First, the 5 GB free cap is per run, per phone — a phone with a 40 GB library needs eight free runs or one $9.99 Pro purchase on that phone, and the second phone needs the same again. Second, SnapDisk does not dedupe across phones: a photo that exists on both phones — the same file sent to both, or both phones photographing the same moment and producing different files — is copied twice, once per folder, taking twice the space. That is the price of the safe method, and it is stated here rather than discovered on a full drive. If the drive fills up mid-run on the second phone, the run stops with the full error shown; free space by deleting nothing from the drive — move the drive's contents to a bigger drive first, or back up the second phone to a second drive.

Copying only some photos? If you would rather copy just one folder than the whole library, use the From folder picker: tap it, navigate to the folder, and the run copies only that folder, recursively. The picker route keeps only recognised photo and video extensions. If the drive is unplugged mid-copy, the backup pauses with the full error shown and resumes where it stopped when the drive is back. If a file is corrupt or too big for FAT32, it's retried once, then skipped with its reason listed — it never stalls the whole backup. The free version backs up manually, up to 5 GB per backup run, with no ads, no account, and no cloud. SnapDisk Pro is a one-time $9.99 purchase (no subscription) that starts the backup automatically when you plug in a disk and removes the size limit. The app has no internet permission, so your photos physically cannot leave your device.

And the check that matters for this article: after each phone's run, compare the count against what you expected for that phone alone. A green backup that copied everything in the first phone's library has still copied zero of the second phone's photos — they were never in the run. If the second phone's number looks too small, the missing photos are probably still on the second phone, and the run needs to be re-done with that phone's To folder set — not re-run into the first phone's folder. SnapDisk copies, it never deletes — the only files it ever deletes are its own half-finished .part files — so deleting the originals after the check is always your step, never the app's.

Method 2: by hand in the Files app, one folder per phone

If you'd rather not install anything, Android's built-in Files app can do the same copy — with the same folder rule, and without any of the automation. On the first phone, plug the drive in, open Files, and create a folder for that phone on the drive — Den-Pixel, say. Then browse to Internal storage, select the photo folders (DCIM for camera photos, Pictures for screenshots and saved images, plus any messaging-app folders), tap Copy, navigate to the phone's folder on the drive, and paste. Wait for the copy to finish before unplugging, and then verify it: plug the drive into another device and open a few photos, and confirm they render. Then do the same on the second phone, into its own folder. The folder rule is the same as in Method 1 — two phones, two folders — and for the same reason: the Files app copy has no collision warning either, and pasting the second phone's DCIM into the first phone's folder overwrites same-named files with no prompt worth trusting.

The honest limits of this route are the ones SnapDisk exists to remove. There is no oldest-first order, no progress bar with speed and time left, no Pause and Stop, and no resume if you unplug mid-copy — a manual copy interrupted halfway has to be started again, and working out which files already landed is your job, by comparing counts. There is no per-file verification: the Files app does not check sizes after copying, so a file that copied short looks finished until you open it. And the folder walk is manual: DCIM, Pictures, Screenshots, WhatsApp, Telegram — every folder you forget is a set of photos that never left the phone, and there is no MediaStore whole-library run to catch them. Copy in batches small enough to finish, check the count against what you selected, and open a few files on another device before you trust the drive. And the files on the drive are plain files — anyone who picks up the drive can open them — so if the photos are sensitive, this route protects nothing except against losing the phones.

Method 3: one shared folder — the merge, and what it costs

Sometimes one folder is what you actually want: a single merged library on the drive, both phones' photos together, browsable as one collection rather than two. It can be done, but it costs the safety Method 1 buys, and the costs need stating before the steps. Point both phones at the same To folder — the default /disk/DCIM, or a folder you create for the merge — and run each phone in turn. What happens then is exactly the collision described at the top of this article, and it breaks three ways. If the two phones' files have different names, both land safely and the merge works. If they have the same name but different sizes, the second phone's copy overwrites the first phone's file — the first photo is gone from the drive, and nothing records that it was ever there. If they have the same name and the same size, SnapDisk skips the second file as already copied — the second phone's different photo is silently missing, and the run reports success. The merge is safe only when you know the two libraries share no filenames, and you cannot know that without comparing them first.

If you still want the merge, compare first, then merge. Before either backup, list the filenames on both phones — in the Files app, or on a computer — and look for overlaps. For the overlapping names, rename one phone's files first, or copy them into that phone's own folder and merge the folders on a computer later, where a rename on collision is a prompt instead of a silent loss. Then run each phone into the shared folder, and after both runs, check the merged folder's count against the two phones' counts added together: if the drive count is smaller, files were skipped or overwritten, and the missing ones are the same-named ones. The one case where the shared folder is genuinely safe is when the two phones never produce the same name — for example, if one phone's camera names are all timestamped and the two phones were never used in the same second, which is a claim about your own usage, not a guarantee from any app. And note what the merge does not do: it does not dedupe. Two genuinely identical files — the same photo sent to both phones — land as one file only if they share a name and a size, in which case one copy is skipped; if they have different names, both are kept, taking twice the space. A merge is not a dedupe. It is two libraries in one folder, collisions included.

Method 4: the rival apps that do it for you

Two products are built for exactly this job, and they deserve an honest hearing — because each one does something SnapDisk does not. ThePhotoStick Omni is a USB stick with its own app: plug it into each phone in turn, tap Backup, and the app finds the photos and copies them onto the stick, "leaving the originals in place" — and its store listing claims it "Removes duplicate photos, even if backed up from different devices" and "Automatically identifies and removes exact duplicates, optimizing storage space". The family review sites describe the workflow as one stick, each device in turn, ending with "a copy of everyone's pictures" on something you can hold. The honest limits: it is a product you buy, not a free app for a drive you already own — the stick itself is the purchase, in several capacities — it needs its own companion app on each phone, and the dedupe claim is the vendor's, untested here; the family reviews note it is not automatic (nothing copies until someone plugs it in and presses the button) and that not every phone works with it. If you want dedupe across phones and one object to hold, the stick is the purpose-built answer, and SnapDisk is not it.

VaultDrive is the closer rival: an Android and iPhone app that backs photos to a USB drive with no computer, Pro $19.99 once. Its own site gives each phone its own folder — "One drive for the family: Each phone gets its own folder, so several phones can share one drive" — which is the same folder-per-phone method this article recommends, built into the app rather than set by hand in a folder picker. It also checks each file after it lands and resumes where it stopped, like SnapDisk. The honest limits: it is $19.99 once for Pro against SnapDisk's $9.99 once, and the folder-per-phone behaviour is a feature claim on the vendor's own product page, not a tested fact — no independent guide verifies it — while SnapDisk's per-phone To folder is a setting you can see and check yourself on each phone. VaultDrive is the app to pick if you want the folder separation handled for you; SnapDisk is the app to pick if you want to set it yourself on a drive you already own, for half the Pro price, with the collision logic visible in the open code. Neither app deduplicates across phones: VaultDrive's folders keep the two libraries separate, which is the opposite of merging them.

Do the two phones' photos get deduplicated?

Short answer: no — not by SnapDisk, and not by the folder method either. Deduplication means recognising that two files are the same photo and keeping one copy. SnapDisk never does that: it has no hash, no content comparison, and no record of what any other phone copied. Its only skip is destination-path-plus-size, which is a resume check, not a dedupe check — it answers "is this file already at this path", not "is this photo already on this drive somewhere". So a photo that exists on both phones is copied twice under Method 1, once into each phone's folder, taking twice the space. Under Method 3, the same photo with the same name and size is skipped once — one copy kept — but that is a collision, not a dedupe: a different photo with the same name and size is skipped the same way, and there is no way to tell the two cases apart from the run's output.

The products that claim dedupe do it in their own apps, on their own terms. ThePhotoStick's listing claims it "removes exact duplicates" across devices — exact duplicates, meaning byte-identical files, found by its own app while it scans each device. Nero's DriveSpan promises consolidation "free of duplicates" over Wi-Fi to one central location. Neither claim is verified here, and neither applies to a plain USB drive with SnapDisk: there is no dedupe step in the SnapDisk route at all. If dedupe matters — if the two phones share most of their library, for example after a phone-to-phone transfer, and the drive is small — the honest options are the stick, a computer-side dedupe after the copy (a duplicate-finder on the merged folder, run on a computer, where the files can be compared safely), or accepting the double space. Do not mistake the skip for a dedupe: a skipped file is a file SnapDisk believes is already at that path, and when two phones share a folder, that belief is exactly what loses photos.

Checking the drive after both phones

The check is per phone, not per drive, and it has to happen twice — once after each phone's run, before the next phone starts. After the first phone finishes, open the drive on a computer or on the phone itself and count: the folder for phone 1 should hold the number of photos and videos that phone's Gallery shows, and a few opened at random should render fully, videos included. If the count is short, the run stopped early — the 5 GB free cap is the usual cause, and running it again picks up where it stopped. After the second phone finishes, check its folder the same way, against the second phone's count. The drive total should be the two folders added together. If you used the shared-folder merge instead, the check is harder: the merged folder's count should equal the two phones' counts added together, and any shortfall is a skipped or overwritten same-named file — compare the filenames on both phones to find which ones, and re-copy the missing ones into a per-phone folder.

Three checks that catch the failures this article is about. First, open a few photos from each phone's folder on a different device — a computer is best — and confirm they render; a file that copied short looks like a photo until you open it. Second, look for the same filename in both folders: if IMG_0001.jpg appears in both, the folders did their job, and each copy is that phone's own photo. Third, check the drive's free space before the second phone starts: the second run needs the second library's size in free space, and a run that stops halfway for lack of space leaves a half-copied folder that looks finished until you count it. And the check that matters most for a family drive: confirm the folders are labelled for the phones, not the dates. A folder called 2026-11-23 tells you when the backup happened; a folder called Den-Pixel tells you whose photos are inside it when you come back to the drive in a year.

What to avoid

  • Pointing both phones at the same To folder. The default /disk/DCIM on both phones is the collision. Same name and same size means the second phone's different photo is skipped as already copied; same name and different size means it overwrites the first phone's photo. Set a different To folder per phone before either backup starts.
  • Trusting a green second run to have copied the second phone. A run that copied everything in the second phone's library copied zero of the first phone's — and a run into the first phone's folder that skipped same-named files copied fewer than the second phone holds. Check the count per phone, against that phone's Gallery.
  • Mistaking the skip for a dedupe. SnapDisk's skip answers "is a file of this size already at this path" — it never compares contents. Two different photos with the same name and size are skipped the same way as two copies of the same photo. A merge is not a dedupe.
  • Backing up the second phone before the first is finished and checked. A half-finished first phone plus a started second phone is the state where a collision is most likely to be missed. One phone completely, checked, then the second.
  • Forgetting the folders outside DCIM on either phone. Screenshots live in Pictures/Screenshots, WhatsApp and Telegram media in their own folders. SnapDisk's default run covers the whole library via MediaStore, so it catches them — a manual Files-app copy does not, unless you select each folder.
  • Using a FAT32 drive for two libraries. FAT32 cannot hold a single file over 4 GB, and with two phones the odds that one of them holds a long 4K video are doubled. SnapDisk skips those files and lists them — use exFAT.
  • Buying a second drive when one would do. Two phones do not need two drives — they need two folders. A second drive is a second copy, which is a different job (the 3-2-1 kind), not a fix for the folder problem.
  • Assuming the free 5 GB cap is per drive. It is per run, per phone. Each phone gets its own 5 GB free per run, and each phone that wants unlimited size needs its own $9.99 Pro — one purchase does not cover both phones.
  • Assuming the copy keeps running with the screen off. Unverified — no wake lock, no battery-saver handling in the repo — so keep the phone awake for the run, or check it. Screen-off continuation under battery saver is unverified, and a run that stopped when the screen went dark is the expected failure, not a surprise.
  • Unplugging mid-copy. Pulling a USB drive out while files are still writing can corrupt the file in flight. Wait for the copy to finish, or pause it first — SnapDisk's Stop button exists for exactly this. With two phones sharing one drive, an unplug mid-run on phone 1 leaves a half-copied folder that phone 2's run cannot tell from a finished one.

Rule of thumb: one phone, one folder — the drive is shared, the folders are not. Set the To folder per phone before either backup starts, and check the count per phone, not per drive.
