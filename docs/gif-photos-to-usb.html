Save GIFs to a USB drive from Android

A GIF is an ordinary .gif file — the animation lives inside the file itself, no playback note, no sidecar. The job is finding the file, because the apps that show you GIFs rarely give you one.

November 25, 2026 · 13 min read

TL;DR: A GIF is an ordinary .gif file, and the animation lives inside the file itself — frames stored one after another, no playback metadata, no sidecar file, nothing like the slow-motion case where the speed lives in a note attached to the video. That is the good news, and it makes the backup simple once you have the file: copy the .gif and the animation comes with it, byte-for-byte, because there is nothing to lose in the copy. The trap is getting the file in the first place, and it is a trap with two jaws. The first jaw is the chat app: WhatsApp converts a GIF you send into a short looping MP4 video, Telegram treats GIFs as silent MPEG-4 video and its Save to GIFs writes nothing to the phone at all, and a GIF picked from the keyboard's GIPHY search was never a file on your phone — it is served from a library. So the GIF you watched in a chat is usually not a .gif anywhere on the phone, and no backup app can copy a file that does not exist. The second jaw is the share step: sharing a GIF out of the Gallery or a chat into another app can flatten it to a still image — a frozen first frame — because some share targets take one frame and hand that on. The certain route copies the saved .gif file, never a re-shared copy: find it in Downloads, in the gallery's GIFs album, or in Pictures, and copy that file to the drive. SnapDisk's default run covers saved .gif files with no folder to pick — .gif is a recognised image extension, and Android indexes image/gif files in the MediaStore Images table exactly the way it indexes JPEGs — so plug in the drive, tap Backup, and the GIFs copy along with everything else. The check is playing one GIF back from the drive and watching it animate: a GIF that lost its animation still looks like a photo in every other check. And screen-off continuation under battery saver is unverified — the repo holds no wake lock and no battery-saver handling — so keep the phone awake for the run or check it. As of November 25, 2026, no top search result offers a dedicated GIF-to-USB how-to: the results are generic OTG copy guides that never name GIFs at all.

The wall: the GIFs you see are rarely files — and the files that are GIFs hide in plain sight

Start with the fact that decides the whole job, because the GIF wall is the opposite of the Threema wall and easy to misread. Threema's wall is a locked door: the photos exist and the app will not let them out until you save them. The GIF wall is a hall of mirrors: the GIFs are everywhere on your screen — in chats, in the keyboard, on web pages — and almost none of them is a file on your phone. A GIF you watched in WhatsApp is a short looping MP4 video by the time it reaches the other end, because WhatsApp converts it behind the scenes. A GIF you watched in Telegram is a silent MPEG-4 video, technically, and Telegram's own saved-GIF collection lives in your account's GIF panel, not in any folder. A GIF you picked from the keyboard's GIPHY search was served from a content library and never touched your storage. So a phone can show you a hundred GIFs a day and hold zero .gif files, and a backup that copies every file on the phone copies zero GIFs — not because the backup missed them, but because from the file system's point of view there were no GIFs to copy.

That is the wall, and it is a total one in the same way the messaging-app walls are: a chat full of GIFs you laughed at and never saved as files is a chat full of animations that do not exist anywhere outside the chat, and running SnapDisk's default backup on that phone copies every photo in the gallery — and zero GIFs, because the media index has no .gif entries to return. The difference from Threema is what counts as the save. Threema gives you a switch and a save button, and the saved file lands in a named folder. GIFs give you no switch at all, and the save is scattered across the phone: a browser download lands in Downloads, a GIF you make in the Gallery lands in the gallery's GIFs album, a GIF you download from Pinterest or another app lands in the gallery or in Downloads, and a GIF sent to you as a file — as an attachment, not as a chat GIF — lands wherever the app puts attachments. There is no single save step to turn on, and no single folder to point at. The job is a hunt first and a copy second, and the hunt is the part this article does that the generic guides do not.

Two scope facts, because they decide what this article can and cannot promise. First, the file itself is simple in a way that should reassure you once you have it: a GIF is an ordinary file with the animation stored inside it as a sequence of frames, and there is no playback note to lose the way there is with slow-motion video, where the speed lives in metadata attached to the file. Copy the .gif and you copy the animation — all of it, every frame, at the original frame rate — because the copy is byte-for-byte and the bytes are the animation. There is no conversion step to get wrong and no quality setting to choose, and SnapDisk never converts anything in any case. Second, the MP4 versions are not lost either, and they deserve a straight answer rather than a shrug: a GIF that WhatsApp or Telegram already turned into an MP4 is a video file, and SnapDisk copies it as a video — .mp4 is a recognised video extension — so it backs up, it plays, and it loops in most players. What it is not is a GIF, and the difference matters if you ever want the file back as a GIF: a video file cannot become a .gif again without a conversion step, and the conversion is a different job from this backup. This article is about the .gif files; the MP4 versions get their own method, Method 3, so neither is mistaken for the other.

And a word on whose GIFs these are, because GIFs are usually someone else's clip — a scene from a show, a reaction shot, a meme someone made — and because the line between saving and re-posting is worth stating plainly. The GIFs this article covers are the ones you downloaded or made for yourself: a GIF you saved from a web page, one you made from a video in the Gallery, one a friend sent you as a file that you want to keep. Saving them to your own drive for your own records is the job. They are also someone else's work in a plain sense: a clip from a film, a moment from a stream, a meme with an author you will never meet. Saving a file does not grant permission to reuse it — so re-posting a GIF as if it were yours, or using someone's clip in your own content without asking, is a different act, and the same courtesy applies here as anywhere: the person who made it is the person to ask before the GIF leaves your phone for anywhere else. This article's methods copy the file to your drive; what you do with it afterwards is yours to decide, and asking is the honest step before anything leaves your phone. Only save GIFs you have permission to keep — and this article makes no claim about recovering GIFs from a chat you have already deleted, because the chat apps keep no .gif file to recover, and a GIF that was served from a library was never yours to recover in the first place.

Where .gif files live on an Android phone — Downloads, Pictures, and the folders that hold MP4s instead

This section exists because the folder is the one fact the guides do not answer at all — and because GIFs, unlike the messaging-app photos in this series, have no single home folder. A Threema photo lands in Pictures/Threema; a WhatsApp photo lands in WhatsApp Images. A GIF lands wherever the thing that made it put it, and the phone has four different makers. So this article does not state one path as the path for every GIF. It gives the check order instead, and the check order is the same on every phone — and the check itself is the file extension, not the app that showed it to you. A file that ends in .gif is a GIF; a file that ends in .mp4 is a video, even if it looks exactly like a GIF when it plays.

Check Downloads first. Open your file manager, go to Internal Storage, then Download — or open Files by Google and tap Downloads. This is where a GIF downloaded from a browser lands: Chrome on Android saves every download to the shared Downloads folder by default, at Internal Storage/Download, and the guides agree on the path across manufacturers. A GIF you long-pressed on a web page and saved, a GIF you downloaded from a GIF site, a GIF someone sent you as a file attachment that your app saved to Downloads — all of them land here, as .gif files with their animation intact. If you have ever saved a GIF from the web on purpose, it is almost certainly here, and this is the folder to check first because it is the only folder a deliberate GIF save reliably produces.

Check the gallery's GIFs album second. Open your gallery app and look for a "GIFs" album. This is where a GIF you made yourself lands: Samsung's Gallery has a Create GIF tool — open a video, tap the three-dot menu, open it in the video player, tap GIF, adjust the clip, save — and the finished GIF shows in the gallery under a GIFs album. Google's Photos app has the same shape: select photos or a video, tap Create GIF, and the result is saved as a GIF. A GIF downloaded from Pinterest or another app that offers a download usually lands in the gallery too, under Pictures or in its own album, depending on the app. If the album is there, the save works — and this is also the check that proves the default run will see the GIFs, because the gallery and SnapDisk read the same media index, and a GIF the gallery shows is a GIF the default run sees.

Check Pictures third, and the chat apps' video folders fourth — and understand that the fourth check is for the MP4 versions, not the GIFs. Pictures is where a GIF saved from an app that writes to the shared Pictures directory lands, and it is worth a look when Downloads and the GIFs album come up empty. Then check the WhatsApp Video folder — the WhatsApp Media folder's video half — for the MP4 version of a GIF someone sent you on WhatsApp: WhatsApp converts a sent GIF into a short looping MP4, so the file you save from the chat is an .mp4, and it lands with the other WhatsApp videos. Telegram's case is stricter: a GIF in Telegram is a silent MPEG-4 video, its Save to GIFs keeps the GIF in your account's GIF panel rather than writing a file, and Save As writes an MP4 — so there is no Telegram GIF folder to check, only the MP4 the Save As step produced, if you took it. If the file is in none of those places, check that the save actually happened: a GIF you only watched in a chat was never saved, a GIF you picked from the keyboard's GIPHY search was served from a library and never touched your storage, and no folder on the phone holds either of them. The hunt ends where the file begins — and for a GIF that was never a file, the hunt ends with making one: download it from the source, or make it from the video with the Gallery's Create GIF tool, and then it is a file like any other.

One more scope fact for this section, because it decides what the drive copy holds: the saved .gif is the GIF as it was when you saved it, and the phone gives you no way to improve it afterwards. A GIF is capped at 256 colours per frame by the format itself — a 1987 format that stores every frame in full — so a GIF saved from the web is already a small, banded, lossy version of whatever it was clipped from, and copying it byte-for-byte keeps it exactly that good and exactly that bad. SnapDisk copies the saved file with no conversion and no quality change — but it cannot recover colours the GIF format already removed, and it cannot upgrade a GIF someone sent compressed. If the animation you want is a video you still have, the original video is the one worth keeping: a short MP4 is smaller, smoother, and true-colour, and the guides that measured this put the same clip at seven times smaller as MP4 than as GIF. The GIF route for a video you still have is only needed when you want the file as a GIF — for a sticker, for an old forum, for the one place that only renders GIFs. And the GIFs you made inside the Gallery's Create GIF tool are a separate case again: they are made from a video, and the video is usually still in your camera roll in DCIM/Camera — back that up too, because the GIF is a small copy of a moment the video holds in full.

What you need

An Android phone — Android 7.0 or later, which is SnapDisk's minimum version — with the apps that hold your GIFs already on it, plus one USB drive your phone can read: a USB-C flash drive, or a regular USB drive with a USB-C OTG adapter. SnapDisk itself is installed from the v0.1.2 APK — it is not on Google Play yet — so install it by allowing "install unknown apps" for the browser or Files app you download it with, which is standard Android. You need nothing else for the main route: no file manager, no extra app, no account. The hunt step is inside the apps you already have — the browser's Downloads, the Gallery's GIFs album, the file manager — and the backup is SnapDisk's default run. Check the drive's space first: GIFs are small — a GIF is a few megabytes at most, usually well under one — so space is almost never the problem here, but look anyway, because a whole-library default run copies everything, not just GIFs. One format note: drives formatted FAT32 cannot hold a single file over 4 GB. That only matters for very long videos — SnapDisk skips those files and lists them instead of failing the whole backup. A drive formatted exFAT has no such limit, and exFAT is the format to use for a photo drive.

Before any method, settle the one question that decides whether the phone route works at all: does your phone see the USB drive? Plug the drive in and open Settings > Connected devices or Settings > Storage — the drive should appear there. That check is the test, and it takes ten seconds. If the drive does not appear, try a different adapter first — cheap OTG adapters are the usual failure — then a different drive, and a powered hub if the drive is a spinning hard drive rather than a flash drive. And one warning up front, because it applies to every route below: do not delete anything from the phone until the USB copy is done and verified. The GIFs in the chat are the chat app's copy, and the GIFs in Downloads are yours — but until the drive copy is checked, Downloads is the only copy outside the chat, and deleting from Downloads before the check is how a GIF ends up nowhere at all. And do not delete the chat app, or clear its data, until the save and the copy are both done: a GIF that was never saved as a file is gone when the chat is gone, and the chat apps keep no .gif file to recover from.

Method 1: Find the saved .gif, then back up with SnapDisk

This is the route to use, because it is the only one that joins the whole job — the .gif file, found on the phone, onto a USB drive plugged into the phone, no computer — using only the apps already on the phone plus SnapDisk. It has two halves, and they have to happen in order: the hunt, which finds the .gif files, and the SnapDisk copy, which puts them on the drive. The first half is the work, and with GIFs it is a hunt across folders rather than a single save step, because there is no switch to turn on and no single folder to open. Skipping the first half is the mistake this article exists to prevent: running SnapDisk's default backup without knowing where the GIFs are copies every photo in the gallery — and zero GIFs, if the GIFs were never saved as files, because from the media index's point of view there are no GIFs to copy.

  1. Hunt the .gif files first, in check order. Open your file manager and go to Internal Storage, Download — the browser-downloaded GIFs live here, as .gif files. Then open your gallery app and look for the GIFs album — the GIFs you made with Create GIF live here. Then check Pictures for GIFs saved from apps that write there. The check at each stop is the file extension: a file that ends in .gif is a GIF, and a file that ends in .mp4 is a video, even if it plays exactly like a GIF. If a folder holds no .gif files, move on — do not assume the GIFs are there because the folder's name sounds right. If you find GIFs in more than one folder, note all of them: the default run covers them all at once, and the picker route in Method 2 needs one pick per folder.
  2. If the hunt comes up empty, make the file before you back it up. A GIF you only watched in a chat was never a file, and a GIF you picked from the keyboard's GIPHY search was served from a library — neither is on the phone, and no step in this article conjures a file out of a watched animation. The fix is at the source: download the GIF from the web page it came from — long-press it in the browser and save it, and it lands in Downloads as a .gif — or make it from the video with the Gallery's Create GIF tool — open the video, tap the three-dot menu, open it in the video player, tap GIF, adjust the clip, save — and it lands in the gallery's GIFs album as a .gif. A GIF sent to you as a file attachment, rather than as a chat GIF, is already a file: save the attachment, and it lands in Downloads or the app's folder as a .gif. Do not try to rescue a chat GIF by sharing it to yourself: the share step is the flattening trap in the next step, and a shared copy is the least reliable GIF on the phone.
  3. Do not re-share a GIF to get it onto the drive. This is the trap the whole article is built around, and it deserves its own step because it looks like the obvious shortcut. Sharing a GIF out of the Gallery or a chat into another app — into a file manager, into a different chat, into yourself — can flatten it to a still image: some share targets take only the first frame and hand on a still, and a GIF sent through a chat can land as a frozen frame. The guides that measured this put the blame on the format itself, a 1987 format that stores every frame in full, which is why the platforms re-encode it to MP4 behind the scenes instead of passing the GIF along. A flattened copy is a still image wearing a GIF's name, and no backup step after it restores the animation, because the animation was lost in the share, not in the copy. The certain route copies the saved .gif file, never a re-shared copy — and if the only copy you have is a re-shared one, go back to step 2 and save the GIF from its source instead.
  4. Check the GIFs album appeared, or the files are in Downloads. Open your gallery app, go to Albums, and look for "GIFs". If it is there, the save works — and this is also the check that proves the default run will see the GIFs, because the gallery and SnapDisk read the same media index. If the album is not there, work through the check order in the section above: Downloads first, then Pictures, then the WhatsApp Video folder for the MP4 versions. If the files are in the folder but not in the gallery, the phone's media scanner has not picked them up yet — a restart forces a rescan. If no folder holds a .gif at all, the save is the suspect: a GIF you watched was never saved, and step 2 is the fix — download it from the source or make it from the video.
  5. Plug in the drive and run SnapDisk. Plug the USB drive into the phone. SnapDisk offers the backup in a notification — tap Backup — or open the app and tap Start. The run copies oldest-first, verifies every file by size after copying, and shows progress with Pause and Stop in the notification. The free run covers up to 5 GB, and GIFs are small, so one run is almost always enough for the GIF half — though a whole-library run copies everything else too, and that is the point: the saved GIFs come along with the rest, with no folder to pick and no step to remember. Screen-off continuation under battery saver is unverified — the repo holds no wake lock and no battery-saver handling — so keep the phone awake for the run or check it.
  6. Do not plan around the GIFs you never saved. A GIF you only watched in a chat is still inside the chat app, and no step in this article changes that: there is no save-all for a chat's GIFs, and there is no export that writes a chat's GIFs out as .gif files — the chat apps that show GIFs do not keep .gif files at all. If a GIF matters, save it from its source now, while the chat is still on this phone and the web page is still up — a GIF that was served from a library is gone when the library stops serving it, and a chat GIF is gone when the chat is gone. A screenshot is the only copy left for a GIF the built-in save will not give you — and a screenshot is a picture of the screen, not the GIF: it is a still image, it carries the app chrome around it, it lands in the Screenshots folder, not with the GIFs, and it does not animate. Do not plan a backup around saving what the apps will not let you save as a file.

Two honest limits. First, the hunt is not retroactive in the other direction either: finding GIFs today does not put the GIFs from a chat you already deleted onto the phone — a deleted chat is gone, and the chat apps keep no .gif file to recover from. That is step 2's job, and it is a manual job: one download per GIF, or one Create GIF per video. Second, the 5 GB free cap is per run — a GIF collection will never reach it, but a whole-library default run might, and running it again picks up where it stopped, because files already copied are never copied twice. Third, SnapDisk copies, it never deletes: deleting the GIFs from the phone after the check is always your step, never the app's — and deleting them from the chat is the chat app's, not SnapDisk's, and it does not free the drive copy. The drive copy is the backup; the phone copy is the original until you decide otherwise.

Copying only some GIFs? If you would rather copy just a few GIFs than the whole collection, the From folder picker still takes a folder, not single files — so copy the ones you want into their own folder first (in the file manager, or by saving them to the gallery and selecting them there), then point the picker at that folder. The picker route keeps only recognised photo and video extensions. If the drive is unplugged mid-copy, the backup pauses with the full error shown and resumes where it stopped when the drive is back. If a file is corrupt or too big for FAT32, it's retried once, then skipped with its reason listed — it never stalls the whole backup. The free version backs up manually, up to 5 GB per backup run, with no ads, no account, and no cloud. SnapDisk Pro is a one-time $9.99 purchase (no subscription) that starts the backup automatically when you plug in a disk and removes the size limit. The app has no internet permission, so your photos physically cannot leave your device.

And the check that matters for this article: after the run, play a GIF back from the drive and watch it animate. A green backup that copied the whole library has still copied zero GIFs if nothing was ever saved as a .gif — which is exactly what happens when the GIFs were only ever watched in chats. Open the drive and look for the GIFs by extension: the default run mirrors the source tree, so the files should be there as .gif files, in Downloads or the GIFs album's folder. If they are missing, the hunt is the suspect, not the run — find the .gif files first, then run again. SnapDisk copies, it never deletes — the only files it ever deletes are its own half-finished .part files — so deleting the originals after the check is always your step, never the app's.

Method 2: Point the From picker at the folder that holds the GIFs

If you would rather copy just the GIFs and nothing else — and the GIFs are already saved as files — point SnapDisk's From folder picker at the folder that holds them. Open SnapDisk, tap the From folder picker, and navigate to the folder you found them in, using the check order in the folder section above: Downloads first, then the gallery's GIFs album folder, then Pictures — and tap Backup. To get everything in Downloads at once, pick the Downloads folder itself: SnapDisk walks the folder recursively, so one run copies the GIFs and any other photo or video that lives under Downloads together. The same 5 GB free cap applies, and the same oldest-first order, size verification, Pause and Stop.

The honest limit on this route is that it is the code-supported route, not the test-proven one — and this article says so rather than claiming a test that never ran — and the folder itself is the second honest limit. The picker is the system's folder picker, and the code has no GIF path handling anywhere — zero matches for "gif" as a folder in the whole source tree, only the .gif extension in the recognised-extensions list — so the navigation is yours, step by step, through folders whose names are ordinary. But the exact folder depends on where the GIF was saved — Downloads for a browser download, the GIFs album for a Gallery-made GIF, Pictures for an app save — so this article does not state one folder path as the path, and no SnapDisk test has picked any of these exact folders yet. Neither candidate name starts with a dot, so none of them is hidden from the picker the way a dot-folder would be, and the folders sit in shared storage, not under Android/data, so the scoped-storage wall that blocks the Telegram folder does not apply here at all. And the folder walk recurses into every subfolder it can list, so picking the parent Downloads folder reaches every GIF under it. But the end-to-end pick is untested, and this article marks it as such. If the picker will not show the folder on your phone, fall back to Method 1: find the .gif files first, then run the default backup, which is the route that is proven to work. And one more scope fact for this route: the folder walk keeps only recognised photo and video extensions — a document in the folder is simply skipped, and a chat is never copied, because a chat is not a photo or a video. For a whole chat, use Method 3 — this article is only about the .gif and .mp4 files.

One GIF-specific reason Method 2 matters more here than in the other format articles: the split between the .gif files and the MP4 versions. The default run reads the media index, and it reads both the images table and the videos table, so it covers Downloads' .gif files and the WhatsApp Video folder's .mp4 versions together with no step beyond the hunt. The picker route does not: if you point it at Downloads you get the GIFs and not the WhatsApp MP4s, and the MP4s need a second pick at the WhatsApp Video folder — or one pick at a parent that holds both, which does not exist, because the two folders sit under different parents. That makes the picker the route for just the GIFs, and the default run the route for the whole animated set. This is a code-grounded difference, not a guess: the default path queries both MediaStore tables, while the picker path walks one folder tree — and the split is the chat apps' own conversion, which turns GIFs into MP4 video before the files ever reach a folder. The pick itself is still untested end to end on a real phone, and this article marks it as such — but the reason the default run covers both halves where the picker covers one is the code's own two paths, stated as such.

Method 3: The GIFs that are not files — WhatsApp, Telegram, and the keyboard

WhatsApp, Telegram, and the keyboard are the three places GIFs are watched most and saved least, and they are worth untangling carefully, because each one fails in a different way — and each failure looks like a backup problem when it is really a file problem. WhatsApp is the first: when you send a GIF on WhatsApp, the app converts it behind the scenes into a short looping MP4 video, and the file the recipient saves is that MP4. The guides agree on the shape — one writes that WhatsApp stores GIFs as short MP4 clips, so an MP4 is its native format; another that WhatsApp does not support uploading GIF files directly and a sent GIF is actually a short, muted MP4 video that auto-loops; a third that the conversion is automatic and you cannot opt out of it. So a GIF you received on WhatsApp, saved to the phone, lands in the WhatsApp Video folder as an .mp4 — and SnapDisk copies it as a video, because .mp4 is a recognised video extension, and it plays and loops like the GIF did. What it is not is a GIF, and no backup step makes it one again: the file was converted before it reached the phone, and the .gif version of it exists only on the sender's phone, if it exists anywhere at all. If you want the .gif itself, ask the sender for the file — sent as a document, not as a chat GIF, because WhatsApp sends a document as-is and does not convert it — and then it lands in Downloads as a .gif.

Telegram is the second, and it is stricter: a Telegram GIF is technically a silent MPEG-4 video, and Telegram's own saved-GIF collection lives in your account's GIF panel, not in any folder. To add a GIF to that collection you press and hold it in a chat and choose Save or Add to GIFs — and that saves it to the panel, synced with your account, appearing on all your devices, with no file written to the phone. To get a file out of Telegram you use Save As, and Save As writes an MP4 — the guides state it plainly, that the file will be saved in MP4 format. So there is no Telegram GIF folder to back up, and no Telegram GIF file to hunt for: the GIFs you saved inside Telegram are panel entries, and the files you saved out of Telegram are MP4 videos. Both still back up — the MP4s copy as videos in the default run, and the panel entries need nothing, because they live in your Telegram account and reappear on any device you sign into. But a drive holding the MP4s holds videos, not GIFs, and a drive holding nothing holds no Telegram GIFs at all — because the GIFs were never files. If you want a Telegram GIF as a .gif, the route is the same as WhatsApp's: get the original file from its source — the web page, the GIF site, the sender as a document — and save that file to Downloads.

The keyboard is the third, and it is the quietest of the three: a GIF you pick from the keyboard's GIPHY search — the GIF button in Gboard or in the chat app's own GIF search — is served from a content library and never touches your storage. The guides state it in the same breath as the WhatsApp conversion: a GIF from the keyboard's GIPHY or Tenor integration loads from a CDN, has no file size issue, and leaves no file behind. So a GIF you sent from the keyboard was never yours to back up in the first place: it is a library entry you borrowed for one message, and the copy of it that matters — if any — is the one in the chat history, which the chat app holds and which no backup in this article touches. The fix is the same as the other two: if a keyboard GIF matters enough to keep, find it at its source — search the GIF site for it, download it from the web page, save it to Downloads as a .gif — and then it is a file like any other, and Method 1 covers it. And the same permission rule applies to all three routes: only save GIFs you have permission to keep, and do not use a backup tool to pull someone else's clip out of a chat you were never meant to keep.

Can SnapDisk read the GIF folder directly?

This is the question the whole article turns on, and it deserves a straight answer in three parts — what the code proves it can do, what is untested, and what would prove the rest. The first part is proven, from the code at the current base and from how Android's media index works — and it is the same shape as the Threema, Kik, and Viber cases, with one GIF-specific condition. SnapDisk's default run reads the phone's media index — it queries the MediaStore images and videos tables, oldest-first by date taken, with no folder filter. A saved .gif file is an ordinary indexed file: Android's own developer documentation states that each MediaStore collection is organised by the primary MIME type of the content, and that image/* content is indexed under Images — and a GIF's MIME type is image/gif, so a GIF is indexed under Images exactly the way a JPEG is. The app's recognised image extensions include .gif, in the same list as .jpg, .png, and .heic. The query is in PhotoQuery.kt, the no-folder-filter shape is the code's own design — the query call passes no selection at all — and the gallery evidence is the platform fact that closes the loop. So the default run sees saved GIFs that show in the gallery, and it sees them with no step beyond the hunt. That is not an assumption: it is the code's query shape plus the platform's indexing rule, stated as such. And the default run copies the whole library, not DCIM only — the query reads every indexed image and video on the phone, whatever folder it sits in, so the GIFs in Downloads are covered the same way DCIM is, and the MP4 versions in the WhatsApp Video folder are covered the same way the photos are.

The condition is the hunt, and it is the part that makes GIFs different from every other format in this series: the default run's coverage is conditional on the GIFs having been saved as files, and with GIFs there is no save switch and no single save folder — the save is scattered across Downloads, the gallery's GIFs album, and Pictures, and the chat apps that show GIFs do not save .gif files at all. If nothing was ever saved as a .gif, the GIFs are still inside the chat apps as MP4s or panel entries or library loans, and the default run cannot see them — not because the code is wrong, but because the index it reads has no .gif entries to return. The fix is its own: download the GIF from its source or make it from the video, so it lands in Downloads or the GIFs album as a .gif. Until that is done, the default run copies zero GIFs while the chats sit full of animations. This article states the condition in the TL;DR, in the wall section, in Method 1 steps 1 and 2, and here — because a guide that promised the default run covers every GIF, without the condition, would be wrong on exactly the phones where the GIFs were only ever watched. The second condition is the share trap: a GIF that was re-shared into a still is a still in the index too, and the default run copies the still faithfully — the copy is correct, and the file was already wrong.

The second part is untested, and this article marks it as such rather than guessing in either direction: whether SnapDisk's From folder picker reaches the GIF folders end to end on a real phone. The picker is the system's folder picker — ActivityResultContracts.OpenDocumentTree, in MainActivity.kt — and it opens with no folder pre-selected: there is no initial-folder hint anywhere in the code, and no GIF path handling anywhere in the app — the only "gif" in the source is the .gif extension in the recognised-extensions list. The navigation chain is ordinary folders — Downloads, the gallery's GIFs album folder, Pictures — none of them dot-prefixed, so none of them is hidden from the picker the way a dot-folder would be, and the folders sit in shared storage, outside Android/data, so the scoped-storage wall that blocks the Telegram folder does not apply here. And the folder walk recurses into every subfolder it can list, so picking Downloads should reach every GIF under it. But the exact folder depends on where the GIF was saved, and no SnapDisk test has picked any of these exact folders yet, so the end-to-end pick is untested — do not plan a backup around it as the only route, and do not assume it fails either. The joined workflow in Method 1 is the route that is proven to work, and it is the route this article gives first. The picker has one GIF-specific limit the default run does not, stated in Method 2: it walks one folder tree, so Downloads gives the .gif files and the WhatsApp Video folder needs a second pick for the MP4 versions — but that limit is itself untested end to end, and this article marks it as such too.

The third part is what the code does prove about the rest of the job, so the limits above are not mistaken for a wider doubt. The manifest requests the media-read permissions (READ_MEDIA_IMAGES and READ_MEDIA_VIDEO, plus the older READ_EXTERNAL_STORAGE capped at Android 12), the notification permission, and foreground-service permissions — and no INTERNET permission at all, zero occurrences, so the photos physically cannot leave the device. It does not request all-files access — no MANAGE_EXTERNAL_STORAGE anywhere — which is the permission a file manager uses to browse another app's folders freely, and the absence is the reason SnapDisk cannot simply walk into a chat app's private storage the way a file manager can; the folder picker is the route instead, and it needs your tap. The backup itself is the verified core: oldest-first by date taken with a date-modified fallback (PhotoQuery.kt), every file size-verified after copying (BackupEngine.kt), Pause and Stop in the notification (NotificationHelper.kt, BackupService.kt), files of 4 GB or more on a FAT32 drive skipped with their reason instead of stalling the job (BackupService.kt), and the free run capped at 5 GB with Pro a one-time $9.99 purchase (ProPrefs.kt). None of that changes the picker verdict — it bounds it. The backup engine is proven; the end-to-end pick of these exact folders is not yet tested.

GIFs you made vs GIFs you received

The route is the same for both, but the starting point is not, and it is worth saying which one you are saving before you start. GIFs you received — the case this article is really about — are the ones the hunt governs: with the save they land in Downloads or the gallery, and without it they are not on the phone at all, and the methods above are written for them. GIFs you made are different, because you usually have a better original: a GIF you made from a video is almost certainly still in your camera roll as the video itself, in DCIM/Camera, at full quality, as an ordinary indexed file that SnapDisk's default run already covers — and the default run copies the whole library, not DCIM only, so it is covered either way. Back that up instead. The GIF is a small, 256-colour copy the Gallery made for sharing — smaller and banded, unless the clip was simple flat colours to begin with — and the original video is the one worth keeping. That matters more than it sounds, because the GIFs you make are often the ones you care about most: a moment from a family video clipped for a chat, a reaction shot cut from a longer recording, the loop you made to show someone what something looked like. The original is the one they will ask for again. The GIF route for a GIF you made is only needed when the original is gone — you deleted the video from the camera roll, or it was a clip you made inside another app and never saved — and then the GIF is the only copy left: find it in the gallery's GIFs album the same way as a received GIF, and the default run picks it up like any other indexed file, or point the From picker at the folder and copy it directly.

One related corner is worth a line, because GIF owners hit it and it looks like a shortcut that is not one: a GIF sent as a file, rather than as a chat GIF, is a different thing again — WhatsApp lets you send files as documents, and a GIF sent that way is sent as-is, without the MP4 conversion, and it lands in Downloads or the app's folder as a .gif. That is the one WhatsApp route that preserves the GIF, and it is the route to ask for when someone sends you a GIF you want to keep: ask them to send it as a document, not as a GIF in the chat. The same shape holds on Telegram: a GIF sent as a file lands as a file, while a GIF sent as a GIF becomes an MPEG-4 video. If a GIF you are missing was sent as a chat GIF, check the WhatsApp Video folder for the MP4 version first — and if the .gif itself is what you want, ask the sender to re-send it as a document. And one more GIF-specific corner: a GIF with transparency — a floating sticker with no background — is the one GIF that must stay a GIF, because converting it to MP4 fills the transparent areas white. If your GIF relies on transparency, keep it as a .gif and do not convert it; the MP4 versions the chat apps make already lost the transparency when they converted it, and no backup step brings it back.

Checking the drive after the copy

The check has two halves, and they have to happen in order: first that the hunt actually produced .gif files on the phone, then that the drive holds them moving. After the SnapDisk run finishes, open the drive on a computer or on the phone itself and count: the drive should hold the GIFs you saved, in a Downloads folder of their own — the default run mirrors the source tree, so the files should be there by name and extension — and one opened at random should animate. Open a GIF itself — not just any photo on the drive — because a run that covered the rest of the library would still look complete on a random check while the one format you cared about was missing. Play it back and watch it move for a full loop: a GIF that lost its animation still looks like a photo in every other check, and only playback answers the question. If the count is short, the run is not the first suspect — the hunt is. Check Downloads: are the .gif files actually there, and do they end in .gif? If the folder holds no .gif files, the GIFs were never saved — download them from the source or make them from the video, and run again. If the files are in Downloads but not on the drive, the run is the suspect, and the run needs repeating, not a different folder. If the files are in the folder but not in the gallery, the media scanner is the suspect: restart the phone to force a rescan, and run again — or pick the folder directly with the From picker, which does not depend on the gallery.

If the drive's free space ran out mid-run, the run stops with the full error shown; free space by moving the drive's contents to a bigger drive first, or back up to a second drive. If the run stopped at the 5 GB free cap — unlikely for a GIF collection alone, possible on a whole-library default run — run it again and it picks up where it stopped, because files already copied are never copied twice. If a GIF on the drive does not move, the copy is not the suspect — the source is. Check the source file's extension: if it ends in .mp4, the GIF was converted by the chat app before you copied it, and the MP4 version is what the phone held; if it is a still image, it was flattened by a share step. Find the original .gif in Downloads or the gallery's GIFs album and copy that file instead. And the check that matters most for a GIF that only existed inside a chat: confirm the drive copy before you delete anything from the phone. The copy in Downloads is an ordinary file and will survive; the copy in the chat depends on the chat app keeping it, and a GIF that was served from a library is gone when the library stops serving it. The drive is a plain folder of plain files. Anyone who picks up the drive can open them. That is the price of a copy you can open anywhere, and it is worth stating before the GIFs leave the phone — especially for GIFs, where the clip is often someone else's work.

What to avoid

  • Assuming a GIF you watched is a .gif file on your phone. It usually is not — WhatsApp converts sent GIFs to MP4 video, Telegram keeps GIFs as MPEG-4 video in its account panel, and a keyboard GIF is served from a library and never touches your storage. A one-tap backup copies zero GIFs until the GIFs exist as .gif files in Downloads, the GIFs album, or Pictures.
  • Assuming the chat apps keep .gif files. They do not — WhatsApp stores a sent GIF as a short MP4 clip, Telegram represents GIFs as silent MPEG-4 video, and Save to GIFs writes nothing to the phone. The MP4 versions still back up as videos, but they are videos, not GIFs.
  • Re-sharing a GIF to get it onto the drive. Sharing a GIF out of the Gallery or a chat can flatten it to a still image — some share targets take only the first frame. Copy the saved .gif file, never a re-shared copy; a flattened copy never animates again.
  • Assuming the default run covers GIFs you only watched. It cannot — proven from the code and the platform: the default run reads the media index, and a GIF that was never saved as a file never enters the index. A green backup copies zero GIFs from chats you never saved from.
  • Assuming one folder holds every GIF. UNVERIFIED as a single path — the folder depends on where the GIF was saved: Downloads for a browser download, the gallery's GIFs album for a Gallery-made GIF, Pictures for an app save, the WhatsApp Video folder for the MP4 version. Check Downloads first, then the GIFs album, then Pictures — do not plan a backup around a single path.
  • Assuming the From picker route is test-proven. Untested — no SnapDisk test has picked the Downloads or GIFs-album folders yet, and the exact folder depends on where the GIF was saved. The code supports it and the folder names are ordinary, but do not plan a backup around it as the only route; Method 1's hunt-first workflow is the proven one.
  • Assuming the default run covers the MP4 versions if you only picked the GIFs folder. It does not — that is the picker route, not the default run. Pointing the From picker at Downloads copies the .gif files and not the WhatsApp MP4s, which live in the WhatsApp Video folder and need a second pick. The default run covers both, because it reads both MediaStore tables.
  • Assuming a still on the drive means the copy failed. It does not — the copy is byte-for-byte, so a still on the drive means the source was already a still: a GIF flattened by a share step, or a screenshot. Check the source file, not the run; find the original .gif and copy that file instead.
  • Assuming a GIF you made is the original. A GIF you made from a video is a small, 256-colour copy of it. The video is usually still in DCIM/Camera at full quality. Back the original up, and use the GIF only when the original is gone — except a transparent sticker GIF, which must stay a GIF, because converting it fills the transparency white.
  • Assuming a screenshot is the GIF. It is not — a screenshot is a picture of the screen, a still image, carrying the app chrome around it, and it lands in the Screenshots folder, not with the GIFs. It does not animate. Save the GIF itself when the save works, and screenshot only when it does not.
  • Assuming screen-off continuation under battery saver. UNVERIFIED — the repo holds no wake lock and no battery-saver handling. Keep the phone awake for the run, or check it.
  • Using a FAT32 drive for a library with long videos. FAT32 cannot hold a single file over 4 GB, and a library with long 4K clips will hold one. SnapDisk skips those files and lists them — use exFAT.
  • Assuming the free 5 GB cap covers the whole library. It is per run. A library over 5 GB needs several free runs — run it again and it picks up where it stopped — or one $9.99 Pro purchase.
  • Unplugging mid-copy. Pulling a USB drive out while files are still writing can corrupt the file in flight. Wait for the copy to finish, or pause it first — SnapDisk's Stop button exists for exactly this. An unplug mid-copy leaves a half-copied library that looks finished until you count it.
  • Checking the drive by opening any photo. Play a GIF back from the drive and watch it animate — not just any photo. A random check passes even when the one format you cared about was never copied, because the photos that did copy render fine.

Rule of thumb: Find the .gif file first, then back it up — the GIFs you watched in chats are MP4s now, a re-share can flatten a GIF to a still, and the animation lives inside the file, so the saved .gif is the only copy that still moves.
