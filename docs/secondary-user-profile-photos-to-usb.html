Back up secondary-user photos to a USB drive

A personal-profile app cannot see your secondary-user photos — Android gives the secondary user its own separate storage, and it wipes that storage when the user is deleted. The backup has to start inside the secondary user, or the photos have to cross to the owner profile first. Here are the routes that actually work, and the ones that don't.

November 23, 2026 · 6 min read

TL;DR: SnapDisk installed in your owner profile cannot back up secondary-user photos — the secondary user is a separate Android user with its own storage area, and a file path valid in one user is not valid in the other, so your owner-profile apps simply never see the secondary-user photos. There are four honest routes, each with its own limit. (1) Copy inside the secondary user with the secondary user's own file manager — the only route that needs no crossing and no cloud — but whether a USB drive even appears in the secondary user's Files app is unverified from Android's documentation, so try it and fall back if it doesn't show up. (2) Move the photos to the owner profile before the secondary user is deleted — upload them to a cloud account signed in inside the secondary user, or send them to yourself from inside the secondary user — because the secondary-user guides give no backup advice of their own, and name no owner-visible shared folder on stock Android. (3) A secondary-user cloud account as a bridge — a fallback, not a USB backup, and the copy dies with that account if you lose access to it. (4) Installing SnapDisk inside the secondary user — SnapDisk isn't on Google Play at all, and side-loading inside a secondary user is untested, so do not plan on this route. The sharpest motive is the deletion itself: removing the user erases all of its local data with no restore, so back the photos up and verify the copy before the user is removed. SnapDisk's one-tap copy works once the photos are in the owner profile — free up to 5 GB per run, Pro $9.99 once — and SnapDisk copies, it never deletes. As of November 23, 2026, no top search result offers a phone-direct USB-drive backup of secondary-user photos — the generic OTG guides never mention a secondary user, and the secondary-user explainers never take the USB step.

SnapDisk cannot see your secondary-user photos — say it first

This is the fact the whole article turns on, so here it is with the evidence, not the claim. Android's secondary user is a full user type in the multi-user system — AOSP names it android.os.usertype.full.SECONDARY — and Android's own multi-user documentation says the system supports multiple users "by separating user accounts and app data": each user "has distinct app data and some unique settings", and "an app's data exists within each associated user". A secondary user is any user added to the device other than the system user: it can be created from the settings user interface, it can run in the background while another user is active, and it "cannot impact other users on a device". Underneath, the separation is the same one that keeps every Android user apart: physical internal storage is partitioned into per-user directories, each user runs under a distinct Linux UID range, and one user's apps cannot inspect another user's files. The secondary-user guides say the same thing in plainer words — each profile has "its own home screen, apps, Google Account, and storage allocation, invisible to other profiles".

So the first step is not a backup method at all. It is finding out which user holds the photos. Photos taken while the phone was in the secondary user — with the secondary user's camera app, or saved inside a secondary-user app, or received as attachments in a secondary-user email or chat app — live in the secondary user. Photos taken with your owner camera, and everything in your owner Gallery, live in the owner profile — and those are the ones SnapDisk can already back up. If you are not sure, switch into the secondary user and look: swipe down twice for Quick Settings, tap the user icon, tap the secondary user, and open its Gallery. If the photos are there, the rest of this article is about them.

Two scope distinctions before the methods, because they decide which device and which situation this article even applies to. First, a secondary user is permanent until the owner deletes it — unlike a guest session, which is wiped when it ends. The secondary user's data stays until the owner deletes that user, while a guest's data is erased when you exit Guest mode. That makes the backup less urgent day to day — the photos are not on a countdown — but no safer in the end: deleting the user still erases everything in it. Second, a secondary user is a full user, not a restricted profile: it signs in with its own Google account and installs its own apps, where a restricted profile is tablet-only and the owner decides which apps it can see. If your situation is a guest profile, the routes are in our guest-profile guide; if it is a restricted profile on a tablet, they are in our restricted-profile guide. This article is for the permanent second user on a phone or a tablet — a partner, a child, a second identity on one shared device.

One more scope fact, because it decides which of them SnapDisk can help with at all. SnapDisk copies image and video files only. On the default run it reads the phone's MediaStore images and videos tables, with no folder filter — the whole owner library, oldest-first, whatever folder the photos sit in. On the From-picker route it walks the folder you picked and keeps only recognised photo and video extensions. A backup run that finishes green has copied your owner photos — it has not touched the secondary user, and the count it reports is the owner count. If the number looks too small for what you expected, that is probably why: the secondary-user photos were never in the run. Keep that in mind through Methods 1 to 4: the question is never "can SnapDisk copy these photos" in the abstract. It is "are these photos in the user SnapDisk runs in."

What you need

An Android phone or tablet with secondary users — on stock Android it is Settings > System > Multiple users, then Add user; on some devices the path is Settings > Users & accounts > Users. One availability warning: not every maker ships the option. If the Multiple users menu is missing, or the only option under Add user is Guest, the manufacturer has disabled secondary users, and this article's routes do not apply to your device — Samsung Galaxy phones, for example, don't offer guest mode at all, only Galaxy tablets do, and the same multi-user menu is where a secondary user would be added. You also need a USB drive your phone can read — a USB-C flash drive, or a regular USB drive with a USB-C OTG adapter (most modern Android phones support OTG; if the phone doesn't see the drive, try a different adapter) — and enough space on the drive for the photos you want to keep. One format note: drives formatted FAT32 can't hold a single file over 4 GB. That only matters for very long videos — SnapDisk skips those files and lists them instead of failing the whole backup. A drive formatted exFAT has no such limit.

Before any method, check which user holds the photos, as above — the secondary-user Gallery or the owner one. And one warning up front, because it applies to every route below: do the work while you are still in the secondary user. The photos have to leave the user before it is deleted — there is no after. The move has to happen inside the secondary-user session, not after it is gone.

Method 1: copy inside the secondary user, by hand

This is the route to try first, because it is the only one that needs no crossing between users and no cloud account. Everything happens inside the secondary user: the photos start there, the copy happens there, and the drive is the destination. Switch into the secondary user first — swipe down twice, tap the user icon, tap the secondary user — then plug the USB drive into the phone. Open the secondary user's Files app and look for the USB drive under storage. If it appears, browse to the secondary-user photos (in the user's Gallery, or Internal storage → DCIM → Camera inside the secondary user), select them, tap Copy to, and choose the USB drive as the destination. Wait for the copy to finish before unplugging, and then verify it: plug the drive into another device and open a few photos, and confirm they render.

The honest limit of this route is the one stated in the TL;DR, and it is worth spelling out because it is the difference between a guide and a guess. Whether a USB drive plugged into the phone appears in the secondary user's Files app is unverified from Android's documentation: the developer docs confirm the users have separate storage areas, but they say nothing about whether a USB volume is visible per user, and no source found for this article answers it either way. It may appear, and on many phones it will — USB storage is device-wide hardware, not a per-user folder — but that is an expectation, not a verified fact. So treat this method as a test, not a promise: plug the drive in, open the user's Files app, and look. If the drive is there, copy by hand and you are done. If it is not there, the route is closed on your phone — do not keep tapping around hoping it appears — and the fallback is Method 2 or Method 3.

One more limit is worth naming, and it comes from how a secondary user differs from a restricted profile. The secondary user is a full user: it has its own file manager, its own Gallery, its own account — nothing for the owner to enable first. If the Files app is missing inside the secondary user, that is a device quirk, not a permission the owner forgot: try the Gallery's share-to-USB route, or install a file manager from the Play Store inside the secondary user with its own account. If the copy works, remember what it is: a manual copy. There is no oldest-first order, no progress bar with speed and time left, no Pause and Stop, and no resume if you unplug mid-copy. Copy in batches small enough to finish, check the count against what you selected, and open a few files on another device before you trust the drive. And the files on the drive are plain files — anyone who picks up the drive can open them — so if the photos are sensitive, this route protects nothing except against losing the phone. Do the copy and the check before the user is deleted: once it is gone, the photos are gone with it.

Method 2: move the photos to the owner profile before the user is deleted

If the drive doesn't appear in the secondary user, the next route is to move the photos across the boundary into the owner profile, where your personal apps — and SnapDisk — can see them. Do this while you are still in the secondary user, before deleting it. There are two workable crossings. The first is a cloud account signed in inside the secondary user: open Google Photos or Google Drive in the secondary user, sign in with an account that belongs to the secondary user's person — not the owner's, or the point of the separate user is gone — upload the photos, wait for the upload to finish, and then check from another device or a browser that the photos are actually in the account. The second is sending the photos to yourself: from inside the secondary user, share the photos by email or messaging to your own address, then open them in the owner profile and save them there. Once the photos are owner-profile files, Method 4 below backs them up to the USB drive with one tap.

The honest limit: the secondary-user guides name no crossing at all — no "shared folder", no cloud advice, nothing. The guest-mode guides at least give one line — copy to a shared folder or cloud before deleting — but they name no owner-visible shared folder on stock Android, and the secondary-user guides do not even go that far. So the cloud upload and the send-to-yourself are the crossings with named steps, because they are the only ones any guide describes with steps. A second limit is the account itself. A secondary user signs in with its own Google account — that is what makes it a full user — so a cloud app or an email app inside the user normally has an account to work with. But if the secondary user was set up without ever signing in, the send-to-yourself route needs an account first — an email app with no account cannot send mail. Check that before you count on either crossing.

Two things to know if the crossing works. First, the copy is a copy — the original stays in the secondary user until the user itself is removed, so you now have two copies, and the secondary-user one is still at risk until the owner copy is verified. Second, check the moved copies before you rely on them: open a few in the owner Gallery and confirm they are the full photos, not thumbnails, and that videos play. A share that silently downscaled or truncated a file is worse than a share that failed loudly. And do the crossing before you delete the user: there is no Keep-or-Remove prompt to save you, as there is when leaving a guest session — deleting the user is the wipe, and it happens the moment the owner taps Delete.

Method 3: secondary-user cloud as a bridge — not a USB backup

The third route goes through a cloud account that lives inside the secondary user — Google Photos or Google Drive signed in with the secondary user's account, in the secondary user's instance of the app. Upload the photos from the user's app to that account, wait for the upload to finish, and then check from another device or a browser that the photos are actually in the account — a pending upload is not a verified copy, and a backup setting alone proves nothing. This gets the photos off the phone, which is the urgent part when a user deletion is coming.

Label this honestly: it is a fallback, not a USB backup. The photos leave the phone to a secondary-user account, not to a drive you hold, and getting them back after the user is removed depends on keeping access to that account. The secondary-user account is often a partner's or a child's account, or one created on the spot for the user — so keep the credentials available, because a cloud copy you cannot sign into is not a backup. And do not rely on standard Android device backup as the route: the secondary user's local data is not part of the owner profile's device backup, and restoring a device backup does not bring a deleted secondary user back.

If the cloud copy is verified and you can still reach the account, the photos can come back down to the owner profile — download them there, or open them on a computer and copy them to the USB drive directly — and then Method 4 handles the drive copy. But if the only copy of the photos is in a secondary-user account you are about to lose, that is not a backup. It is a countdown. The USB drive is the copy that survives the user ending; the cloud is the bridge that gets the photos there.

Method 5: installing SnapDisk inside the secondary user

It sounds like the clean fix — put SnapDisk in the secondary user, and it would see the secondary-user photos the same way it sees owner ones. Do not plan a backup around it. SnapDisk is not on Google Play at all yet, so it cannot be installed from the Play Store in either user — there is no listing for anyone to install. The other way in is side-loading the APK inside the secondary user, and that route is untested: no one has installed SnapDisk in a secondary user, and no test has run there. A secondary user is a full user, so unlike a restricted profile there is no owner allow-list standing in the way — the user signs in with its own account and installs its own apps — but that only removes one obstacle, not the test. And even if it installed, the user is wiped when it is deleted — the app, its settings, and anything it had not yet copied would go with it — so the backup would have to finish before the deletion, with no second chance.

Deleting the user? Back up before it's removed

This is the sharpest motive for the whole article, and the one with the least room for error. Deleting a secondary user deletes all of its local data: every photo the user took, every file it downloaded, every app it installed — gone, with no built-in way to restore them. The multi-user documentation is plain about the boundary: a user does not exist beyond the lifetime of the owner who created it, and removing a user "wipes all of that profile's apps, accounts, and files immediately, with no way to bring them back afterward". Unlike leaving a guest session, there is no Keep-or-Remove prompt on the way out — the owner opens Settings > System > Multiple users, taps the secondary user, taps Delete, and the wipe is the deletion itself.

So the order matters, and it is not negotiable: back up first, verify the copy on another device second, delete the user third. Open several photos from the drive on a computer and confirm they render; confirm the count matches what the secondary-user Gallery showed. Only then delete the user — or leave it in place if the person still uses the phone. After deletion, check that the user is gone as expected — and know what survives: nothing local does. The cloud copy survives only if you can still sign into the secondary-user account, and the USB copy survives because you hold the drive. If the photos matter — a partner's pictures on a shared phone, a child's photos in their own user — the backup is the job, and the deletion is the deadline.

What to avoid

  • Assuming SnapDisk backs up secondary-user photos. It cannot see them. A personal-profile app reads the owner profile's MediaStore, and the secondary-user photos are in a different storage area. If the photos matter and they live in the secondary user, Methods 1 to 3 are the routes — SnapDisk is the last step, not the first.
  • Trusting a green owner backup to have covered the secondary-user photos. A backup that copied everything in the owner library copied zero secondary-user photos. Check the count against what the secondary-user Gallery shows before you call it done.
  • Deleting the user before the crossing is done. There is no Keep-or-Remove prompt on the way out of a secondary user — Delete is the wipe. Copy or upload first, delete second.
  • Assuming the drive appears in the secondary user's Files app. Unverified from Android's documentation. Plug it in, look, and if it isn't there, move to Method 2 or 3 instead of tapping around hoping it appears.
  • Confusing a secondary user with a guest session. A guest is temporary and wiped when it ends; a secondary user is permanent until deleted. The guest-profile routes are the temporary-borrower equivalent — this article is for the permanent second user.
  • Confusing a secondary user with a restricted profile. A restricted profile is tablet-only and the owner picks its apps; a secondary user is a full user on a phone or a tablet, with its own account and its own apps. The restricted-profile routes are the tablet equivalent.
  • Counting on a "shared folder" that no guide names. The secondary-user guides give no backup advice at all. The cloud upload and the send-to-yourself are the crossings with named steps — use those.
  • Treating a cloud upload as a USB backup. A secondary-user cloud copy is a bridge, not a backup: it dies with that account if you lose access to it. The USB drive is the copy that survives the user ending.
  • Signing the secondary user in with your own account. The user can set up a Google account — but signing in with yours gives the user your photos, messages, and app data, which is the thing a separate user exists to prevent. Use the secondary user's own account.
  • Assuming the copy keeps running with the screen off. Unverified — no wake lock, no battery-saver handling in the repo — so keep the phone awake for the run, or check it. Screen-off continuation under battery saver is unverified, and a run that stopped when the screen went dark is the expected failure, not a surprise.
  • Unplugging mid-copy. Pulling a USB drive out while files are still writing can corrupt the file in flight. Wait for the copy to finish, or pause it first — SnapDisk's Stop button exists for exactly this.

Rule of thumb: the user is the boundary — the backup has to start inside the secondary user, or the photos have to cross to the owner profile first. Check which user holds the photos before you trust any backup, and back them up before the user is removed, not after.
