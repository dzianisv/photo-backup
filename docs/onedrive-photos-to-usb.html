Save OneDrive photos to USB from Android

Your photos in OneDrive are files in the cloud, not files on your phone. Save them first — the OneDrive app writes a real file into Downloads — then copy that file to a USB drive, no computer.

November 25, 2026 · 14 min read

TL;DR: A photo in OneDrive is not on your phone yet. OneDrive is a cloud file store: you can see the photo, open it, share it, and mark it available offline — and none of that writes a file you can copy to a USB drive. The file appears only when you save it. In the OneDrive app, open the folder in List view — not thumbnails — tap the three-dot More menu next to the photo, tap Save, then tap the arrow at Save to this location, pick a folder, and tap Save again — Microsoft's own support page gives exactly those steps — and the file lands in the phone's Downloads folder as an ordinary .jpg or .png. That is the whole first half of the job, and it is the half every other guide skips: the generic Android-to-USB guides start from photos already on the phone, and the OneDrive guides that do exist stop at the phone — save to phone storage, done — which is the opposite of what you asked for. From Downloads the backup is the easy half: SnapDisk's default run reads Android's media index with no folder filter and copies the whole library — not DCIM only — so plug in the drive, tap Backup, and the saved OneDrive photos copy along with everything else, no computer. The honest limits, up front: Keep offline is not a save — it keeps the file inside the OneDrive app, and a file the OneDrive app holds is not a file SnapDisk or a file manager can see; a saved photo shows the download date, not the date the photo was taken — Microsoft's own support forum reproduced exactly that, that photos downloaded from OneDrive only show the date of download — so it copies in download-date order, and the taken date may already have been replaced by the upload date when the photo was put into OneDrive in the first place; there is no download-all button in the OneDrive Android app, so a folder is emptied one select-all pass per folder, and a folder with subfolders takes one pass per subfolder; and screen-off continuation under battery saver is unverified — the repo holds no wake lock and no battery-saver handling — so keep the phone awake for the run or check it. As of November 25, 2026, no top search result offers a dedicated OneDrive-photos-to-USB how-to with no computer: the results are save-to-phone guides that stop at the phone, a computer route for large libraries and cloud-only photos, and generic USB-copy guides that never mention OneDrive at all.

The confusion first: OneDrive is not Google Photos — and not Google Drive either

OneDrive sits in the middle of three confusions, and the whole job depends on clearing all three before you tap anything. The first confusion is OneDrive versus Google Photos. They are not two names for the same cloud. OneDrive is a file store. You put files in folders — documents, PDFs, spreadsheets, and photos as files — and you open them from the OneDrive app, a browser, or any signed-in device. Google Photos is a photo library. You back up your camera roll there, and the photos live in a library organised by date, album, and face, with editing and search built in. They are not two views of the same thing. They are two different stores, run by two different companies, that happen to both hold your photos.

The distinction matters because the save step is different for each, and the guides that confuse them will send you down the wrong menu. Uploading a photo to OneDrive does not put it in Google Photos. Backing up in Photos does not put a file in OneDrive. A photo you dragged into a OneDrive folder in your browser is a OneDrive file, and it stays a OneDrive file until you save it. A photo your phone backed up automatically is a Photos library photo, and the OneDrive app will never show it as a file in a folder, because it was never put in a folder. If you open the OneDrive app and cannot find a photo you are sure you have, that is the first thing to check: it may be in Photos, not OneDrive, and this article's steps do not apply to it. The Google Photos route — download from the Photos app, then copy to USB — is a different job, covered by the live2tech guide and the tecnobits guide, and it is not this article. This article covers photos stored as files in OneDrive only.

The second confusion is OneDrive versus Google Drive, and it is subtler, because these two actually are the same kind of thing. Both are file stores. Both hold photos as files in folders. Both have an Android app with a three-dot menu next to every file. The route is the same shape for both — save on the phone, then copy to USB — and our own Google Drive article covers the Drive half of it. But they are different accounts in different apps, and the menu wording differs in a way that will stop you if you follow the wrong article: Drive says Download, OneDrive says Save. Drive's download is two taps from the file's menu; OneDrive's save is three taps through a folder picker, because OneDrive asks where the file should go. If you open the OneDrive app looking for a Download button, you will not find one, and the absence of that button is not a missing feature — it is a different word for the same action, with a folder choice attached. This article uses OneDrive's words, in OneDrive's order, so the menu you see matches the menu this article describes.

The third confusion hides inside OneDrive itself, between the two ways a photo gets there. One way is upload: you, or someone, put a file in a OneDrive folder — dragged it in a browser, tapped Upload in the app, or saved it there from another app. The photo is a file in a folder, and the OneDrive app shows it in that folder, and the save steps in this article apply. The other way is camera upload: your phone's OneDrive app uploaded the camera roll automatically, and the photos live in a folder called Camera roll. Those photos are files too — OneDrive stores them at original size and full quality when you are on Wi-Fi, in a folder called Camera roll — and the save steps apply to them exactly the same way, because a file in Camera roll is a file like any other. The difference is only where to look: an uploaded photo is in the folder you put it in, and an auto-uploaded photo is in Camera roll, and if you open the wrong folder you will conclude the photo is not in OneDrive when it is. Search by name first — the search covers every folder — and let the app tell you where the photo lives.

Why does any of this need an article at all? Because the obvious thing — plug the drive into the phone and copy the photos — fails silently when the photos are still in the cloud. A USB drive plugged into an Android phone can only receive files that exist on the phone. The file manager can see Downloads, DCIM, Pictures, and every folder on internal storage; it cannot see inside your OneDrive account. SnapDisk can only copy files the phone's media index holds or a folder you point it at contains; it cannot reach into OneDrive either — the app has no INTERNET permission at all, which is a deliberate design choice, not a missing feature, and it means no cloud account of any kind is ever in scope for it. So the job is always two jobs: first get the files out of the cloud and onto the phone, then get them off the phone and onto the drive. The first job is a save. The second job is a copy. Guides that describe only one of the two are not wrong about the half they describe; they are useless for the job as a whole, because the half they skip is the half that stops you.

One more thing to settle before the steps: the photos you save are yours in the plainest sense. A .jpg saved from OneDrive is the same file you uploaded — same pixels, same resolution — because OneDrive stores files, it does not recompress your photos the way a backup service with a storage-saver setting might. Copy the file and everything worth keeping lives inside the file itself, byte-for-byte. That is the honest centre of this article: a OneDrive photo is an ordinary image file once it is saved, and the only trap is the save — the difference between a file on your phone and a file in your account, and the difference between the two menu items that look like they do the same thing and do not. The one thing that does not always survive is the date, and the date section below says so plainly, with Microsoft's own reproduction of the failure, because for OneDrive the date problem is worse than for the other clouds: the taken date can be lost twice, once at upload and once at download.

The wall: Save writes a file, Keep offline does not

The OneDrive app offers two menu items that sound like they save a file, and only one of them does. The first is Save, reached from the file's three-dot More menu: tap More next to the photo, tap Save, then tap the arrow at Save to this location, pick a folder, and tap Save again. The second is Keep offline, reached by tapping and holding the file and then tapping Keep offline at the top of the app. They are not two names for the same action. They are opposite actions with opposite results, and picking the wrong one is the single most common way this job fails — silently, because nothing tells you it failed. You tap the item, the app confirms something, and you go to copy the photo to the drive and find nothing there.

Save writes a real file. Microsoft's support page says so in the plainest terms it has: open the folder that has the files you want to download, make sure the folder contents appear in List view and not as thumbnails, tap More next to the file you want to save, and then tap Save — and then tap the arrow at Save to this location to see folders on your device, pick a folder for the downloaded files, and tap Save. Two independent guides agree on where the file goes: mobikin says the files are saved in the Download folder on your Android phone, and its FAQ says downloaded files are generally stored in your device's Downloads folder or another folder selected during the saving process; seedofyou says the Android app can save selected files, and to copy those saved items to independent storage. The file is an ordinary file in shared storage. Any app can reach it: the Files app can see it, the gallery can index it, and SnapDisk can copy it. That is what "a real file" means, and it is the whole point of this step.

Keep offline does not write a file. It keeps a copy inside the OneDrive app so you can read the photo without a connection. Microsoft's own page describes it exactly that way, under its own heading: mark files or folders offline to read them anytime, even when you are not connected to the internet, and files or folders marked for offline reading have the Keep offline icon in the List view — you tap the file listing anytime to open the file for reading. Seedofyou states the difference in one line, and it is worth quoting because it is the only source that states it in one place: "Make available offline is app access, not a separate archive." Mobikin's FAQ says the same thing in its own words: files marked for offline use may remain accessible through the OneDrive app instead of appearing as ordinary local files. A file kept offline lives in OneDrive's private storage, not in shared storage. It will not appear in the Files app. It will not appear in the gallery. SnapDisk will not see it, because SnapDisk reads the media index and the folders you point it at, and a file inside OneDrive's private storage is in neither. If you tapped Keep offline and then wondered why the backup found nothing, this is why: you saved the photo for OneDrive, not for the phone.

There is one more difference between the two that matters for this job, and it is the reason the save route goes through a folder picker. A saved file is yours, separate from your OneDrive account, and editing it on the phone does not edit the copy in OneDrive. Microsoft's page makes the same point for offline files in the other direction: files or folders marked offline are read-only, you can edit them only when you are online, and if you edit a file offline it saves as a new file and does not change the original OneDrive file. For a backup, the one-way save is exactly what you want — a standalone copy on a drive, independent of the account — but it means the save is one-way by design. Do not save a photo, edit the saved copy, and expect the edit to appear in OneDrive. It will not. Save again after the edit, or edit the file inside OneDrive instead.

So the rule for the whole article, stated once and used everywhere: Save means a file in Downloads; Keep offline means a file in OneDrive. If you are ever unsure which one you tapped, open the Files app and look in Downloads. If the photo is there, you saved it. If it is not, you did not — whatever the app seemed to confirm. And one detail that trips people up before they even reach the menu: the folder must be in List view, not thumbnails. Microsoft's steps say so explicitly, and the multi-select only works from List view too — press and hold one photo or video, then tap the circle next to additional file names to check them. In thumbnail view the same taps do something else, or nothing at all, and the Save item is not where you expect it. Switch to List view first, and the menu you see matches the menu this article describes.

What you need. Four things, none of them exotic. An Android phone with the OneDrive app installed and signed in to the Microsoft account that holds the photos — the account matters, because OneDrive shows you one account's files at a time, and a photo in a different account's OneDrive is invisible until you switch accounts in the app. Enough free space on the phone to hold the saves: the photos have to land on the phone before they can be copied to the drive, so if the phone is nearly full, save in batches and copy each batch to the drive before saving the next. A USB drive the phone can read and write — USB-C straight in, or USB-A through an OTG adapter that carries data, not just power; a charging-only adapter will power the drive and transfer nothing. And the drive formatted in a filesystem the phone can write: exFAT is the safe choice, because FAT32 cannot hold a single file of 4 GB or more, and SnapDisk skips such a file with its reason instead of failing the whole backup.

Check the drive before you start, not after the first batch fails. Plug it in, open Files by Google, and look under Storage devices: if the drive appears, the phone sees it. Copy one small photo to it by hand — select, Copy to, choose the drive — and open it from the drive to confirm it reads back. That one-minute check rules out the three most common hardware failures at once: a charge-only adapter, a drive the phone cannot mount, and a drive formatted in a filesystem the phone cannot write. The rest of this article assumes the drive works, because the save steps are the same either way, and a broken drive deserves its own diagnosis, not a footnote in a save guide.

One more check, on the OneDrive side: open the OneDrive app and confirm the photos are actually there. Search for one by name. If the app shows it, it is a OneDrive file and the steps below apply. If the app does not show it, check the other account — tap your picture at the top of the app and switch accounts, and note that you can add only one personal account to the app, so a second personal account means signing out of the first — and then check Google Photos, because the photo may be a library photo, not a OneDrive file, and the Photos download is a different menu in a different app. Do not save first and diagnose later: a save of the wrong photo is a waste of the phone's storage and your time, and a save of a photo that was never in OneDrive is impossible, which is a confusing way to discover the mistake.

Method 1: Save one photo, then back it up with SnapDisk

This is the core route, and it is short enough to do from memory once you have done it once. Open the OneDrive app. Open the folder that holds the photo — browse the folder, or search for it by name — and make sure the folder contents are in List view, not thumbnails. Next to the photo's name, tap the three-dot More menu. Tap Save. Tap the arrow at Save to this location to see the folders on your device, pick Downloads, and tap Save again. A notification tells you when the save has finished; wait for it, because a photo that is still saving is a half-written file, and a half-written file is not a backup of anything. Then open the Files app, look in Downloads, and confirm the photo is there: the file name should match the one in OneDrive, and the size should be plausible for a photo, not a few kilobytes.

That confirmation matters more than it sounds, because the Downloads folder is where the whole second half of the job starts. A photo in Downloads is a real file in shared storage, and everything downstream — the gallery, the file manager, SnapDisk — reads from shared storage. You do not need to move the photo out of Downloads, rename it, or put it in DCIM. Leave it where OneDrive put it. The default run, described in the next section but one, reads the media index with no folder filter, and Downloads is indexed like any other folder. Moving the file is an extra step that can only go wrong: a move that is interrupted leaves the file in neither place, and a rename breaks the link between the file on the drive and the file in OneDrive if you ever need to match them up again.

There is a shorter form of the same menu worth knowing, because the app's wording has shifted across versions and the guides describe it differently. Mobikin describes the route as: select the photos, tap the Save button at the bottom, then tap the Save button in the upper-right corner of the pop-up. That is the same route with fewer named steps — the More menu and the folder picker are the same sheet, described from the other side. If your app's menu shows Save directly under the three-dot button, without the folder picker step, use it: the result is identical, a file in Downloads. The steps in this article follow Microsoft's own support page, because that is the version Microsoft itself documents; if your app version shows a shorter menu, the shorter menu is the same action, not a different one. What matters is the last tap: Save, with a folder chosen. If you never see Save to this location, you have not saved anything yet.

Once the photo is in Downloads, the backup is one tap. Plug in the USB drive. SnapDisk shows a notification offering Backup — tap it, and the run starts. The app copies oldest-first, in the background, with a progress notification that shows the percentage, the gigabytes copied against the total, the speed, and the time left, and Pause and Stop on the notification itself. You do not pick the photo, the folder, or the file: the default run copies the whole library, and the saved OneDrive photo copies along with everything else. The free version caps each run at 5 GB; if the save batch is bigger than that, run it again past the cap and it picks up where it stopped, because files already copied are never copied twice. Pro is a one-time $9.99 purchase for auto-backup when a disk is connected and unlimited backup size. When the run finishes, open the drive in the Files app and check a few photos on the drive itself — open them from the drive, not from the phone — before you delete anything from the phone. SnapDisk copies, it never deletes: deleting the originals afterwards is your step, only after verifying the copy.

A note on scale, because it decides whether this method is the right one. Method 1 is one photo at a time, and it is the right method for a handful of photos — the ten you actually want, the folder of twenty from a trip, the scans someone sent you. It is the wrong method for a thousand photos, because a thousand three-tap saves is an evening of tapping, and an evening of tapping is a job that will not get done. For a folder full of photos, use Method 2, which empties a whole folder in one select-all pass. For a whole OneDrive account, use the OneDrive website on a computer — it downloads the whole account as a ZIP you copy to the drive — and accept that the whole-account job is the one job in this article that genuinely needs a computer. The phone route is for the photos you actually want, not for the archive you might want one day.

Method 2: A whole OneDrive folder — the select-all workaround (and the no-download-all limit)

OneDrive has no download-all button. That is not a guess: the WPS guide states it directly — "The OneDrive Android app lacks a one-click option to download the entire account at once, requiring manual workarounds for bulk downloads" — and seedofyou says the same thing in its own way, that the Android app can save selected files and you should use a computer for a folder archive. There is no menu item that saves a folder, no setting that saves an account, and no batch command in the Android app that empties a folder in one tap. The workaround is selection: open the folder in List view, long-press one file until the top bar shows one file selected, tap the circles next to the other photos to add them, then tap More in the upper right corner and choose Save, then pick a folder and tap Save again. Every selected file saves. It is a handful of taps for a whole folder instead of three taps per photo, and it is the difference between a feasible job and a tedious one.

There are two catches, and both are worth knowing before you tap Save on fifty files. The first is that the selection is per folder, and only per folder. A folder that contains subfolders is not emptied in one pass: the files inside each subfolder need their own select-all pass, inside that subfolder. For a folder with two subfolders, that is three passes; for a folder with twenty, it is twenty-one. At that point the honest advice changes: if the folder tree is deep, the phone route is the wrong tool, and the OneDrive website on a computer — which downloads a whole folder as a single ZIP, subfolders included — is the right one. Do not spend an evening tapping through subfolders to prove a point. The phone route is for flat folders and handfuls; the computer route is for trees and archives. Knowing which job you have is the skill, and the skill is worth more than any single workaround.

The second catch is that the selection includes everything you selected, and OneDrive's idea of a file includes things that are not photos. If the folder holds a mix — photos, a PDF, a spreadsheet, a video — the select-all pass saves all of them, and the save lands in Downloads as a mix. That is fine for the backup: SnapDisk copies the photos and videos and skips the rest, because its extension list keeps only image and video files, and a PDF in Downloads is simply not a photo. But it is not fine for the phone's storage if the folder is large, because every non-photo file you save still takes up space until you delete it. If the folder is mixed and large, save the photos in a separate pass: long-press one photo, tap the other photos one by one, then Save. It is slower, and it is the pass that respects the phone's storage.

One more detail on the multi-select pass, and it is a difference from the Google Drive route that is easy to get wrong if you have read our Drive article first. On Drive, selecting several photos at once may hand you a single ZIP file instead of separate photos, and the article warns you to unzip it before backing up. For OneDrive, no source this run says the app zips a multi-select save, and this article does not claim it does or does not — the behaviour is unreported, and stating it either way would be a guess. What the sources do say is that each selected file saves as its own file to the device. The check is the same either way: after the save, open Downloads and look. If you see separate .jpg files, the save worked as separate files. If you see one .zip, extract it in Files first, because SnapDisk copies photos, not ZIP archives. The check costs ten seconds, and it is the check that catches the case either way. The one route that definitely produces a ZIP is the computer route: on the OneDrive website, selecting a folder and choosing Download gives you a ZIP, and the Microsoft support forum's own answer says to choose "Compress files" to create it — so if you ever take the computer route for a folder, unzip before you copy to the drive.

There is also a question readers ask at this point that deserves a straight answer: can you save a shared folder — a family album, a work folder, a photographer's delivery — the same way? Yes. A folder someone shared with you is still a OneDrive folder, and the save steps still apply: find it in the Shared view — tap the Shared icon at the bottom of the app, then the sharer's name for a personal account — open the shared folder, select the photos, tap More, tap Save, pick Downloads, and the files land in Downloads like any other. But they are not your files, and that matters in two ways. First, the owner can remove your access, and a photo you have not saved yet is a photo you may lose — so save shared photos promptly, and do not assume they will be there next month. Second, the save is one-way, as the offline note says: changes to the saved copy do not flow back to the shared folder. The USB copy is yours once it is on the drive, and it stays yours even if the share is revoked — which is, after all, the point of a backup.

Method 3: Save straight to the drive from the Save-to screen

There is a shorter route than Downloads, and it is worth trying first, because if it works it skips the second half of the job entirely. When you tap Save, OneDrive shows you a Save to this location screen — a folder picker — and that screen lets you choose where the file goes. Microsoft's own steps say to tap the arrow at Save to this location to see folders on your device, and a USB drive plugged into the phone is a storage location too, so it may appear in the same list: plug the drive in before you start the save, and look for it in the Save-to screen. If it is there, pick it, and the photo lands on the drive directly — no Downloads, no second copy, no SnapDisk run needed for that photo at all.

The honest limit on this method is that the direct pick is reported for SD cards and untested for USB drives on this phone. Mobikin's FAQ says you may be able to choose an SD-card folder as the download destination on devices that support expandable storage, and that the available options depend on your Android version, OneDrive app version, and phone manufacturer — and no source this run shows a USB drive in the Save-to picker. The picker is Android's storage picker, and a mounted USB drive shows up in that picker in the ordinary case — the Files app lists it under Storage devices, and the picker draws from the same mounted volumes — but "in the ordinary case" is not a test, and this article does not claim a test it has not run. So the direct route is stated as a try-first, not as a promise: if the drive appears in the Save-to screen, use it; if it does not, save to Downloads and copy from there, which is the route the rest of this article proves. The two routes are not rivals. The direct route is the shortcut, and Downloads is the road that always works.

If the drive does not appear in the Save-to screen, check the mount before you blame the picker: open Files by Google and look under Storage devices. If the drive is not listed there, the phone has not mounted it, and no picker will show it — check the adapter, the cable, and the drive format first. If the drive is listed in Files but not in the Save-to screen, the picker is only showing internal storage, and the Downloads route is the answer, not a different setting. Do not spend the evening in the picker's settings: one look, and then save to Downloads.

One more thing about the direct route, because it changes how you should think about the batch. Saving straight to the drive writes one photo at a time, through the OneDrive app, with no progress detail, no resume if you unplug mid-save, and no verification that every file actually arrived. It is the right route for a handful of photos, and it is the wrong route for a hundred, because a hundred one-by-one saves is the same evening of tapping as Method 1, with less feedback. For a folder, save the batch to Downloads first — one select-all pass — and then let SnapDisk copy the batch to the drive in one run, with progress, pause, and a size check on every file. The direct route saves a step for one photo. The Downloads route saves an evening for a folder. Use each one for the job it fits.

Does SnapDisk's default run cover a saved OneDrive photo?

Yes — with one condition, and the condition is the whole point of this section. SnapDisk's default run reads Android's media index with no folder filter, so a saved photo in the Downloads folder copies with the rest of the library. The code is short enough to quote in full, and this article quotes it rather than paraphrasing it, because the claim is only as strong as the code behind it. The default run calls queryMediaStoreOldestFirst, which queries two tables — MediaStore.Images and MediaStore.Video, the external-content URIs — and merges the results, then sorts them oldest-first. The query itself passes no selection at all: the contentResolver.query call takes the projection, then null, null, then the sort order. Null selection means no filter. No folder filter, no file-name filter, no source filter. Every image and every video the media index holds is in the result, whatever folder it sits in — DCIM, Pictures, Download, or anywhere else in shared storage.

The condition is that the photo has to be in the media index at all. A photo the gallery shows is a photo the index holds, and a photo the index holds is a photo the default run sees. That chain is the test you can run yourself: save the photo, open the gallery, and look for it. If it is in the gallery — in the Download album, or in the camera roll if you used a save-to-gallery route — it is indexed, and the default run covers it. If it is not in the gallery, open the Files app and look in Downloads: if the file is there but the gallery does not show it, the index has not picked it up yet, and the fix is to wait a moment or open the file once, which prompts the media scanner; or use the From picker route, covered in the uploaded-versus-camera-upload section below, which reads the folder directly and does not depend on the index at all. Either way, the check is the gallery, and the gallery is the answer to the question this section asks.

What the default run does not do is reach into OneDrive. That is not a limitation to work around; it is the design. The app holds no INTERNET permission — zero occurrences in the manifest — and no Google Play Services dependency, so it cannot open a network connection and cannot ask OneDrive for anything. A photo still in the cloud is invisible to it, in exactly the same way a photo still in the cloud is invisible to the file manager. The save is not an optional first step you can skip by pointing the app at OneDrive; it is the step that moves the photo from a place the app cannot reach into a place it can. Anyone who tells you an app can back up OneDrive photos without saving them first is selling you a different app, or a misunderstanding.

The default run also does not care where the photo came from. It does not know, and it does not need to know, whether a .jpg in Downloads came from OneDrive, from a browser, from WhatsApp, or from a camera. It reads the index, it sorts oldest-first, it copies the file byte-for-byte, and it verifies the size of every file after copying — a copy result is only recorded as copied after the verification passes. The source of the photo is irrelevant to the copy, and that irrelevance is a feature: it means the OneDrive route, the Drive route, the Dropbox route, the WhatsApp route, and the camera-roll route are all the same route once the file is on the phone, and the only part that differs is the save that puts it there.

The date problem: a saved photo shows the download date

There is one honest limit in the default run that this article has to state plainly, because it changes the order your photos arrive in on the drive — and for OneDrive it is worse than for the other clouds, because the date can be lost twice. A photo saved from OneDrive shows the download date, not the date the photo was taken. That is not a suspicion. Microsoft's own support forum reproduced it on its side, on different devices and different operating systems: photos downloaded from OneDrive only show the date of download. So the run is oldest-first by effective date, and the effective date of a saved OneDrive photo is, in the ordinary case, the day you saved it. A photo taken in 2019 and saved today copies as if it were taken today, at the end of the run rather than near the beginning. If the order matters to you — if you want the drive to read like a timeline — that is worth knowing before you start, not after you finish.

The code is explicit about the fallback, and it is worth quoting because it is the difference between a guess and a fact. The query projects both DATE_TAKEN and DATE_MODIFIED, and the sort order is a CASE expression: when DATE_TAKEN is null, use DATE_MODIFIED times a thousand; otherwise use DATE_TAKEN — ascending, with the row id as the tiebreak. The comment above it says it in one line: missing DATE_TAKEN falls back to DATE_MODIFIED. DATE_MODIFIED for a saved file is the save time, or close to it. So the run is oldest-first by effective date, and the effective date of a saved photo is, in the ordinary case, the day you saved it. That is not a bug. It is the only sane fallback when the taken date is not there — and it is the reason the article says "oldest-first by the date the phone knows", not "oldest-first by the date the photo was taken", when the photos came from a save.

And the date can already be gone before the download even happens. Microsoft's support forum is equally plain about the upload side: OneDrive is aware of the issue where it overwrites the "Date taken" metadata with the upload date, especially when using the mobile app for photo backup, and the mobile app on Android often replaces the original EXIF "Date Taken" with the file system's "Date Modified" or the upload timestamp — most commonly when uploading in bulk, when using the Camera Upload feature, and when uploading from apps like WhatsApp or Signal, which may strip metadata. So a photo that was camera-uploaded to OneDrive may already carry the upload date in OneDrive itself, before you ever tap Save. The forum's own recommendation is to use the OneDrive desktop app on a computer and copy photos into a local folder synced with OneDrive, which preserves the original EXIF metadata — but that is a computer route, and this article is a no-computer route, so it states the loss instead of routing around it.

Whether the taken date survives at all depends on the file, and the cases where it fails are common enough to name. A photo that was uploaded to OneDrive from Google Photos, rather than from a camera, may carry the upload date rather than the taken date. A photo that was edited in an app that rewrites EXIF may carry the edit date. A screenshot has no taken date at all in the photographic sense — its DATE_TAKEN is the moment of the screenshot, which is the date you want anyway. And a photo saved through a browser, rather than through the OneDrive app, may be re-written by the browser's download handling in ways that drop or alter the metadata. The practical rule is simple: save one photo, check where it lands in the gallery's date order, and you will know what the rest will do. If it lands on its taken date, the batch will too. If it lands on today, the batch will too, and you should decide whether that matters before you save a thousand of them.

There is a second, subtler version of the same problem, and it concerns the file name rather than the date. OneDrive lets two files in different folders share a name — "IMG_0001.jpg" in the 2019 folder and "IMG_0001.jpg" in the 2021 folder — and when you save both to the same Downloads folder, the second save either overwrites the first or arrives as "IMG_0001 (1).jpg", depending on the app version and the phone. Either way, something is lost: an overwrite loses a photo, and a rename breaks the match between the file on the drive and the file in OneDrive. The defence is to save one folder at a time and copy each batch to the drive before saving the next, or to rename the folders in OneDrive first so the names are unique. It is a dull precaution, and it is the precaution that saves a photo. The backup verifies the size of every file it copies, so a photo that was overwritten before the backup started is a photo the backup cannot know about — the verification proves the copy matches the file on the phone, not that the file on the phone is the photo you meant to save.

If the order on the drive matters more than anything else — if you are building an archive, not just a copy — the From picker route gives you more control than the default run, because you choose the folder, and the folder's contents copy in their own oldest-first order, separate from the rest of the library. Save the 2019 folder, back up Downloads, clear Downloads, save the 2021 folder, back up Downloads again: the drive ends up with the folders in the order you chose, even if the dates inside them are save dates. It is slower, and it is the route for an archive. The default run is the route for a backup. Know which one you are doing.

Photos you uploaded vs photos camera upload saved

This section is the untangling, stated as a table and then as a rule, because it is the section readers will come back to when they are stuck. There are two ways a photo ends up in OneDrive, and they look identical in the app but are different in every way that matters for finding them. The first is upload: you, or someone, put a file in a OneDrive folder — dragged it in a browser, tapped Upload in the OneDrive app, or saved it there from another app. The photo is a file in a folder, and the OneDrive app shows it in that folder, and the save steps in this article apply. The second is camera upload: your phone's OneDrive app uploaded the camera roll automatically, and the photo lives in a folder called Camera roll. The photo is a file too, and the save steps apply to it exactly the same way — the difference is only where to look.

Camera upload deserves a paragraph of its own, because it is the case most OneDrive users actually have. When you turn on camera upload in the OneDrive app — Settings, then Camera upload, then set it to On — the app copies every photo and video you take into your OneDrive account, at original size when you are on Wi-Fi, into a folder called Camera roll. That is Microsoft's own description, from the support page this article is built on: if your device is set to automatically upload pictures to OneDrive, pictures you take with your device go to the OneDrive Camera roll folder, and you do not need to upload them manually. You cannot change where they go — the folder is always Camera roll — and that fixed name is a gift for this job, because it means the whole auto-uploaded set is one folder, and one folder empties in a single select-all pass from Method 2. Open Camera roll, long-press one photo, select all, More, Save, pick Downloads, and the whole set is in Downloads. If your photos are the ones your phone uploaded by itself, you do not need to hunt through folders at all: the folder is named, the folder is one, and the pass is one.

There are two details on camera upload worth knowing before you rely on it. The first is the account: camera upload is set per account, and if the toggle is greyed out, the page says, you need to select an account first under Camera upload account. For a work or school account the route is different again — Me, then Photos, then turn camera upload on from the pop-up — so if you are saving from a work account, look there, not in Settings. The second is the date, and it is the bad news from the date section in its sharpest form: camera upload is one of the two cases Microsoft's forum names for the taken date being replaced by the upload date, so a photo that reached OneDrive by camera upload is the photo most likely to have already lost its taken date before you save it. Save one, check the gallery, and you will know.

One tool fits both cases, and it is worth naming here because the default run copies the whole library and sometimes the whole library is not what you want. Sometimes the OneDrive photos are the only ones that matter — the rest of the library is already backed up, or the rest of the library is three years of screenshots you do not want on the drive — and in that case the From picker is the tool. Open SnapDisk, open settings, tap the From folder, and pick Downloads. The app then backs up exactly that folder, and nothing else.

The picker route is code-supported, and it is worth saying exactly what that means, because this article does not claim a test it has not run. The picker is Android's folder picker — ActivityResultContracts.OpenDocumentTree, with no folder pre-selected — and the code that lists the folder walks the folder tree directly, recursing into subfolders, and keeps only files whose names end in an image or video extension. That walk does not depend on the media index at all: a photo the index has not picked up yet still copies, because the picker reads the folder, not the index. The extension list it uses is the same list the default run uses, and it includes .jpg, .jpeg, .png, .heic, .heif, .webp, .gif, .bmp, .dng, .raw, .avif, and .jxl for images, and .mp4, .mov, .mkv, .webm, .3gp, .m4v, and .avi for video. A OneDrive photo is a .jpg or a .png in the ordinary case, and both are in the list.

What this article does not claim is that a SnapDisk test has picked the Downloads folder end to end on a real phone. No SnapDisk test has run a OneDrive backup end to end on a real phone at all — the app is pre-launch, the backup has been proven on the emulator, and the real-device proof on the owner's Pixel 9a is still an open gate. So the From-picker route is marked code-supported but untested on this exact folder, in the same form the series has used since WL-246: the code path exists, the folder is an ordinary folder in shared storage outside Android/data, and the navigation chain is ordinary folders, none dot-prefixed — but the end-to-end run on this folder has not happened, and the article says so instead of asserting it. If you use this route, verify the copy on the drive before deleting anything, exactly as you would for the default run. The verification is not a formality; it is the test.

There is also a manual route that needs no app at all, and it is worth keeping in the article because it is the fallback when everything else fails. Plug in the drive, open Files by Google, go to Downloads, select the photos, tap Copy to, choose the drive, and tap Copy here. It works, and it works for any file. The manual route has no progress detail, no resume if you unplug mid-copy, and no verification that every file actually arrived, and you have to repeat the whole selection next time photos pile up. That is the honest contrast: the manual copy is the route that always works, and SnapDisk is the route that works without the repetition. Use the manual copy to check the drive works; use SnapDisk for the backup itself.

Checking the drive after the copy

A backup you have not checked is a hope, not a backup. The check takes two minutes, and it is the same check the series has used since the first article, because it is the only check that proves what matters. Plug the drive into the phone — or into a computer, if one is handy — open it in the file manager, and open three photos from the drive itself, not from the phone. Pick one from the beginning of the run, one from the middle, and one from the end: the oldest, a middle one, and the most recent save. If all three open, full-size, from the drive, the copy worked. If one does not open, or opens as a thumbnail, or opens at the wrong size, something went wrong with that file, and the fix is to run the backup again — SnapDisk skips files already copied at the right size and copies the ones that are missing or wrong, so a second run repairs the first without starting over.

Check the count as well as the content. The Files app shows the number of files in a folder and the folder's total size; compare those against Downloads on the phone before you delete anything. The numbers will not match exactly — the drive holds the photos, and Downloads holds the photos plus whatever else was already there — but the photo count should match the number you saved, and the total size should be close. If the drive holds far fewer photos than you saved, the likely cause is the duplicate-name problem from the date section: a second save overwrote the first under the same file name, and the photo is gone from Downloads before the backup ever saw it. Save one folder at a time and copy each batch before saving the next, and check the count a second time. If the drive holds far more photos than you saved, the likely cause is the default run: it copied the whole library, not just the OneDrive batch, which is what it is supposed to do, and the extra photos are your camera roll, correctly backed up. That is not an error. It is the default run doing its job, and the article says so because the first time it happens it looks like one.

Check the dates, too, with the expectation set in the date section: a saved photo shows the download date, not the taken date, and that is expected, not a failure. What is a failure is a photo with a date of 1970, or a photo with no date at all in the file manager's list: that usually means the metadata did not survive the save, and the photo itself is still fine — the pixels are all there — but the date is gone, and it will not come back. If the date matters, save that photo again through the OneDrive app rather than the browser, and check whether the date survives the second time; if it does not, the metadata was lost at upload, not at save — camera upload is the usual suspect — and no save route will recover it.

Finally, eject the drive before you unplug it. Android's Files app offers an eject or unmount control for the connected drive, and the drive's own notification offers the same. It takes one tap, and it is the difference between a finished write and a corrupted one: unplugging mid-write is the single most common cause of a drive that reads fine on the phone and fails on the computer, or the other way round. SnapDisk's verification — the size check on every file after copying — proves the copy matched the file on the phone at the moment it was written; it cannot prove the drive's filesystem survived being yanked out during the last write. Eject, wait for the confirmation, then unplug. Then put the drive somewhere safe, and label it with the date: a drive you cannot find is not a backup either.

What to avoid

Do not tap Keep offline and call it a save. It is the trap this article is built around, and it is worth repeating in this section because it is the mistake readers make after reading the steps: the two menu items sit near each other, the offline one sounds more thorough, and the confirmation it gives sounds like a download. It is not. A file kept offline lives inside the OneDrive app, and nothing outside the OneDrive app can see it. If you have already tapped it, nothing is lost — tap More again, tap Save, pick Downloads, tap Save again, and the real file appears in Downloads.

Do not save the whole OneDrive account to the phone. The phone does not have room for it, and the save will fail partway through with a storage error, leaving a half-saved set that is worse than nothing, because you will not know which photos arrived and which did not. Save in batches — one folder at a time, or fifty photos at a time — copy each batch to the drive, and delete the batch from Downloads before starting the next. The batch size is set by the phone's free space, not by your patience: leave at least a gigabyte free at all times, because Android itself needs room to work, and a phone with zero free space stops saving, stops copying, and stops telling you why.

Do not use Move instead of Copy, in the file manager or anywhere else. Move deletes the original as it goes, which means a failure halfway through the move loses the photos that were already moved and the photos that were not yet moved in different ways, and neither is recoverable from the other. Copy leaves the originals on the phone until you have verified the drive, and the verification is the step that makes the whole job safe. SnapDisk copies and never deletes, for exactly this reason: the only .delete() calls in the code are on SnapDisk's own half-finished .part files, the temporary files of a copy that was interrupted, and they exist so a failed copy does not leave a corrupt file pretending to be a photo.

Do not save straight to the drive for a whole folder. The direct route from Method 3 writes one photo at a time with no progress detail and no verification, and a hundred one-by-one saves is an evening of tapping with nothing to show for it until the last one. Save the batch to Downloads first, then let SnapDisk copy the batch in one run. The direct route is the shortcut for one photo. The Downloads route is the road for a folder.

Do not trust the cloud as the only copy. OneDrive is a store, not a backup: files in OneDrive can be deleted, accounts can be closed, shares can be revoked, and storage quotas can be exceeded, and any one of those turns a photo in OneDrive into a photo that is gone. The USB drive is the second copy, and the second copy is the one that survives the account. That is the whole argument for this article in one paragraph: the cloud is convenient, the drive is yours, and a photo with one copy is a photo at risk. Save it, copy it, check it, and then — only then — delete the original from the phone if you need the space.

Do not assume the screen-off run finished. Screen-off continuation under battery saver is unverified — the repo holds no wake lock and no battery-saver handling — so keep the phone awake for the run or check it. The Android 15 six-hour dataSync budget is handled: the backup service pauses cleanly with a message when the budget is reached, and the run resumes from where it stopped. But a phone that fell asleep under battery saver is a different case, and this article does not claim it works, because no test has proven it. Plug the phone in, keep the screen on, and watch the progress notification reach 100%. A watched run is a finished run.
