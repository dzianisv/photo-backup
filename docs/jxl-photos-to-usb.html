Save JPEG XL photos to a USB drive from Android

A JXL is an ordinary .jxl file — smaller than a JPEG, with lossless JPEG inside. The job is getting the file onto the drive, because no camera shoots it, Android itself can't open it, and the two backup routes disagree about it.

November 25, 2026 · 14 min read

TL;DR: A JXL is an ordinary .jxl file, and everything that makes it worth keeping lives inside the file itself — the smaller size, the HDR, the transparency, and, for a JXL made from a JPEG, the reconstruction data that restores the original JPEG bit for bit, no conversion note, no sidecar file, nothing like the slow-motion case where the speed lives in a note attached to the video. That is the good news, and it makes the backup simple once you have the file: copy the .jxl and all of it comes with it, byte-for-byte, because there is nothing to lose in the copy. The trap is the route, and it is a trap with two jaws that bite in opposite directions The first jaw is the default run: SnapDisk's default backup reads the phone's media index with no extension filter, so a .jxl the index holds copies like any other photo — but whether the index holds a .jxl at all is not settled by the code or by the public Android sources, so the default run covers your JXLs on a phone whose scanner indexed them and copies zero of them on a phone whose scanner did not, and nothing in the run tells you which phone you have. The second jaw is the From picker, and it is certain in the other direction: the picker walks a folder and keeps only the extensions in the app's recognised list, and .jxl is not in that list — so pointing the picker at Downloads copies every photo in the folder except the JXLs. The third fact decides the whole job before either route matters: no mainstream Android camera shoots JXL, and Android itself cannot open a JXL file — the gallery shows a blank thumbnail, and the only viewer on the phone that decodes it is Chrome 155 or later, which turned JXL decoding on by default on October 6, 2026. So the certain route for a .jxl you can see in Downloads or Pictures is the file manager's manual copy, in Method 2 — and the default run is the try-first route, because it costs nothing to try and it covers the indexed JXLs with no step beyond the hunt. The check is opening one JXL back from the drive in Chrome 155 or later and watching it open — because a JXL that lost its quality still looks like a photo in every other check, and the gallery cannot do the check at all. And screen-off continuation under battery saver is unverified — the repo holds no wake lock and no battery-saver handling — so keep the phone awake for the run or check it. As of November 25, 2026, no top search result offers a dedicated JXL-to-USB how-to: the results are generic OTG copy guides that never name JXL at all.

The wall: the JXLs you see are files you never chose — and the phone can't open them

Start with the fact that decides the whole job, because the JXL wall is easy to misread in both directions at once. It is not a locked door like Threema's wall: the photos exist and the app will not let them out until you save them. And it is not a hall of mirrors like the GIF wall: the GIFs are everywhere on your screen and almost none of them is a file. The JXL wall is a filing error with a second fault underneath it — and a third fault on top, which is the phone itself. The files exist, the backup can copy them — and they sit in folders nobody thinks to look in, under a name nobody recognises, because JXL arrived quietly, and the phone that holds them cannot open them. It is the web's newest image format in the other direction from AVIF: smaller than a JPEG at the same quality — 30 to 50 percent smaller, by the Chrome team's own numbers — with HDR and transparency in the same file, able to animate, and with one trick no other format in this series has: it can recompress an existing JPEG losslessly, about 20 percent smaller, in a way that is fully reversible, so the original JPEG can be restored bit for bit from the JXL. Chrome 155 turned JXL decoding on by default on October 6, 2026, on desktop and on Android, and Firefox 158 followed a week later — so a phone can hold JXL files now, and the owner has never once seen the extension, because the gallery shows nothing at all for them, not even the picture.

That is the wall, and it is a total one in the same way the messaging-app walls are, but with the blame in a different place and two more faults underneath. A phone full of JXLs that were never hunted down is a phone full of files the backup copies only by accident: the default run copies the ones the media index knows about — the Downloads saves, the Pictures exports — and misses the ones it does not, because whether the phone's media scanner indexes .jxl files at all is not settled. The difference from AVIF is what the phone does about it. For AVIF, the gallery at least shows the picture on Android 12 or later, so the owner can see the files exist. For JXL, the gallery shows a blank thumbnail or nothing, because Android itself has no JXL decoder — the operating system is the outlier here, and the format may not arrive in Android until version 18 in 2027, if then — so the owner cannot tell a JXL from a broken file by looking at the gallery, and the only viewer on the phone that decodes it is Chrome 155 or later. And the difference from WebP is what the picker does about it. For WebP, the picker was the certain route: the folder walk keeps .webp files. For JXL, the picker is not a route at all: the folder walk keeps only the extensions in the app's recognised list, and .jxl is not in that list — so the picker copies every photo in the folder except the JXLs. There is no single save step to turn on, and no single folder to point at, and the one tool that usually rescues a format the index missed does not rescue this one, and the phone cannot even show you the files to check. The job is a hunt first and a copy second, and the hunt is the part this article does that the generic guides do not — and the copy, for JXL, is the file manager's manual copy, not the picker.

Two scope facts, because they decide what this article can and cannot promise. First, the file itself is simple in a way that should reassure you once you have it: a JXL is an ordinary file with everything stored inside it — the smaller size is the compression, the HDR is a wide gamut in the file, the transparency is an alpha channel in the file, and the lossless JPEG reconstruction data, for a JXL made from a JPEG, is stored inside the file too, so the original JPEG can be restored bit for bit from it. Copy the .jxl and you copy all of it — the HDR, the transparency, the reversible JPEG — because the copy is byte-for-byte and the bytes are the picture. There is no conversion step to get wrong and no quality setting to choose, and SnapDisk never converts anything in any case. Second, the format confusion is real and worth naming plainly: a JXL is not a JPEG with a different name, and renaming a file does not convert it. A file called photo.jxl holds JXL data; renaming it to photo.jpg leaves JXL data inside a file called .jpg, and the next app that opens it by extension will fail or misread it. The guides that measured this say it outright: keep the extension the site supplied unless you intentionally convert the file with an image editor. This article is about the .jxl files; a file that was renamed is a different problem, and the fix is converting it properly, not renaming it back.

And a word on whose JXLs these are, because JXLs are usually someone else's picture — a photo from a site, a shot someone sent you, a frame clipped from a show — and because the line between saving and re-posting is worth stating plainly. The JXLs this article covers are the ones you downloaded or were sent for yourself: an image you saved from a web page, a photo a friend sent you as a file that you want to keep. Saving them to your own drive for your own records is the job. They are also someone else's work in a plain sense: a photograph with a photographer, a picture with an author you will never meet. Saving a file does not grant permission to reuse it — so re-posting a JXL as if it were yours, or using someone's picture in your own content without asking, is a different act, and the same courtesy applies here as anywhere: the person who made it is the person to ask before the JXL leaves your phone for anywhere else. This article's methods copy the file to your drive; asking is the honest step before anything leaves your phone. Only save JXLs you have permission to keep — and this article makes no claim about recovering JXLs from a chat you have already deleted, because the chat apps keep no .jxl file to recover once the chat is gone, and a JXL that was served from a library was never yours to recover in the first place.

Where .jxl files live on an Android phone — Downloads, Pictures, and nowhere in the camera roll

This section exists because the folder is the one fact the guides do not answer at all — and because JXLs, unlike the messaging-app photos in this series, have no single home folder, and unlike the AVIFs, they have no camera-roll home at all. A Threema photo lands in Pictures/Threema; a WhatsApp photo lands in WhatsApp Images; an AVIF camera shot lands in DCIM/Camera. A JXL lands wherever the thing that made it put it, and the phone has two different makers and one folder that never holds them. So this article does not state one path as the path for every JXL. It gives the check order instead, and the check order is the same on every phone — and the check itself is the file extension, not the app that showed it to you. A file that ends in .jxl is a JXL; a file that ends in .jpg is a JPEG, even if it looks identical on screen.

Check Downloads first. Open your file manager, go to Internal Storage, then Download — or open Files by Google and tap Downloads. This is where a JXL downloaded from a browser lands: Chrome on Android saves every download to the shared Downloads folder by default, at Internal Storage/Download. A JXL you long-pressed on a web page and saved, a JXL you downloaded from a converter site, a JXL someone sent you as a file attachment that your app saved to Downloads — all of them land here, as .jxl files with their HDR and transparency and lossless JPEG data intact. Most of the images on the modern web are served as AVIF or WebP now, and JXL joined them in October 2026: Chrome 155 puts image/jxl first in the Accept header it sends for images, so a site that picks a format from that header now replies with JXL, and the long-press save writes those bytes to disk — there is no Chrome setting that changes that, and no step in the middle where Chrome re-encodes the picture into something else. If you have ever saved an image from the web on purpose since October 2026, it may well be here, and this is the folder to check first because it is the only folder a deliberate JXL save reliably produces.

Check Pictures second — and understand that the third check, the camera roll, is the one this article does not have. Pictures is where a JXL saved from an app that writes to the shared Pictures directory lands, and where a converted photo exported by an editing app or a converter app usually goes, and it is worth a look when Downloads comes up empty. Then check the folder the transfer used, if one was involved: a JXL moved from a computer over USB lands wherever you put it — often Downloads, sometimes a folder you made for it — and a JXL from a photo library converted on a computer lands wherever the conversion tool wrote it. Then stop: do not check DCIM/Camera expecting JXLs — no mainstream Android camera shoots JXL, and a .jxl file in DCIM/Camera is one you moved there yourself, not one the camera made. If the file is in none of those places, check that the save actually happened: a JXL you only viewed on a web page was never saved, a picture you only saw inside a chat was never a file, and a JXL you only saw in a browser older than Chrome 155 was never shown to you at all — the old browser could not decode it, so it showed nothing, and there was nothing to save. The hunt ends where the file begins — and for a JXL that was never a file, the hunt ends with making one: save the image from the web page in Chrome 155 or later, or convert it from the JPEG or PNG you already have, and then it is a file like any other.

One more scope fact for this section, because it decides what the drive copy holds: the saved .jxl is the JXL as it was when you saved it, and the phone gives you no way to improve it afterwards. A JXL is already the small version — that is the point of the format, 30 to 50 percent smaller than a JPEG at the same quality — so a JXL saved from the web is already a compressed copy of whatever the site had, and copying it byte-for-byte keeps it exactly that good and exactly that bad. SnapDisk copies the saved file with no conversion — but it cannot recover detail the JXL compression already removed. If the picture you want is a photo you still have as a JPEG in your camera roll, the JPEG is the one worth keeping alongside it: the JXL is a smaller copy the web made for loading fast, and the original is the one with the full detail. And the JXLs you converted yourself are a separate case again: they were made from a JPEG or a PNG, and the original is usually still in your camera roll in DCIM/Camera — back that up too, because the JXL is a small copy of a moment the original holds in full. The one exception is a JXL made by lossless JPEG recompression: that JXL carries the reconstruction data that restores the original JPEG bit for bit, so it is not a lesser copy — it is the original, smaller — and keeping the JXL alone is enough, because the JPEG can be rebuilt from it exactly.

What you need

An Android phone — Android 7.0 or later, which is SnapDisk's minimum version — with the apps that hold your JXLs already on it, plus one USB drive your phone can read: a USB-C flash drive, or a regular USB drive with a USB-C OTG adapter. SnapDisk itself is installed from the v0.1.2 APK — it is not on Google Play yet — so install it by allowing "install unknown apps" for the browser or Files app you download it with, which is standard Android. You need one more thing no other format article in this series has asked for: Chrome 155 or later on the phone, because Chrome is the only viewer on the phone that decodes JXL. The gallery cannot do it — Android itself has no JXL decoder — so the check step in this article happens in Chrome, not in the gallery, and an older Chrome cannot do it either: Chrome 154 and earlier show nothing for a .jxl file, because the decoder only turned on by default in 155. If your Chrome is older, update it from Google Play before you start, and the check will work. You need nothing else for the main route: no extra app, no account. The hunt step is inside the apps you already have — the browser's Downloads, the file manager — and the backup is SnapDisk's default run, or the file manager's manual copy in Method 2. One version note that matters for JXL and for no other format in this series: the phone that holds the JXLs does not need to decode them to copy them — a copy moves bytes, and bytes do not care about the format — but the phone you check them on does need to decode them. Chrome 155 or later decodes JXL on Android; on a phone without it, the check has to happen on a computer — Preview on a Mac, a Windows computer with the free JPEG XL image extension, or a browser viewer page that brings its own decoder. Check the drive's space first: JXLs are small — a JXL is 30 to 50 percent smaller than the JPEG it replaces, a web-saved JXL usually well under a megabyte — so space is almost never the problem here, but look anyway, because a whole-library default run copies everything, not just JXLs. One format note: drives formatted FAT32 cannot hold a single file over 4 GB. That only matters for very long videos — SnapDisk skips those files and lists them instead of failing the whole backup. A drive formatted exFAT has no such limit, and exFAT is the format to use for a photo drive.

Before any method, settle the one question that decides whether the phone route works at all: does your phone see the USB drive? Plug the drive in and open Settings > Connected devices or Settings > Storage — the drive should appear there. That check is the test, and it takes ten seconds. If the drive does not appear, try a different adapter first — cheap OTG adapters are the usual failure — then a different drive, and a powered hub if the drive is a spinning hard drive rather than a flash drive. And one warning up front, because it applies to every route below: do not delete anything from the phone until the USB copy is done and verified. The JXLs in Downloads are yours — but until the drive copy is checked, Downloads is the only copy outside the browser, and deleting from Downloads before the check is how a JXL ends up nowhere at all. And do not delete the chat app, or clear its data, until the save and the copy are both done: a picture that was never copied as a file is gone when the chat is gone, and the web does not keep a second copy of an image it served you once.

Method 1: Find the saved .jxl, then back up with SnapDisk

This is the route to try first, because it is the only one that joins the whole job — the .jxl file, found on the phone, onto a USB drive plugged into the phone, no computer — using only the apps already on the phone plus SnapDisk. It has two halves, and they have to happen in order: the hunt, which finds the .jxl files, and the SnapDisk copy, which puts them on the drive. The first half is the work, and with JXLs it is a hunt across folders rather than a single save step, because there is no switch to turn on and no single folder to open. Skipping the first half is the mistake this article exists to prevent: running SnapDisk's default backup without knowing where the JXLs are copies every photo in the gallery — and possibly zero JXLs.

  1. Hunt the .jxl files first, in check order. Open your file manager and go to Internal Storage, Download — the browser-downloaded JXLs live here, as .jxl files. Then check Pictures for JXLs saved from apps that write there. Then check the folder a transfer used, if one was involved. The check at each stop is the file extension: a file that ends in .jxl is a JXL, and a file that ends in .jpg is a JPEG, even if it looks identical on screen. If a folder holds no .jxl files, move on — do not assume the JXLs are there because the folder's name sounds right. If you find JXLs in more than one folder, note all of them: the default run covers the indexed ones all at once, and the manual copy in Method 2 needs one selection per folder.
  2. If the hunt comes up empty, make the file before you back it up. A JXL you only viewed on a web page was never a file, and a JXL you only saw in a browser older than Chrome 155 was never shown to you at all — neither is on the phone, and no step in this article conjures a file out of a viewed picture. The fix is at the source: open the page in Chrome 155 or later, long-press the image and save it, and it lands in Downloads as a .jxl — or convert the JPEG or PNG you already have into a JXL with a converter, and it lands in Downloads or Pictures as a .jxl. A JXL sent to you as a file attachment, rather than as a chat image, is already a file: save the attachment, and it lands in Downloads or the app's folder as a .jxl. Do not try to rescue a chat picture by sharing it to yourself: the share step can convert a JXL to a JPEG, or hand on a still instead of the file, and a shared copy is the least reliable JXL on the phone.
  3. Do not re-share a JXL to get it onto the drive. This is the trap the whole article is built around, and it deserves its own step because it looks like the obvious shortcut. Sharing a JXL out of the Gallery or a chat into another app — into a file manager, into a different chat, into yourself — can change it on the way: some share targets re-encode the file as a JPEG, dropping the HDR and the lossless JPEG data with it, and some take only the still out of an animated JXL and hand on a JPEG instead of the .jxl. A converted copy is a JPEG wearing a JXL's name, and no backup step after it restores the HDR or the reconstruction data, because both were lost in the share, not in the copy. The certain route copies the saved .jxl file, never a re-shared copy — and if the only copy you have is a re-shared one, go back to step 2 and save the JXL from its source instead.
  4. Check the files are in Downloads or Pictures. Open your file manager, go to Downloads, and look for .jxl files — if they are there, the save works. Then check Pictures — if the .jxl files are there, the converter or the app saved them there, and this is also the check that proves the manual copy in Method 2 can reach them, because the file manager and the copy read the same folders. If the files are in the folder but the gallery shows a blank thumbnail, that is expected — the gallery on every Android version cannot decode JXL — and it is not a problem for the copy, which moves bytes and does not decode anything. Open the file in Chrome 155 or later to see it. If no folder holds a .jxl at all, the save is the suspect: a JXL you viewed was never saved, and step 2 is the fix — save it from the web page in an updated Chrome, or convert it from the JPEG or PNG you have.
  5. Plug in the drive and run SnapDisk. Plug the USB drive into the phone. SnapDisk offers the backup in a notification — tap Backup — or open the app and tap Start. The run copies oldest-first, verifies every file by size after copying, and shows progress with Pause and Stop in the notification. The free run covers up to 5 GB, and JXLs are small, so one run is almost always enough for the JXL half — though a whole-library run copies everything else too. Screen-off continuation under battery saver is unverified — the repo holds no wake lock and no battery-saver handling — so keep the phone awake for the run or check it. And the check after this step is the whole job for JXL: open the drive and look for the .jxl files by extension. If they are not there, the run is not the first suspect — the index is. Go to Method 2 and copy them by hand.
  6. Do not plan around the JXLs you never saved. A JXL you only viewed on a web page is still on the web page, and no step in this article changes that: there is no save-all for a page's images, and there is no export that writes a page's JXLs out as files. If a JXL matters, save it from its source now, while the page is still up — a JXL that was served from a site is gone when the site stops serving it. A screenshot is the only copy left for a JXL the built-in save will not give you — and a screenshot is a picture of the screen, not the JXL: it is a still image, usually a PNG or a JPEG, it carries the app chrome around it, it lands in the Screenshots folder, not with the JXLs, and it does not hold HDR and has no lossless JPEG data to keep. Do not plan a backup around saving what the apps will not let you save as a file.

Two honest limits. First, the hunt is not retroactive in the other direction either: finding JXLs today does not put the JXLs from a chat you already deleted onto the phone — a deleted chat is gone, and the web keeps no second copy of an image it served you once. That is step 2's job, and it is a manual job: one save per JXL. Second, the 5 GB free cap is per run — a JXL collection will never reach it, but a whole-library default run might, and running it again picks up where it stopped, because files already copied are never copied twice. Third, SnapDisk copies, it never deletes: deleting the JXLs from the phone after the check is always your step, never the app's — and deleting them from the chat is the chat app's, not SnapDisk's, and it does not free the drive copy. The drive copy is the backup; the phone copy is the original until you decide otherwise.

Copying only some JXLs? If you would rather copy just a few JXLs than the whole collection, the From folder picker still takes a folder, not single files — and for JXL it takes nothing at all, because .jxl is not in the recognised list — so copy the ones you want in the file manager instead: select the .jxl files, tap Copy, navigate to the USB drive, and tap Paste. That is Method 2, and for JXL it is the certain route, not the fallback. If the drive is unplugged mid-copy, the SnapDisk backup pauses with the full error shown and resumes where it stopped when the drive is back. If a file is corrupt or too big for FAT32, it's retried once, then skipped with its reason listed — it never stalls the whole backup. The free version backs up manually, up to 5 GB per backup run, with no ads, no account, and no cloud. SnapDisk Pro is a one-time $9.99 purchase (no subscription) that starts the backup automatically when you plug in a disk and removes the size limit. The app has no internet permission, so your photos physically cannot leave your device.

And the check that matters for this article: after the run, open a JXL back from the drive in Chrome 155 or later and look at it — watch it open, and check the picture is the one you saved. A green backup that copied the whole library has still copied zero JXLs if the index never held them — which is exactly what happens when the scanner did not index the .jxl files. Open the drive and look for the JXLs by extension: the default run mirrors the source tree, so the files should be there as .jxl files, in Downloads or the Pictures folder. If they are missing, the hunt is the suspect, not the run — find the .jxl files first, then copy them by hand in Method 2. SnapDisk copies, it never deletes — the only files it ever deletes are its own half-finished .part files — so deleting the originals after the check is always your step, never the app's.

Method 2: Copy the .jxl files by hand in the Files app — the From picker skips them

If the default run did not carry your JXLs — or if you would rather copy just the JXLs and nothing else — copy them by hand in the file manager. Plug the USB drive into the phone, open Files by Google or your phone's file manager, browse to the folder that holds the .jxl files — Downloads first, then Pictures, then the folder the transfer used, using the check order in the folder section above — long-press one .jxl file, tap the rest, tap Copy, navigate to the USB drive, and tap Paste. Check the drive afterwards: open a few .jxl files on the drive or on your computer, and confirm the sizes match the phone. This route has one advantage no SnapDisk route has for JXL: you see exactly which files you selected, and a .jxl file you selected is a .jxl file that copies — there is no index between you and the file, and no extension list to pass.

The honest limit on this route is that it is the manual route, and it gives up everything SnapDisk automates — and this article says so rather than pretending otherwise. There is no oldest-first order — you copy in whatever order you selected. There is no progress notification with speed and time left, no Pause and Stop, and no resume: if the drive is unplugged mid-copy, you start that file again and work out yourself which files already arrived. There is no per-file size verification, and no skipped-file list — a file that does not fit, or a copy that silently stops, fails quietly. For a hundred JXLs that is fine. For a thousand, try the default run in Method 1 first, and fall back to the manual copy for the JXLs it missed. And one more scope fact for this route: the manual copy is also the fallback for the files no SnapDisk route recognises — and for JXL, that is every .jxl file the picker would have taken, because the picker takes none of them.

One JXL-specific reason Method 2 matters more here than in the other format articles: the split between the indexed JXLs and the rest. The default run reads the media index, and it reads both the images table and the videos table, so it covers the Downloads and Pictures JXLs the index holds together with no step beyond the hunt. The manual copy does not need the index at all: it copies the files you select, so it reaches the JXLs the default run cannot see — the ones the scanner never indexed — and it reaches them one selection at a time. That makes the manual copy the route for the JXLs the index missed, and the default run the route for everything else. The default path queries both MediaStore tables with no extension filter, while the picker path walks one folder tree and keeps only the extensions in its list — and the split is the scanner's own indexing, which this article cannot promise for your phone. The manual copy itself is the route that needs no promise: select the .jxl files, copy them, check them. If the picker ever learns .jxl — a one-line change to the app's extension list — the picker route becomes the certain route for JXLs the way it already is for HEIC and WebP. Until then, do not point the picker at a folder of JXLs and expect them to copy.

Method 3: The JXLs that are not files — converted libraries, and the ones the apps made

Converted libraries, chat documents, and the web page itself are the three places JXLs are made most and saved least, and they are worth untangling carefully, because each one fails in a different way — and each failure looks like a backup problem when it is really a file problem. Converted libraries are the first, and they are the one with a route that works if you follow the file: a photo library converted to JXL — a decade of JPEGs run through cjxl, the reference converter, which recompresses each JPEG losslessly about 20 percent smaller and keeps the data to rebuild the original exactly — is a folder of .jxl files, and the conversion is usually done on a computer, not on the phone. The photo app Immich added JXL support in version 3.4.0 in November 2026, and that was the signal for its users to start converting — so the JXLs that matter most to a photo keeper are often sitting on a computer or a home server, not on the phone at all. Copy that folder to the phone first — over USB, or through a shared folder — and then it is a folder of .jxl files like any other, and Methods 1 and 2 cover it. But the same route split applies to it as to every other JXL: the default run copies it only if the index holds it, and the picker skips it, because it ends in .jxl. And one honest limit on the check: a converted JXL's lossless JPEG data can only be proven by rebuilding the JPEG from it with the djxl tool, so check the file by its size and extension on the drive, and rebuild one JPEG on a computer before you delete the originals.

Chat documents are the second, and they are the newest of the three: a JXL sent as a file, rather than as a chat image, is a different thing again — WhatsApp lets you send files as documents, and a JXL sent that way is sent as-is, without conversion, and it lands in Downloads or the app's folder as a .jxl. That is the one chat route that preserves the JXL, and it is the route to ask for when someone sends you a JXL you want to keep: ask them to send it as a document, not as a picture in the chat. The same shape holds on Telegram: a JXL sent as a file lands as a file, while a JXL sent as a photo can be re-encoded as a JPEG. If a JXL you are missing was sent as a chat picture, ask the sender to re-send it as a document.

The web page itself is the third, and it is the quietest of the three: a picture you pick from the keyboard's search — the image button in Gboard or in the chat app's own search — is served from a content library and never touches your storage, and a JXL you only viewed on a web page was never a file either. The guides state it in the same breath as the download folder: a picture from the keyboard's search loads from a library, has no file size issue, and leaves no file behind. So a picture you sent from the keyboard was never yours to back up in the first place: it is a library entry you borrowed for one message, and the copy of it that matters — if any — is the one in the chat history, which the chat app holds and which no backup in this article touches. The fix is the same as the other two: if a picture matters enough to keep, find it at its source — search the image site for it, download it from the web page in Chrome 155 or later, save it to Downloads as a .jxl — and then it is a file like any other, and Method 1 covers it. And the same warning holds for a picture you only viewed in a chat: a chat picture is a file only once you save it, and the save is the step — long-press, save, check Downloads — not the backup. One more JXL-specific note: email and social media do not accept JXL yet, so a JXL you try to share that way will be converted or refused — send it as a file through a messenger's document route instead.

Can SnapDisk read the JXL folders directly?

This is the question the whole article turns on, and it deserves a straight answer in three parts — what the code proves it can do, what is untested, and what would prove the rest. The first part is proven, from the code at the current base and from how Android's media index works — and it is the same shape as the AVIF case, with one JXL-specific condition that runs further the other way. SnapDisk's default run reads the phone's media index — it queries the MediaStore images and videos tables, oldest-first by date taken, with no folder filter. A saved .jxl file is an ordinary file the query would return — the query call passes no selection at all, so it asks for everything in the Images table, and a .jxl the table holds is returned the same way a JPEG is. The app's recognised image extensions do not matter to this route at all: the extension list gates only the picker route, and the MediaStore route has no extension filter. The query is in PhotoQuery.kt, and the default run copies the whole library, not DCIM only — so the JXLs in Downloads are covered the same way DCIM is, when the index holds them. That is the code's query shape, stated as such.

The condition is whether the index holds the .jxl at all, and it is the part that makes JXL different from every other format in this series: the default run's coverage is conditional on the JXLs having been indexed, and whether a given phone's media scanner indexes .jxl files is not settled by the public Android sources — and the evidence leans further against it than it did for AVIF. The chain is short enough to state exactly. The scanner resolves a file's MIME type from its extension — the current MediaProvider code calls the system's MIME map with the extension, and if the map returns nothing the file is treated as an unknown type, not an image. Android's own developer documentation states that each MediaStore collection is organised by the primary MIME type of the content, and that image/* content is indexed under Images — and a JXL's MIME type is image/jxl, so a .jxl the scanner typed as image/jxl is indexed under Images exactly the way a JPEG is. But the step in the middle — the map itself — is where the proof runs out, and the surrounding evidence points the other way. Android's own supported-media-formats document lists no JXL row at all: BMP, GIF, JPEG, PNG, WebP, HEIF, and AVIF with Android 14 are all listed, and JXL is absent — the operating system cannot decode the format, so the scanner has no reason to know it. The old extension table in MediaFile is a deprecated no-op stub in current Android, the live MIME map is supplied by the framework at startup and is not visible in any public source this article could read, and the Debian MIME table the framework's map is drawn from did gain an image/jxl entry years ago — but the Android copy of that table was only updated in a commit that, by its own message, affects future versions of Android. So this article does not claim the index holds your JXLs, and it does not claim it does not: it says the default run covers a .jxl on a phone whose scanner indexed it, and copies zero of them on a phone whose scanner did not, and the check after the run — open the drive, look for the .jxl files — is the step that tells you which phone you have. This article states the condition in the TL;DR, in the wall section, in Method 1 step 5, and here — because a guide that promised the default run covers every JXL, without the condition, would be wrong on exactly the phones where the JXLs are the pictures that matter. The second condition is the share trap: a JXL that was re-shared into a JPEG is a JPEG in the index too, and the default run copies it faithfully — the copy is correct, and the file was already wrong.

The second part is the picker, and for JXL it is not untested — it is proven, and proven in the other direction. The From folder picker walks one folder tree directly — PhotoQuery.kt, listTreeFiles and walkTree — and keeps only the files whose names end in a recognised extension — isMediaName, the IMAGE_EXTENSIONS list. That list holds .jpg, .jpeg, .png, .heic, .heif, .webp, .gif, .bmp, .dng, .raw and .avif, and no .jxl. So pointing the picker at Downloads copies every photo in the folder except the JXLs, and pointing it at Pictures copies every converted photo except the JXLs, and no test is needed to say so, because the list is the code and the code is the verdict. The fix is a one-line change to the app — adding .jxl to that list — and until it lands, the picker is not a route for JXLs at all, and this article does not present it as one. The manual copy in Method 2 is the route that needs no list and no index: select the .jxl files, copy them, check them. The third part is what the code does prove about the rest of the job, so the limits above are not mistaken for a wider doubt. The manifest requests the media-read permissions (READ_MEDIA_IMAGES and READ_MEDIA_VIDEO, plus the older READ_EXTERNAL_STORAGE capped at Android 12), the notification permission, and foreground-service permissions — and no INTERNET permission at all, zero occurrences, so the photos physically cannot leave the device. It does not request all-files access — no MANAGE_EXTERNAL_STORAGE anywhere — which is the permission a file manager uses to browse another app's folders freely; the folder picker is the route instead, and it needs your tap. The backup itself is the verified core: oldest-first by date taken with a date-modified fallback (PhotoQuery.kt), every file size-verified after copying (BackupEngine.kt), Pause and Stop in the notification (BackupService.kt, NotificationHelper.kt), files of 4 GB or more on a FAT32 drive skipped with their reason instead of stalling the job (BackupService.kt), and the free run capped at 5 GB with Pro a one-time $9.99 purchase (ProPrefs.kt). On Android 15 and later a dataSync foreground service gets 6 hours in 24 hours, so a very long copy can be paused by Android itself, and opening the app resets the timer — the service pauses cleanly with a message, it does not fail. None of that changes the JXL verdict — it bounds it. The backup engine is proven; the index coverage for JXL is not yet proven, and the picker skip for JXL is proven.

JXLs you downloaded vs JXLs you converted

The route is the same for both, but the starting point is not, and it is worth saying which one you are saving before you start. JXLs you downloaded — the case this article is really about — are the ones the hunt governs: with the save they land in Downloads or Pictures, and without it they are not on the phone at all, and the methods above are written for them. JXLs you converted are different, because the conversion made them for its own use: a JXL converted from a JPEG is a .jxl file in Downloads or Pictures, in the open, and the same route split applies — the default run copies it only if the index holds it, the picker skips it, and the manual copy is the certain route. Back the downloaded ones up with the default run first and the manual copy for the ones it missed, and back the converted ones up the same way — the split does not care where the file came from. That matters because the converted JXLs are often the ones you care about most: a library you converted on purpose, in the format you chose for quality. The downloaded ones are files, and files can be backed up — but only by a route that takes .jxl files, and the picker is not one.

One related corner is worth a line, because JXL owners hit it and it looks like a shortcut that is not one: a JXL sent as a file, rather than as a chat image, is a different thing again — WhatsApp lets you send files as documents, and a JXL sent that way is sent as-is, without conversion, and it lands in Downloads or the app's folder as a .jxl. That is the one WhatsApp route that preserves the JXL, and it is the route to ask for when someone sends you a JXL you want to keep: ask them to send it as a document, not as a picture in the chat. The same shape holds on Telegram: a JXL sent as a file lands as a file, while a JXL sent as a photo can be re-encoded as a JPEG. If a JXL you are missing was sent as a chat picture, check Downloads for the file version first — and if the .jxl itself is what you want, ask the sender to re-send it as a document. And one more JXL-specific corner: a JXL made by lossless JPEG recompression — the one JXL that must stay a JXL, because it carries the reconstruction data that restores the original JPEG bit for bit — is the one JXL that must never be converted to JPEG for the sake of compatibility, because converting it throws the reconstruction data away with it, and converting it to WebP keeps the picture but not the reversibility. If your JXL relies on that lossless link back to the original, keep it as a .jxl and do not convert it; the JPEG versions the chat apps make already lost the link when they converted it, and no backup step brings it back.

Checking the drive after the copy

The check has two halves, and they have to happen in order: first that the hunt actually produced .jxl files on the phone, then that the drive holds them whole. After the SnapDisk run finishes, open the drive on a computer or on the phone itself and count: the drive should hold the JXLs you saved, in a Downloads folder of their own — the default run mirrors the source tree, so the files should be there by name and extension — and one opened at random should look right. Open a JXL itself — not just any photo on the drive — because a run that covered the rest of the library would still look complete on a random check while the one format you cared about was missing. Open it in a viewer that decodes JXL — Chrome 155 or later on the phone, Preview on a Mac, a Windows computer with the free JPEG XL image extension, or a browser viewer page that brings its own decoder — and look at it: it should open, it should show the picture, and on a screen that shows HDR it should show the bright range. If it opens and looks right, the copy is good: the HDR is a wide gamut stored inside the .jxl file and the transparency is an alpha channel inside the same file, and the lossless JPEG reconstruction data is inside the same file too, and a byte-for-byte copy carries all of them. If the count is short, the run is not the first suspect — the index is. Check Downloads: are the .jxl files actually there, and do they end in .jxl? If the folder holds no .jxl files, the JXLs were never saved — save them from the source and run again. If the files are in Downloads but not on the drive, the run is the suspect, and the manual copy in Method 2 is the fix, not a different folder. If the files are in the folder but the gallery shows a blank thumbnail, the decoder is the suspect — open the file in Chrome 155 or later — or the index is the suspect — restart the phone to force a rescan, and run again — or copy them by hand, which does not depend on the gallery or the index at all. And if the converted JXLs are the ones missing, the picker is the suspect, not the run: the picker never takes .jxl files, and the manual copy in Method 2 is the fix.

If the drive's free space ran out mid-run, the run stops with the full error shown; free space by moving the drive's contents to a bigger drive first, or back up to a second drive. If the run stopped at the 5 GB free cap — unlikely for a JXL collection alone, possible on a whole-library default run — run it again and it picks up where it stopped, because files already copied are never copied twice. If a JXL on the drive does not open, the copy is not the suspect — the viewer is. Check the phone's Chrome version: on Chrome 154 and earlier the browser cannot decode JXL at all, because the decoder only turned on by default in 155 — update Chrome and open the file there instead, and if it opens in the updated Chrome the file is fine and the old browser was the gap. If it opens nowhere, check the source file's extension: if it ends in .jpg, the picture was converted by a share step before you copied it. Find the original .jxl in Downloads or Pictures and copy that file instead. And the check that matters most for a JXL that only existed inside a chat: confirm the drive copy before you delete anything from the phone. The copy in Downloads is an ordinary file and will survive; the copy in the chat depends on the chat app keeping it, and a JXL that was served from a library is gone when the library stops serving it. The drive is a plain folder of plain files — anyone who picks it up can open them, and it is worth stating before the JXLs leave the phone.

What to avoid

  • Assuming a JXL you viewed is a .jxl file on your phone. It usually is not saved until you save it — a JXL you only viewed on a web page was never a file, and a picture you picked from the keyboard's search was served from a library and never touched your storage. A one-tap backup copies zero JXLs until the JXLs exist as .jxl files in Downloads or Pictures.
  • Assuming the default run covers your JXLs. It may not — the default run reads the media index, and whether the phone's media scanner indexes .jxl files is not settled by the public Android sources, and Android's own supported-formats document lists no JXL row at all. A green backup copies zero JXLs while the folders sit full of .jxl files, and nothing in the run tells you it happened. Check the drive for .jxl files after every run.
  • Assuming the From picker covers your JXLs. It cannot — proven from the code: the picker walks the folder and keeps only the extensions in the app's recognised list, and .jxl is not in that list. Pointing the picker at Downloads copies every photo in the folder except the JXLs. Copy them by hand in the Files app instead.
  • Assuming the gallery can check a JXL. It cannot — Android itself has no JXL decoder, so the gallery shows a blank thumbnail for a real .jxl file on every Android version. A blank thumbnail means the gallery lacks the codec, not that the file is bad. Open the file in Chrome 155 or later before you conclude anything.
  • Assuming your camera shoots JXL. It does not — no mainstream Android camera saves in JXL, and there is no JXL capture setting in any stock camera app. Do not hunt for JXLs in DCIM/Camera expecting the camera to have made them; the JXLs live in Downloads and Pictures, or in the folder a transfer put them in.
  • Assuming an old Chrome can show a JXL. It cannot — Chrome 154 and earlier show nothing for a .jxl file, because the decoder only turned on by default in version 155, on October 6, 2026. Update Chrome before you check a JXL on the phone, or check it on a computer instead.
  • Assuming the chat apps keep .jxl files. WhatsApp and Telegram keep pictures as chat images, and a picture sent as a chat image can be re-encoded as a JPEG before it ever reaches your storage — only a file sent as a document lands as a .jxl. A keyboard picture was served from a library and never touched your storage. The chat pictures live in the chat and reappear when you sign in; the files were never yours to keep.
  • Re-sharing a JXL to get it onto the drive. Sharing a JXL out of the Gallery or a chat can re-encode it as a JPEG and drop the HDR and the lossless JPEG data, or take only the still out of an animated JXL. Copy the saved .jxl file, never a re-shared copy; a converted copy never gets its quality back.
  • Renaming a file to change its format. Renaming photo.jxl to photo.jpg does not convert it — the JXL data stays inside a file called .jpg, and the next app that opens it by extension will fail or misread it. Convert with an image editor or a converter; never rename.
  • Assuming one folder holds every JXL. UNVERIFIED as a single path — the folder depends on where the JXL was saved: Downloads for a browser download, Pictures for a converter export, the transfer folder for a file moved from a computer. Check Downloads first, then Pictures, then the transfer folder — do not plan a backup around a single path.
  • Assuming the default run is test-proven for JXL. Untested — no SnapDisk test has run a JXL backup end to end on a real phone, and whether the index holds a .jxl at all is device-dependent. Do not plan a backup around it as the only route; Method 2's manual copy is the certain one.
  • Assuming a JXL you converted is the original. A JXL you made from a JPEG or a PNG is a smaller, compressed copy of it — except a JXL made by lossless JPEG recompression, which carries the data to rebuild the original JPEG bit for bit. Back the original up too — except a losslessly recompressed JXL, which is the original, smaller, and needs no JPEG beside it.
  • Assuming a screenshot is the JXL. It is not — a screenshot is a picture of the screen, a still image, usually a PNG or a JPEG, carrying the app chrome around it, and it lands in the Screenshots folder, not with the JXLs. It does not hold HDR and it has no lossless JPEG data. Save the JXL itself when the save works, and screenshot only when it does not.
  • Assuming screen-off continuation under battery saver. UNVERIFIED — the repo holds no wake lock and no battery-saver handling. Keep the phone awake for the run, or check it.
  • Using a FAT32 drive for a library with long videos. FAT32 cannot hold a single file over 4 GB, and a library with long 4K clips will hold one. SnapDisk skips those files and lists them — use exFAT.
  • Assuming the free 5 GB cap covers the whole library. It is per run. A library over 5 GB needs several free runs — run it again and it picks up where it stopped — or one $9.99 Pro purchase.
  • Unplugging mid-copy. Pulling a USB drive out while files are still writing can corrupt the file in flight. Wait for the copy to finish, or pause it first — SnapDisk's Stop button exists for exactly this. An unplug mid-copy leaves a half-copied library that looks finished until you count it.
  • Checking the drive by opening any photo. Open a JXL back from the drive and look at it — check it opens in Chrome 155 or later, and check it is the picture you saved — not just any photo. A random check passes even when the one format you cared about was never copied, because the photos that did copy render fine.
  • Checking a JXL in the gallery. The gallery cannot decode JXL on any Android version — the operating system has no JXL decoder. A blank thumbnail there means the gallery lacks the codec, not the file is bad. Open the file in Chrome 155 or later, which has decoded JXL since October 6, 2026, before you conclude anything.

Rule of thumb: Find the .jxl file first, then back it up — the JXLs you viewed on the web are in Downloads, the converted ones are in Downloads or Pictures, and the HDR and the lossless JPEG data live inside the file, so the saved .jxl is the only copy that still holds them — and the From picker skips .jxl files, so copy them by hand if the default run did not carry them.
