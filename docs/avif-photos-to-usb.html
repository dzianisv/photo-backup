Save AVIF photos to a USB drive from Android

An AVIF is an ordinary .avif file — smaller than a JPEG, with HDR and transparency inside. The job is getting the file onto the drive, because the two backup routes disagree about it.

November 25, 2026 · 14 min read

TL;DR: An AVIF is an ordinary .avif file, and everything that makes it worth keeping lives inside the file itself — the smaller size, the HDR, the 10-bit colour, the transparency, and, for an animated AVIF, the frames stored one after another, no playback note, no sidecar file, nothing like the slow-motion case where the speed lives in a note attached to the video. That is the good news, and it makes the backup simple once you have the file: copy the .avif and all of it comes with it, byte-for-byte, because there is nothing to lose in the copy. The trap is the route, and it is a trap with two jaws that bite in opposite directions. The first jaw is the default run: SnapDisk's default backup reads the phone's media index with no extension filter, so a .avif the index holds copies like any other photo — but whether the index holds a .avif at all is not settled by the code or by the public Android sources, so the default run covers your AVIFs on a phone whose scanner indexed them and copies zero of them on a phone whose scanner did not, and nothing in the run tells you which phone you have. The second jaw is the From picker, and it is certain in the other direction: the picker walks a folder and keeps only the extensions in the app's recognised list, and .avif is not in that list — so pointing the picker at Downloads copies every photo in the folder except the AVIFs. The certain route for a .avif you can see in Downloads, Pictures, or DCIM/Camera is the file manager's manual copy, in Method 2 — and the default run is the try-first route, because it costs nothing to try and it covers the indexed AVIFs with no step beyond the hunt. The check is opening one AVIF back from the drive and watching it open — on Android 12 or later in the gallery, on an older phone in Chrome, which has shown AVIF since version 89 — because an AVIF that lost its HDR or its transparency still looks like a photo in every other check. And screen-off continuation under battery saver is unverified — the repo holds no wake lock and no battery-saver handling — so keep the phone awake for the run or check it. As of November 25, 2026, no top search result offers a dedicated AVIF-to-USB how-to: the results are generic OTG copy guides that never name AVIF at all.

The wall: the AVIFs you see are files you never chose — and the two backup routes disagree about them

Start with the fact that decides the whole job, because the AVIF wall is easy to misread in both directions at once. It is not a locked door like Threema's wall: the photos exist and the app will not let them out until you save them. And it is not a hall of mirrors like the GIF wall: the GIFs are everywhere on your screen and almost none of them is a file. The AVIF wall is a filing error with a second fault underneath it. The files exist, the phone can open them on Android 12 or later, the backup can copy them — and they sit in folders nobody thinks to look in, under a name nobody recognises, because AVIF arrived quietly. It is the web's newest default image format: smaller than a JPEG at the same quality — roughly half the size, by the format's own numbers — with HDR and 10-bit colour and transparency in the same file, and able to animate like a GIF. Android has decoded it since version 12, and Chrome has shown it since version 89, so a phone can hold hundreds of AVIF files — downloaded images, converted photos, camera shots from a recent phone — and the owner has never once seen the extension, because the gallery shows the picture and never the filename.

That is the wall, and it is a total one in the same way the messaging-app walls are, but with the blame in a different place and a second fault underneath. A phone full of AVIFs that were never hunted down is a phone full of files the backup copies only by accident: the default run copies the ones the media index knows about — the Downloads saves, the Pictures exports, the camera shots — and misses the ones it does not, because whether the phone's media scanner indexes .avif files at all is not settled. The difference from WebP is what the picker does about it. For WebP, the picker was the certain route: the folder walk keeps .webp files, so pointing it at the folder reached the files the index missed. For AVIF, the picker is not a route at all: the folder walk keeps only the extensions in the app's recognised list, and .avif is not in that list — so the picker copies every photo in the folder except the AVIFs, and a backup that ran the picker route looks complete while the one format you cared about was never copied. There is no single save step to turn on, and no single folder to point at, and the one tool that usually rescues a format the index missed does not rescue this one. The job is a hunt first and a copy second, and the hunt is the part this article does that the generic guides do not — and the copy, for AVIF, is the file manager's manual copy, not the picker.

Two scope facts, because they decide what this article can and cannot promise. First, the file itself is simple in a way that should reassure you once you have it: an AVIF is an ordinary file with everything stored inside it — the smaller size is the compression, the HDR is 10-bit colour and a wide gamut in the file, the transparency is an alpha channel in the file, and the animation, for an animated AVIF, is a sequence of frames, exactly like a GIF. Copy the .avif and you copy all of it — every frame, the HDR, the transparency, at the original quality — because the copy is byte-for-byte and the bytes are the picture. There is no conversion step to get wrong and no quality setting to choose, and SnapDisk never converts anything in any case. Second, the format confusion is real and worth naming plainly: an AVIF is not a JPEG with a different name, and renaming a file does not convert it. A file called photo.avif holds AVIF data; renaming it to photo.jpg leaves AVIF data inside a file called .jpg, and the next app that opens it by extension will fail or misread it. The guides that measured this say it outright: keep the extension the site supplied unless you intentionally convert the file with an image editor. This article is about the .avif files; a file that was renamed is a different problem, and the fix is converting it properly, not renaming it back.

And a word on whose AVIFs these are, because AVIFs are usually someone else's picture — a photo from a site, a shot someone sent you, a frame clipped from a show — and because the line between saving and re-posting is worth stating plainly. The AVIFs this article covers are the ones you downloaded or were sent for yourself: an image you saved from a web page, a photo a friend sent you in a chat that you want to keep. Saving them to your own drive for your own records is the job. They are also someone else's work in a plain sense: a photograph with a photographer, a picture with an author you will never meet. Saving a file does not grant permission to reuse it — so re-posting an AVIF as if it were yours, or using someone's picture in your own content without asking, is a different act, and the same courtesy applies here as anywhere: the person who made it is the person to ask before the AVIF leaves your phone for anywhere else. This article's methods copy the file to your drive; what you do with it afterwards is yours to decide, and asking is the honest step before anything leaves your phone. Only save AVIFs you have permission to keep — and this article makes no claim about recovering AVIFs from a chat you have already deleted, because the chat apps keep no .avif file to recover once the chat is gone, and an AVIF that was served from a library was never yours to recover in the first place.

Where .avif files live on an Android phone — Downloads, Pictures, and the camera roll

This section exists because the folder is the one fact the guides do not answer at all — and because AVIFs, unlike the messaging-app photos in this series, have no single home folder. A Threema photo lands in Pictures/Threema; a WhatsApp photo lands in WhatsApp Images. An AVIF lands wherever the thing that made it put it, and the phone has three different makers. So this article does not state one path as the path for every AVIF. It gives the check order instead, and the check order is the same on every phone — and the check itself is the file extension, not the app that showed it to you. A file that ends in .avif is an AVIF; a file that ends in .jpg is a JPEG, even if it looks identical on screen.

Check Downloads first. Open your file manager, go to Internal Storage, then Download — or open Files by Google and tap Downloads. This is where an AVIF downloaded from a browser lands: Chrome on Android saves every download to the shared Downloads folder by default, at Internal Storage/Download, and the guides agree on the path across manufacturers. An AVIF you long-pressed on a web page and saved, an AVIF you downloaded from a converter site, an AVIF someone sent you as a file attachment that your app saved to Downloads — all of them land here, as .avif files with their HDR and transparency intact. Most of the images on the modern web are served as AVIF or WebP now, so an image you save from a site is a .avif or a .webp far more often than a .jpg — and the save keeps the site's format, so the file you get is the format the site sent. Chrome saves the exact bytes the server sent: the browser tells the site it can display AVIF, the site replies with AVIF, and the long-press save writes those bytes to disk — there is no Chrome setting that changes that, and no step in the middle where Chrome re-encodes the picture into something else. If you have ever saved an image from the web on purpose, it is almost certainly here, and this is the folder to check first because it is the only folder a deliberate AVIF save reliably produces.

Check Pictures second, and the camera roll third — and understand that the third check is the one the other format articles do not have. Pictures is where an AVIF saved from an app that writes to the shared Pictures directory lands, and where a converted photo exported by an editing app usually goes, and it is worth a look when Downloads comes up empty. Then check DCIM/Camera — Internal Storage, DCIM, Camera — for the camera shots: a few recent phones save camera photos as AVIF now that Android 14 made AVIF encoding part of the platform, and the encoder is mandatory from Android 14 for the format's baseline profile, so a phone that saves in AVIF is a recent one, and the files land in the camera roll with the JPEGs. If your phone saves in AVIF, the setting is in the camera app — look for a high-efficiency or format option — and the files it makes are .avif files in DCIM/Camera, exactly where the JPEGs used to be. Then check for the Motion Photos: a Motion Photo whose primary image is AVIF ends in .avif — the filename pattern is a name ending in MP, then .avif — and it sits in DCIM/Camera with the short video appended inside the same file, so the .avif you find there is both a still and a clip at once. If the file is in none of those places, check that the save actually happened: an AVIF you only viewed on a web page was never saved, a sticker you picked from the keyboard's search was served from a library and never touched your storage, and a picture you only saw inside a chat was never a file. The hunt ends where the file begins — and for an AVIF that was never a file, the hunt ends with making one: save the image from the web page, or export it from the app that made it, and then it is a file like any other.

One more scope fact for this section, because it decides what the drive copy holds: the saved .avif is the AVIF as it was when you saved it, and the phone gives you no way to improve it afterwards. An AVIF is already the small version — that is the point of the format, roughly half a JPEG at the same quality — so an AVIF saved from the web is already a compressed copy of whatever the site had, and copying it byte-for-byte keeps it exactly that good and exactly that bad. SnapDisk copies the saved file with no conversion and no quality change — but it cannot recover detail the AVIF compression already removed, and it cannot upgrade an AVIF someone sent compressed. If the picture you want is a photo you still have as a JPEG in your camera roll, the JPEG is the one worth keeping alongside it: the AVIF is a smaller copy the web made for loading fast, and the original is the one with the full detail. The AVIF route for a photo you still have as a JPEG is only needed when you want the file as an AVIF — for a website, for the one place that only renders AVIF. And the AVIFs you converted yourself in the browser are a separate case again: they were made from a JPEG or a PNG, and the original is usually still in your camera roll in DCIM/Camera — back that up too, because the AVIF is a small copy of a moment the original holds in full.

What you need

An Android phone — Android 7.0 or later, which is SnapDisk's minimum version — with the apps that hold your AVIFs already on it, plus one USB drive your phone can read: a USB-C flash drive, or a regular USB drive with a USB-C OTG adapter. SnapDisk itself is installed from the v0.1.2 APK — it is not on Google Play yet — so install it by allowing "install unknown apps" for the browser or Files app you download it with, which is standard Android. You need nothing else for the main route: no extra app, no account. The hunt step is inside the apps you already have — the browser's Downloads, the Gallery, the file manager — and the backup is SnapDisk's default run, or the file manager's manual copy in Method 2. One version note that matters for AVIF and for no other format in this series: the phone that holds the AVIFs does not need to decode them to copy them — a copy moves bytes, and bytes do not care about the format — but the phone you check them on does need to decode them. Android 12 and later decode AVIF system-wide, so the gallery shows them; on Android 11 and earlier the gallery cannot, and the check has to happen in Chrome, which has shown AVIF since version 89. If your phone runs Android 11 or earlier and the gallery shows a blank thumbnail for a .avif file, the file is probably fine and the gallery is old — open it in Chrome before you conclude anything. Check the drive's space first: AVIFs are small — an AVIF is roughly half the JPEG it replaces, a web-saved AVIF usually well under a megabyte — so space is almost never the problem here, but look anyway, because a whole-library default run copies everything, not just AVIFs. One format note: drives formatted FAT32 cannot hold a single file over 4 GB. That only matters for very long videos — SnapDisk skips those files and lists them instead of failing the whole backup. A drive formatted exFAT has no such limit, and exFAT is the format to use for a photo drive.

Before any method, settle the one question that decides whether the phone route works at all: does your phone see the USB drive? Plug the drive in and open Settings > Connected devices or Settings > Storage — the drive should appear there. That check is the test, and it takes ten seconds. If the drive does not appear, try a different adapter first — cheap OTG adapters are the usual failure — then a different drive, and a powered hub if the drive is a spinning hard drive rather than a flash drive. And one warning up front, because it applies to every route below: do not delete anything from the phone until the USB copy is done and verified. The AVIFs in Downloads are yours — but until the drive copy is checked, Downloads is the only copy outside the browser, and deleting from Downloads before the check is how an AVIF ends up nowhere at all. And do not delete the chat app, or clear its data, until the save and the copy are both done: a picture that was never copied as a file is gone when the chat is gone, and the web does not keep a second copy of an image it served you once.

Method 1: Find the saved .avif, then back up with SnapDisk

This is the route to try first, because it is the only one that joins the whole job — the .avif file, found on the phone, onto a USB drive plugged into the phone, no computer — using only the apps already on the phone plus SnapDisk. It has two halves, and they have to happen in order: the hunt, which finds the .avif files, and the SnapDisk copy, which puts them on the drive. The first half is the work, and with AVIFs it is a hunt across folders rather than a single save step, because there is no switch to turn on and no single folder to open. Skipping the first half is the mistake this article exists to prevent: running SnapDisk's default backup without knowing where the AVIFs are copies every photo in the gallery — and possibly zero AVIFs, because the default run only sees the AVIFs the media index holds, and the index may hold none of them.

  1. Hunt the .avif files first, in check order. Open your file manager and go to Internal Storage, Download — the browser-downloaded AVIFs live here, as .avif files. Then check Pictures for AVIFs saved from apps that write there. Then open DCIM/Camera and look for .avif files among the JPEGs — a recent phone that saves in AVIF puts them there, and a Motion Photo with an AVIF primary ends in .avif with MP in the name. The check at each stop is the file extension: a file that ends in .avif is an AVIF, and a file that ends in .jpg is a JPEG, even if it looks identical on screen. If a folder holds no .avif files, move on — do not assume the AVIFs are there because the folder's name sounds right. If you find AVIFs in more than one folder, note all of them: the default run covers the indexed ones all at once, and the manual copy in Method 2 needs one selection per folder.
  2. If the hunt comes up empty, make the file before you back it up. An AVIF you only viewed on a web page was never a file, and a sticker you picked from the keyboard's search was served from a library — neither is on the phone, and no step in this article conjures a file out of a viewed picture. The fix is at the source: long-press the image in the browser and save it, and it lands in Downloads as a .avif — or export it from the app that made it, and it lands in Downloads or Pictures as a .avif. An AVIF sent to you as a file attachment, rather than as a chat image, is already a file: save the attachment, and it lands in Downloads or the app's folder as a .avif. Do not try to rescue a chat picture by sharing it to yourself: the share step can convert an AVIF to a JPEG, or hand on a still instead of the file, and a shared copy is the least reliable AVIF on the phone.
  3. Do not re-share an AVIF to get it onto the drive. This is the trap the whole article is built around, and it deserves its own step because it looks like the obvious shortcut. Sharing an AVIF out of the Gallery or a chat into another app — into a file manager, into a different chat, into yourself — can change it on the way: some share targets re-encode the file as a JPEG, dropping the HDR and the transparency with it, and some take only the still out of a Motion Photo and hand on a JPEG instead of the .avif. A converted copy is a JPEG wearing an AVIF's name, and no backup step after it restores the HDR or the transparency, because both were lost in the share, not in the copy. The certain route copies the saved .avif file, never a re-shared copy — and if the only copy you have is a re-shared one, go back to step 2 and save the AVIF from its source instead.
  4. Check the files are in Downloads, Pictures, or DCIM/Camera. Open your file manager, go to Downloads, and look for .avif files — if they are there, the save works. Then check Pictures, then DCIM/Camera — if the .avif files are there, the camera saves in AVIF, and this is also the check that proves the manual copy in Method 2 can reach them, because the file manager and the copy read the same folders. If the files are in the folder but not in the gallery, that is expected on an older phone — the gallery on Android 11 and earlier cannot decode AVIF, so the files sit in the folder invisible to the gallery — and it is not a problem for the copy, which moves bytes and does not decode anything. If no folder holds a .avif at all, the save is the suspect: an AVIF you viewed was never saved, and step 2 is the fix — save it from the web page or export it from the app.
  5. Plug in the drive and run SnapDisk. Plug the USB drive into the phone. SnapDisk offers the backup in a notification — tap Backup — or open the app and tap Start. The run copies oldest-first, verifies every file by size after copying, and shows progress with Pause and Stop in the notification. The free run covers up to 5 GB, and AVIFs are small, so one run is almost always enough for the AVIF half — though a whole-library run copies everything else too, and that is the point: the AVIFs the index holds come along with the rest, with no folder to pick and no step to remember. Screen-off continuation under battery saver is unverified — the repo holds no wake lock and no battery-saver handling — so keep the phone awake for the run or check it. And the check after this step is the whole job for AVIF: open the drive and look for the .avif files by extension. If they are not there, the run is not the first suspect — the index is. Go to Method 2 and copy them by hand.
  6. Do not plan around the AVIFs you never saved. An AVIF you only viewed on a web page is still on the web page, and no step in this article changes that: there is no save-all for a page's images, and there is no export that writes a page's AVIFs out as files. If an AVIF matters, save it from its source now, while the page is still up — an AVIF that was served from a site is gone when the site stops serving it. A screenshot is the only copy left for an AVIF the built-in save will not give you — and a screenshot is a picture of the screen, not the AVIF: it is a still image, usually a PNG or a JPEG, it carries the app chrome around it, it lands in the Screenshots folder, not with the AVIFs, and it does not hold HDR and has no transparency to keep. Do not plan a backup around saving what the apps will not let you save as a file.

Two honest limits. First, the hunt is not retroactive in the other direction either: finding AVIFs today does not put the AVIFs from a chat you already deleted onto the phone — a deleted chat is gone, and the web keeps no second copy of an image it served you once. That is step 2's job, and it is a manual job: one save per AVIF. Second, the 5 GB free cap is per run — an AVIF collection will never reach it, but a whole-library default run might, and running it again picks up where it stopped, because files already copied are never copied twice. Third, SnapDisk copies, it never deletes: deleting the AVIFs from the phone after the check is always your step, never the app's — and deleting them from the chat is the chat app's, not SnapDisk's, and it does not free the drive copy. The drive copy is the backup; the phone copy is the original until you decide otherwise.

Copying only some AVIFs? If you would rather copy just a few AVIFs than the whole collection, the From folder picker still takes a folder, not single files — and for AVIF it takes nothing at all, because .avif is not in the recognised list — so copy the ones you want in the file manager instead: select the .avif files, tap Copy, navigate to the USB drive, and tap Paste. That is Method 2, and for AVIF it is the certain route, not the fallback. If the drive is unplugged mid-copy, the SnapDisk backup pauses with the full error shown and resumes where it stopped when the drive is back. If a file is corrupt or too big for FAT32, it's retried once, then skipped with its reason listed — it never stalls the whole backup. The free version backs up manually, up to 5 GB per backup run, with no ads, no account, and no cloud. SnapDisk Pro is a one-time $9.99 purchase (no subscription) that starts the backup automatically when you plug in a disk and removes the size limit. The app has no internet permission, so your photos physically cannot leave your device.

And the check that matters for this article: after the run, open an AVIF back from the drive and look at it — watch it open, and check the picture is the one you saved. A green backup that copied the whole library has still copied zero AVIFs if the index never held them — which is exactly what happens when the scanner did not index the .avif files. Open the drive and look for the AVIFs by extension: the default run mirrors the source tree, so the files should be there as .avif files, in Downloads or the Pictures folder or DCIM/Camera. If they are missing, the hunt is the suspect, not the run — find the .avif files first, then copy them by hand in Method 2. SnapDisk copies, it never deletes — the only files it ever deletes are its own half-finished .part files — so deleting the originals after the check is always your step, never the app's.

Method 2: Copy the .avif files by hand in the Files app — the From picker skips them

If the default run did not carry your AVIFs — or if you would rather copy just the AVIFs and nothing else — copy them by hand in the file manager. Plug the USB drive into the phone, open Files by Google or your phone's file manager, browse to the folder that holds the .avif files — Downloads first, then Pictures, then DCIM/Camera, using the check order in the folder section above — long-press one .avif file, tap the rest, tap Copy, navigate to the USB drive, and tap Paste. Check the drive afterwards: open a few .avif files on the drive or on your computer, and confirm the sizes match the phone. This route has one advantage no SnapDisk route has for AVIF: you see exactly which files you selected, and a .avif file you selected is a .avif file that copies — there is no index between you and the file, and no extension list to pass.

The honest limit on this route is that it is the manual route, and it gives up everything SnapDisk automates — and this article says so rather than pretending otherwise. There is no oldest-first order — you copy in whatever order you selected. There is no progress notification with speed and time left, no Pause and Stop, and no resume: if the drive is unplugged mid-copy, you start that file again and work out yourself which files already arrived. There is no per-file size verification, and no skipped-file list — a file that does not fit, or a copy that silently stops, fails quietly. For a hundred AVIFs that is fine. For a thousand, the manual route is an afternoon of tapping and checking, and the default run in Method 1 is the honest recommendation — try it first, and fall back to the manual copy for the AVIFs it missed. And one more scope fact for this route: the manual copy is also the fallback for the files no SnapDisk route recognises — and for AVIF, that is every .avif file the picker would have taken, because the picker takes none of them.

One AVIF-specific reason Method 2 matters more here than in the other format articles: the split between the indexed AVIFs and the rest. The default run reads the media index, and it reads both the images table and the videos table, so it covers the Downloads and Pictures AVIFs the index holds together with no step beyond the hunt. The manual copy does not need the index at all: it copies the files you select, so it reaches the AVIFs the default run cannot see — the ones the scanner never indexed — and it reaches them one selection at a time. That makes the manual copy the route for the AVIFs the index missed, and the default run the route for everything else. This is a code-grounded difference, not a guess: the default path queries both MediaStore tables with no extension filter, while the picker path walks one folder tree and keeps only the extensions in its list — and the split is the scanner's own indexing, which this article cannot promise for your phone. The manual copy itself is the route that needs no promise: select the .avif files, copy them, check them. If the picker ever learns .avif — a one-line change to the app's extension list — the picker route becomes the certain route for AVIFs the way it already is for HEIC and WebP. Until then, do not point the picker at a folder of AVIFs and expect them to copy.

Method 3: The AVIFs that are not files — Motion Photos, and the ones the apps made

Motion Photos, camera saves, and the keyboard are the three places AVIFs are made most and saved least, and they are worth untangling carefully, because each one fails in a different way — and each failure looks like a backup problem when it is really a file problem. Motion Photos are the first, and they are the one with a route that works if you read the filename: a Motion Photo is a single file that holds a still photographic image and a short video, with the video appended to the still, and Google's own format document says the primary still can be a JPEG, a HEIC, or an AVIF — so a Motion Photo with an AVIF primary is a file ending in .avif, with MP in the name, sitting in DCIM/Camera. Copy that .avif byte-for-byte and both parts come with it, because the video lives inside the file after the still — but the same route split applies to it as to every other AVIF: the default run copies it only if the index holds it, and the picker skips it, because it ends in .avif. And one honest limit on the check: opening a Motion Photo .avif as a still shows the still, and the motion needs a viewer that knows the Motion Photo format — so check the file by its size and its extension on the drive, and play the motion back on the phone before you delete anything.

Camera saves are the second, and they are the newest of the three: a few recent phones save camera photos as AVIF now that Android 14 made AVIF encoding part of the platform — the encoder is mandatory from Android 14 for the format's baseline profile — so a phone that saves in AVIF is a recent one, and the setting that turns it on is in the camera app, wherever your phone puts its format option. The files it makes are .avif files in DCIM/Camera, exactly where the JPEGs used to be, and the same route split applies: the default run copies them only if the index holds them, the picker skips them, and the manual copy in Method 2 is the certain route. If your camera saves in AVIF and you want JPEGs instead, the fix is the camera setting, not the backup — change the format in the camera app, and the new shots are JPEGs; the AVIFs already on the phone stay AVIFs, and this article is about copying those, not converting them. And the same permission rule applies to all three routes: only save AVIFs you have permission to keep, and do not use a backup tool to pull someone else's picture out of a chat you were never meant to keep.

The keyboard is the third, and it is the quietest of the three: a picture you pick from the keyboard's search — the image button in Gboard or in the chat app's own search — is served from a content library and never touches your storage. The guides state it in the same breath as the download folder: a picture from the keyboard's search loads from a library, has no file size issue, and leaves no file behind. So a picture you sent from the keyboard was never yours to back up in the first place: it is a library entry you borrowed for one message, and the copy of it that matters — if any — is the one in the chat history, which the chat app holds and which no backup in this article touches. The fix is the same as the other two: if a keyboard picture matters enough to keep, find it at its source — search the image site for it, download it from the web page, save it to Downloads as a .avif — and then it is a file like any other, and Method 1 covers it. And the same warning holds for a picture you only viewed in a chat: a chat picture is a file only once you save it, and the save is the step — long-press, save, check Downloads — not the backup.

Can SnapDisk read the AVIF folders directly?

This is the question the whole article turns on, and it deserves a straight answer in three parts — what the code proves it can do, what is untested, and what would prove the rest. The first part is proven, from the code at the current base and from how Android's media index works — and it is the same shape as the HEIC case, with one AVIF-specific condition that runs the other way. SnapDisk's default run reads the phone's media index — it queries the MediaStore images and videos tables, oldest-first by date taken, with no folder filter. A saved .avif file is an ordinary file the query would return — the query call passes no selection at all, so it asks for everything in the Images table, and a .avif the table holds is returned the same way a JPEG is. The app's recognised image extensions do not matter to this route at all: the extension list gates only the picker route, and the MediaStore route has no extension filter. The query is in PhotoQuery.kt, the no-folder-filter shape is the code's own design, and the default run copies the whole library, not DCIM only — the query reads every indexed image and video on the phone, whatever folder it sits in, so the AVIFs in Downloads are covered the same way DCIM is, when the index holds them. That is not an assumption: it is the code's query shape, stated as such.

The condition is whether the index holds the .avif at all, and it is the part that makes AVIF different from every other format in this series: the default run's coverage is conditional on the AVIFs having been indexed, and whether a given phone's media scanner indexes .avif files is not settled by the public Android sources. The chain is short enough to state exactly. The scanner resolves a file's MIME type from its extension — the current MediaProvider code calls the system's MIME map with the extension, and if the map returns nothing the file is treated as an unknown type, not an image. Android's own developer documentation states that each MediaStore collection is organised by the primary MIME type of the content, and that image/* content is indexed under Images — and an AVIF's MIME type is image/avif, so a .avif the scanner typed as image/avif is indexed under Images exactly the way a JPEG is. But the step in the middle — the map itself — is where the proof runs out. The old extension table in MediaFile is a deprecated no-op stub in current Android, the live MIME map is supplied by the framework at startup and is not visible in any public source this article could read, and the format-code table lists HEIF but has no AVIF entry at all. So this article does not claim the index holds your AVIFs, and it does not claim it does not: it says the default run covers a .avif on a phone whose scanner indexed it, and copies zero of them on a phone whose scanner did not, and the check after the run — open the drive, look for the .avif files — is the step that tells you which phone you have. This article states the condition in the TL;DR, in the wall section, in Method 1 step 5, and here — because a guide that promised the default run covers every AVIF, without the condition, would be wrong on exactly the phones where the AVIFs are the pictures that matter. The second condition is the share trap: an AVIF that was re-shared into a JPEG is a JPEG in the index too, and the default run copies it faithfully — the copy is correct, and the file was already wrong.

The second part is the picker, and for AVIF it is not untested — it is proven, and proven in the other direction. The From folder picker walks one folder tree directly — PhotoQuery.kt, listTreeFiles and walkTree — and keeps only the files whose names end in a recognised extension — isMediaName, the IMAGE_EXTENSIONS list. That list holds .jpg, .jpeg, .png, .heic, .heif, .webp, .gif, .bmp, .dng and .raw, and no .avif. So pointing the picker at Downloads copies every photo in the folder except the AVIFs, and pointing it at DCIM/Camera copies every camera shot except the AVIFs, and no test is needed to say so, because the list is the code and the code is the verdict. The fix is a one-line change to the app — adding .avif to that list — and until it lands, the picker is not a route for AVIFs at all, and this article does not present it as one. The manual copy in Method 2 is the route that needs no list and no index: select the .avif files, copy them, check them. The third part is what the code does prove about the rest of the job, so the limits above are not mistaken for a wider doubt. The manifest requests the media-read permissions (READ_MEDIA_IMAGES and READ_MEDIA_VIDEO, plus the older READ_EXTERNAL_STORAGE capped at Android 12), the notification permission, and foreground-service permissions — and no INTERNET permission at all, zero occurrences, so the photos physically cannot leave the device. It does not request all-files access — no MANAGE_EXTERNAL_STORAGE anywhere — which is the permission a file manager uses to browse another app's folders freely, and the absence is the reason SnapDisk cannot simply walk into an app-private folder the way a file manager can; the folder picker is the route instead, and it needs your tap. The backup itself is the verified core: oldest-first by date taken with a date-modified fallback (PhotoQuery.kt), every file size-verified after copying (BackupEngine.kt), Pause and Stop in the notification (BackupService.kt, NotificationHelper.kt), files of 4 GB or more on a FAT32 drive skipped with their reason instead of stalling the job (BackupService.kt), and the free run capped at 5 GB with Pro a one-time $9.99 purchase (ProPrefs.kt). On Android 15 and later a dataSync foreground service gets 6 hours in 24 hours, so a very long copy can be paused by Android itself, and opening the app resets the timer — the service pauses cleanly with a message, it does not fail. None of that changes the AVIF verdict — it bounds it. The backup engine is proven; the index coverage for AVIF is not yet proven, and the picker skip for AVIF is proven.

AVIFs you downloaded vs AVIFs the camera made

The route is the same for both, but the starting point is not, and it is worth saying which one you are saving before you start. AVIFs you downloaded — the case this article is really about — are the ones the hunt governs: with the save they land in Downloads or Pictures, and without it they are not on the phone at all, and the methods above are written for them. AVIFs the camera made are different, because the camera made them for its own use: a camera shot saved as AVIF is a .avif file in DCIM/Camera, in the open, and the same route split applies — the default run copies it only if the index holds it, the picker skips it, and the manual copy is the certain route. Back the downloaded ones up with the default run first and the manual copy for the ones it missed, and back the camera ones up the same way — the split does not care where the file came from. That matters more than it sounds, because the camera AVIFs are often the AVIFs you care about most: a shot you took on purpose, in the format the phone chose for quality, the one picture nobody else has. The downloaded ones are files, and files can be backed up. The camera ones are files too, and files can be backed up — but only by a route that takes .avif files, and the picker is not one.

One related corner is worth a line, because AVIF owners hit it and it looks like a shortcut that is not one: an AVIF sent as a file, rather than as a chat image, is a different thing again — WhatsApp lets you send files as documents, and an AVIF sent that way is sent as-is, without conversion, and it lands in Downloads or the app's folder as a .avif. That is the one WhatsApp route that preserves the AVIF, and it is the route to ask for when someone sends you an AVIF you want to keep: ask them to send it as a document, not as a picture in the chat. The same shape holds on Telegram: an AVIF sent as a file lands as a file, while an AVIF sent as a photo can be re-encoded as a JPEG. If an AVIF you are missing was sent as a chat picture, check Downloads for the file version first — and if the .avif itself is what you want, ask the sender to re-send it as a document. And one more AVIF-specific corner: an AVIF with HDR — a bright sky, a sunlit window, the one shot where the range matters — is the one AVIF that must stay an AVIF, because converting it to JPEG throws the HDR away with it, and converting it to WebP keeps the picture but not the range. If your AVIF relies on HDR, keep it as a .avif and do not convert it; the JPEG versions the chat apps make already lost the HDR when they converted it, and no backup step brings it back.

Checking the drive after the copy

The check has two halves, and they have to happen in order: first that the hunt actually produced .avif files on the phone, then that the drive holds them whole. After the SnapDisk run finishes, open the drive on a computer or on the phone itself and count: the drive should hold the AVIFs you saved, in a Downloads folder of their own — the default run mirrors the source tree, so the files should be there by name and extension — and one opened at random should look right. Open an AVIF itself — not just any photo on the drive — because a run that covered the rest of the library would still look complete on a random check while the one format you cared about was missing. Open it in a viewer that decodes AVIF — a browser, the gallery app on Android 12 or later, or a file manager with a preview — and look at it: it should open, it should show the picture, and on a screen that shows HDR it should show the bright range. If it opens and looks right, the copy is good: the HDR is 10-bit colour and a wide gamut stored inside the .avif file and the transparency is an alpha channel inside the same file, and a byte-for-byte copy carries all of both. If the count is short, the run is not the first suspect — the index is. Check Downloads: are the .avif files actually there, and do they end in .avif? If the folder holds no .avif files, the AVIFs were never saved — save them from the source and run again. If the files are in Downloads but not on the drive, the run is the suspect, and the manual copy in Method 2 is the fix, not a different folder. If the files are in the folder but not in the gallery, the decoder is the suspect for the older phones — open the file in Chrome, which has shown AVIF since version 89 — or the index is the suspect for the newer ones — restart the phone to force a rescan, and run again — or copy them by hand, which does not depend on the gallery or the index at all. And if the camera AVIFs are the ones missing, the picker is the suspect, not the run: the picker never takes .avif files, and the manual copy in Method 2 is the fix.

If the drive's free space ran out mid-run, the run stops with the full error shown; free space by moving the drive's contents to a bigger drive first, or back up to a second drive. If the run stopped at the 5 GB free cap — unlikely for an AVIF collection alone, possible on a whole-library default run — run it again and it picks up where it stopped, because files already copied are never copied twice. If an AVIF on the drive does not open, the copy is not the suspect — the viewer is. Check the phone's Android version: on Android 11 and earlier the gallery cannot decode AVIF at all, because the decoder only arrived in Android 12 — open the file in Chrome instead, and if it opens in Chrome the file is fine and the gallery is old. If it opens nowhere, check the source file's extension: if it ends in .jpg, the picture was converted by a share step before you copied it; if it is a still image, it was flattened by a share step. Find the original .avif in Downloads, Pictures, or DCIM/Camera and copy that file instead. And the check that matters most for an AVIF that only existed inside a chat: confirm the drive copy before you delete anything from the phone. The copy in Downloads is an ordinary file and will survive; the copy in the chat depends on the chat app keeping it, and an AVIF that was served from a library is gone when the library stops serving it. The drive is a plain folder of plain files. Anyone who picks up the drive can open them. That is the price of a copy you can open anywhere, and it is worth stating before the AVIFs leave the phone — especially for AVIFs, where the picture is often someone else's work.

What to avoid

  • Assuming an AVIF you viewed is a .avif file on your phone. It usually is not saved until you save it — an AVIF you only viewed on a web page was never a file, and a picture you picked from the keyboard's search was served from a library and never touched your storage. A one-tap backup copies zero AVIFs until the AVIFs exist as .avif files in Downloads, Pictures, or DCIM/Camera.
  • Assuming the default run covers your AVIFs. It may not — the default run reads the media index, and whether the phone's media scanner indexes .avif files is not settled by the public Android sources. A green backup copies zero AVIFs while the folders sit full of .avif files, and nothing in the run tells you it happened. Check the drive for .avif files after every run.
  • Assuming the From picker covers your AVIFs. It cannot — proven from the code: the picker walks the folder and keeps only the extensions in the app's recognised list, and .avif is not in that list. Pointing the picker at Downloads copies every photo in the folder except the AVIFs. Copy them by hand in the Files app instead.
  • Assuming the chat apps keep .avif files. WhatsApp and Telegram keep pictures as chat images, and a picture sent as a chat image can be re-encoded as a JPEG before it ever reaches your storage — only a file sent as a document lands as a .avif. A keyboard picture was served from a library and never touched your storage. The chat pictures live in the chat and reappear when you sign in; the files were never yours to keep.
  • Re-sharing an AVIF to get it onto the drive. Sharing an AVIF out of the Gallery or a chat can re-encode it as a JPEG and drop the HDR and the transparency, or take only the still out of a Motion Photo. Copy the saved .avif file, never a re-shared copy; a converted copy never gets its HDR back.
  • Renaming a file to change its format. Renaming photo.avif to photo.jpg does not convert it — the AVIF data stays inside a file called .jpg, and the next app that opens it by extension will fail or misread it. Convert with an image editor or a converter; never rename.
  • Assuming one folder holds every AVIF. UNVERIFIED as a single path — the folder depends on where the AVIF was saved: Downloads for a browser download, Pictures for an app save, DCIM/Camera for a camera shot or a Motion Photo. Check Downloads first, then Pictures, then DCIM/Camera — do not plan a backup around a single path.
  • Assuming the default run is test-proven for AVIF. Untested — no SnapDisk test has run an AVIF backup end to end on a real phone, and whether the index holds a .avif at all is device-dependent. The code supports the default route and the folder names are ordinary, but do not plan a backup around it as the only route; Method 2's manual copy is the certain one.
  • Assuming a still on the drive means the copy failed. It does not — the copy is byte-for-byte, so a still on the drive means the source was already a still: an AVIF flattened by a share step, or a screenshot. Check the source file, not the run; find the original .avif and copy that file instead.
  • Assuming an AVIF you converted is the original. An AVIF you made from a JPEG or a PNG is a smaller, compressed copy of it. The original is usually still in DCIM/Camera at full quality. Back the original up, and use the AVIF only when the original is gone — except an AVIF with HDR, which must stay an AVIF, because converting it throws the HDR away.
  • Assuming a screenshot is the AVIF. It is not — a screenshot is a picture of the screen, a still image, usually a PNG or a JPEG, carrying the app chrome around it, and it lands in the Screenshots folder, not with the AVIFs. It does not hold HDR and it has no transparency. Save the AVIF itself when the save works, and screenshot only when it does not.
  • Assuming screen-off continuation under battery saver. UNVERIFIED — the repo holds no wake lock and no battery-saver handling. Keep the phone awake for the run, or check it.
  • Using a FAT32 drive for a library with long videos. FAT32 cannot hold a single file over 4 GB, and a library with long 4K clips will hold one. SnapDisk skips those files and lists them — use exFAT.
  • Assuming the free 5 GB cap covers the whole library. It is per run. A library over 5 GB needs several free runs — run it again and it picks up where it stopped — or one $9.99 Pro purchase.
  • Unplugging mid-copy. Pulling a USB drive out while files are still writing can corrupt the file in flight. Wait for the copy to finish, or pause it first — SnapDisk's Stop button exists for exactly this. An unplug mid-copy leaves a half-copied library that looks finished until you count it.
  • Checking the drive by opening any photo. Open an AVIF back from the drive and look at it — check it opens, and check it is the picture you saved — not just any photo. A random check passes even when the one format you cared about was never copied, because the photos that did copy render fine.
  • Checking an AVIF in the gallery on an old phone. On Android 11 and earlier the gallery cannot decode AVIF at all — the decoder only arrived in Android 12. A blank thumbnail there means the gallery is old, not the file is bad. Open the file in Chrome, which has shown AVIF since version 89, before you conclude anything.

Rule of thumb: Find the .avif file first, then back it up — the AVIFs you viewed on the web are in Downloads, the camera shots are .avif files in DCIM/Camera, and the HDR and the transparency live inside the file, so the saved .avif is the only copy that still holds them — and the From picker skips .avif files, so copy them by hand if the default run did not carry them.
